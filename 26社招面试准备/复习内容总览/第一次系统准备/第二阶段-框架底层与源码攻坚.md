## Day 4 - React Fiber 架构与渲染底层 (3.8，周末)

> **今日策略**：这是决定你能否定级高级工程师（P6+）的最核心理论阵地！抛开所有 API 表象，直击 React 为什么要在 v16 重写底层的根本原因。

### 0. 浏览器线程机制深度解析（理解 Fiber 的前提）

在深入 Fiber 之前，必须先彻底理解浏览器的线程模型。这是理解"为什么 React 15 会阻塞"和"为什么 Fiber 能解决阻塞"的底层基础。

#### 0.1 浏览器的核心线程架构

**浏览器是多进程架构，但每个标签页内部是多线程的**：

**主进程（Browser Process）**：
- 负责浏览器 UI（地址栏、书签栏等）
- 管理其他进程（标签页进程、GPU 进程、网络进程等）
- **每个标签页是一个独立的渲染进程（Renderer Process）**

**渲染进程（Renderer Process）内部的核心线程**：

1. **主线程（Main Thread / UI Thread）**：
   - **职责**：执行 JavaScript、解析 HTML/CSS、布局（Layout）、绘制（Paint）、处理用户交互事件
   - **关键特性**：**单线程执行，同步阻塞**
   - **为什么是单线程**：JavaScript 设计之初就是为了避免多线程带来的复杂同步问题（锁、死锁等）
   - **致命问题**：如果 JS 代码执行时间过长，会阻塞后续所有任务（包括渲染、用户交互）

2. **合成线程（Compositor Thread）**：
   - **职责**：将页面分层（Layer），合成最终画面，发送给 GPU 进程
   - **关键特性**：**独立线程，不阻塞主线程**
   - **工作原理**：主线程把需要绘制的图层信息传给合成线程，合成线程在 GPU 上合成画面

3. **光栅化线程（Raster Thread）**：
   - **职责**：将图块（Tile）光栅化为位图
   - **关键特性**：**多线程并行**（通常有多个光栅化线程）
   - **工作原理**：合成线程把图层分割成图块，分发给多个光栅化线程并行处理

4. **网络线程（Network Thread）**：
   - **职责**：处理网络请求（HTTP/HTTPS）
   - **关键特性**：**异步执行，不阻塞主线程**
   - **工作原理**：当主线程发起 `fetch` 或 `XMLHttpRequest` 时，网络线程在后台处理，完成后通过事件循环通知主线程

5. **存储线程（Storage Thread）**：
   - **职责**：处理本地存储（LocalStorage、IndexedDB 等）
   - **关键特性**：**异步执行，不阻塞主线程**

#### 0.2 主线程的工作流程（事件循环 Event Loop）

**主线程是单线程的，但它通过"事件循环"机制实现了异步效果**：

```
┌─────────────────────────────────────┐
│        主线程（单线程）                │
├─────────────────────────────────────┤
│  1. 执行同步 JS 代码（Call Stack）  │
│  2. 处理微任务队列（Microtask Queue）│
│  3. 处理宏任务队列（Macrotask Queue）│
│  4. 执行渲染流程（Render Pipeline）   │
│  5. 回到步骤 1，循环往复              │
└─────────────────────────────────────┘
```

**详细执行流程**：

1. **执行同步代码**：
   ```javascript
   console.log('1');
   setTimeout(() => console.log('2'), 0);
   Promise.resolve().then(() => console.log('3'));
   console.log('4');
   // 输出：1, 4, 3, 2
   ```
   - 先执行所有同步代码（1, 4）
   - 遇到异步任务，交给对应线程处理，回调函数放入任务队列

2. **处理微任务队列（Microtask Queue）**：
   - **来源**：`Promise.then/catch/finally`、`queueMicrotask`、`MutationObserver`
   - **特性**：**优先级最高**，必须全部执行完才能继续
   - **执行时机**：每次 Call Stack 清空后，立即执行所有微任务

3. **处理宏任务队列（Macrotask Queue / Task Queue）**：
   - **来源**：`setTimeout`、`setInterval`、`setImmediate`（Node.js）、`I/O` 操作、`UI 事件`
   - **特性**：每次事件循环**只执行一个**宏任务
   - **执行时机**：微任务队列清空后，从宏任务队列取一个执行

4. **执行渲染流程（Render Pipeline）**：
   - **时机**：每 16.67ms（60fps）执行一次，但如果主线程被阻塞，会跳过
   - **步骤**：
     ```
     Style（样式计算） → Layout（布局/重排） → Paint（绘制） → Composite（合成）
     ```
   - **关键点**：如果主线程被 JS 代码阻塞，渲染流程无法执行，页面就会卡顿

#### 0.3 为什么说"JS 线程和渲染线程互斥"？

**准确说法**：**主线程同时负责执行 JS 和渲染，它们是互斥的**。

**互斥的原因**：
- 主线程是**单线程**的，同一时刻只能做一件事
- 如果 JS 代码在执行，渲染流程就必须等待
- 如果渲染流程在执行，JS 代码就必须等待

**实际场景**：
```javascript
// 场景 1：JS 阻塞渲染
function heavyTask() {
  const start = Date.now();
  while (Date.now() - start < 2000) {
    // 阻塞主线程 2 秒
  }
}
heavyTask(); // 这 2 秒内，页面无法渲染，用户交互无响应

// 场景 2：渲染阻塞 JS（较少见）
// 当浏览器正在执行 Layout/Paint 时，JS 代码会等待
```

#### 0.4 异步任务的底层机制

**为什么 `setTimeout`、`fetch` 不会阻塞主线程？**

1. **`setTimeout`**：
   - 主线程把定时器交给**定时器线程**（浏览器内部线程）管理
   - 定时器线程在指定时间后，把回调函数放入**宏任务队列**
   - 主线程在下次事件循环时，从宏任务队列取出执行

2. **`fetch` / `XMLHttpRequest`**：
   - 主线程把网络请求交给**网络线程**处理
   - 网络线程在后台发送请求，等待响应
   - 响应到达后，网络线程把回调函数放入**宏任务队列**
   - 主线程在下次事件循环时执行回调

3. **`Promise.then`**：
   - 虽然网络请求是异步的，但 `Promise.then` 的回调是**微任务**
   - 微任务会在当前同步代码执行完后、下一个宏任务之前执行
   - 这就是为什么 `Promise.then` 比 `setTimeout` 先执行

#### 0.5 渲染流程的详细步骤

**每次渲染（每 16.67ms）的完整流程**：

1. **Style（样式计算）**：
   - 计算每个元素的最终样式（考虑 CSS 选择器优先级、继承等）
   - 生成 Render Tree（渲染树）

2. **Layout（布局/重排 Reflow）**：
   - 计算每个元素的位置和大小
   - **触发条件**：修改了影响布局的属性（`width`、`height`、`position`、`display` 等）
   - **性能影响**：**最耗性能**，会触发整个 Render Tree 的重新计算

3. **Paint（绘制/重绘 Repaint）**：
   - 填充每个元素的像素（颜色、背景、边框等）
   - **触发条件**：修改了不影响布局但影响外观的属性（`color`、`background`、`border-radius` 等）
   - **性能影响**：比 Layout 轻量，但仍有开销

4. **Composite（合成）**：
   - 将图层合成最终画面
   - **触发条件**：修改了只影响合成的属性（`transform`、`opacity`、`will-change` 等）
   - **性能影响**：**最轻量**，只在合成线程和 GPU 上执行，不阻塞主线程

**性能优化黄金法则**：
- **避免触发 Layout**：用 `transform` 和 `opacity` 做动画，而不是修改 `width`、`height`
- **利用 GPU 加速**：`transform` 和 `opacity` 会触发 GPU 合成，不阻塞主线程

#### 0.6 与 React Fiber 的关系

**现在你就能理解为什么 React 15 会阻塞了**：

1. React 15 的同步递归会**长时间霸占主线程**
2. 主线程被占用 → 渲染流程无法执行 → 页面卡顿
3. 主线程被占用 → 用户交互事件无法处理 → 点击无响应

**Fiber 的解决方案**：
1. 把大任务切成小任务（每个 Fiber 节点）
2. 每完成一个小任务，就**主动让出主线程**
3. 让浏览器有机会执行渲染流程和处理用户交互
4. 等浏览器忙完，再继续处理下一个 Fiber 节点

**这就是"时间切片（Time Slicing）"的底层原理**！

### 1. 为什么 React 要耗费巨资重写 Fiber 架构？（历史演进）

面试官最爱问的宏观问题：“你能讲讲 React 15 和 React 16 在渲染架构上的核心区别吗？为什么要引入 Fiber？”

**满分回答逻辑（分为痛点与解法）：**

**痛点（React 15 的 Stack Reconciler 的致命缺陷）：**
1. 以前 React 的对比和渲染是一个**同步的递归过程**。
2. JS 线程和浏览器的 GUI 渲染线程是**互斥的**（这俩在同一个线程里，你跑我就得停）。
3. 如果组件树非常庞大，React 一旦开始递归 Diff，就会死死霸占主线程几百毫秒甚至几秒钟不撒手。
4. 这期间，用户的点击没反应，页面的动画直接卡死（掉帧），这就叫**“渲染阻塞”**。

**解法（Fiber 的降维打击）：**
1. React 团队把原来不可中断的递归，改写成了基于**链表结构**的循环。这个链表上的每一个节点，就是一个 **Fiber 对象**。
2. 因为变成了链表，所以这个庞大的渲染任务可以被**“切片（Time Slicing）”**了！
3. React 每执行完一个 Fiber 节点，都会抬起头看看浏览器：**“你现在还有空闲时间吗？还要不要渲染动画？要不要处理用户点击？”**
4. 如果浏览器说“我得渲染动画了”，React 就会**主动让出主线程控制权**，等浏览器忙完了，React 再顺着链表里的指针（`next` 或 `sibling`）回来接着刚才的地方继续算。
5. 这就实现了传说中的 **“可中断的异步渲染”**，彻底解决了页面卡顿问题。

### 2. Fiber 树到底长什么样？（双缓存树结构）

在内存里，React 其实同时维护着**两棵** Fiber 树，这被称为 **双缓存机制（Double Buffering）**：
1. **`current` 树**：当前屏幕上正在显示的树。
2. **`workInProgress` (WIP) 树**：React 正在内存里偷偷计算、构建的新树。

**它们是怎么交替的？**
当 React 算完了所有的 Diff，准备把变化应用到真实 DOM 上时（Commit 阶段），它只需要把内部的一根指针（`fiberRoot.current`），从旧树**瞬间切换**到新算好的 WIP 树上。
那一刻，WIP 树变成了新的 `current` 树，屏幕瞬间更新！这避免了用户看到渲染到一半的“撕裂”画面。

### 3. Render 阶段与 Commit 阶段（生命周期的分水岭）

React 的整个工作流被严丝合缝地分成了两个大阶段。记住这两个阶段，你就能完美解释所有生命周期的表现。

#### 3.1 Render 阶段（可以被打断！）
- **工作内容**：React 在内存里遍历 Fiber 链表，执行组件函数，计算 Diff（新老虚拟 DOM 对比），收集需要更新的副作用（Effect List / Update Queue）。
- **核心特点**：这个阶段因为只是在内存里算，不碰真实 DOM，所以**它是可以被高优先级任务随时打断、甚至废弃重来的！**
- **结论**：这也是为什么 `componentWillMount` 等老生命周期被 React 官方废弃（加上 `UNSAFE_` 前缀）的原因！因为它们处在 Render 阶段，如果渲染被打断并重启，这些生命周期会被**调用多次**，如果里面写了发请求的代码，就会导致极其严重的 Bug！

#### 3.2 Commit 阶段（绝对不可打断！）
- **工作内容**：React 拿着上面算好的更新清单，**一鼓作气**地把变化应用到真实的 DOM 树上。
- **核心特点**：这个阶段是**同步执行**的，绝对不让出主线程。因为如果要操作 DOM 还让出线程，用户就会看到页面闪烁（撕裂）。
- **生命周期/Hooks 的执行点**：DOM 更新完毕后，立刻同步执行 `useLayoutEffect`，随后浏览器绘制屏幕，最后异步执行 `useEffect`。

## Day 5 - React Hooks 底层与并发模式 (3.9，周一)

> **今日策略**：懂了 Fiber 之后，今天我们来扒开日常天天在用的 Hooks 的外衣。面试官非常喜欢问：“为什么 Hooks 必须写在最顶层？”

### 1. Hooks 的底层数据结构：一条脆弱的链表

面试官最毒辣的陷阱：“如果我在一个 `if` 语句里面写了 `useState`，会发生什么？为什么 React 官方死活不让这么干？”

**满分回答逻辑：**

1. **它是怎么存的？** 
   在 Fiber 节点（也就是你这个组件）的底层对象上，有一个属性叫 `memoizedState`。当你在组件里写了一堆 `useState` 和 `useEffect` 时，React **并不是**根据变量名（比如 `[count, setCount]` 里的 count）来存它的。
   **React 仅仅是把它们按你代码里写的顺序，串成了一条单向链表！** 
   （第一个 `useState` 连着第二个 `useEffect`，再连着第三个 `useState`...）

2. **为什么不能放进 `if`？**
   由于它是靠**“顺序”**来取值的。当组件重新渲染时，React 内部的一根指针会从头开始遍历这条链表。
   假设你原来有 3 个 Hook。如果在某次渲染时，因为 `if (false)` 导致第 2 个 Hook 没被执行到。
   那么当代码跑到第 3 个 Hook 时，React 指针依然只指向链表的第 2 个位置！它把原本属于老三的坑位，给了老四。
   **瞬间，所有的状态和副作用全部错位（串序）！** 你的 `name` 变成了 `age` 的值，程序直接崩溃报 `Rendered fewer hooks than expected` 错误。
   
   这才是“不能在条件语句中写 Hooks”的底层真相！

### 2. `useEffect` 与 `useLayoutEffect` 的致命差异

这俩长得一模一样，但它们在时间轴上的执行时机，有着天壤之别。

- **`useLayoutEffect`（霸道总裁，同步阻塞）**
  - **时机**：在 React 刚刚把真实 DOM 操作完，**但浏览器还没来得及把这些变化画（Paint）到屏幕上** 的那一瞬间，它**同步**拦截了主线程开始执行。
  - **副作用**：如果你的里面写了非常耗时的计算，屏幕会白屏！因为浏览器在等你执行完，才敢把画面放出来。
  - **适用场景**：你需要在 DOM 刚出来时立刻读取它的尺寸（比如 `getBoundingClientRect`），并基于这个尺寸再修改一次 DOM。用它就不会让屏幕出现“先高后矮”的闪烁。

- **`useEffect`（谦谦君子，异步非阻塞）**
  - **时机**：在 React 搞完了 DOM，**并且浏览器已经把画面完全展示给用户之后**，它才在一个**宏任务**（或者利用 `MessageChannel` 等方式）里异步悄悄执行。
  - **副作用**：绝不会阻塞页面的视觉渲染，用户能极快地看到画面。
  - **适用场景**：发网络请求、绑定事件监听、一切不影响当前视觉结构的副作用。

### 3. 并发模式（Concurrent Mode）的终极武器

React 18 之后，真正的“可中断渲染”被暴露给了开发者。面试官极大概率会问：**“什么是 `useTransition` 和 `useDeferredValue`？它们解决了什么业务痛点？”**

**痛点场景：** 
页面上有一个搜索框，你每敲一个字母，不仅要更新输入框的值，页面下面还有一个极其庞大的列表（比如 1 万条数据）要跟着重新渲染。这时候，输入框会卡到连字母都打不出来。

**普通防抖的痛：**
虽然你可以用防抖（Debounce）等 500ms，但这会让用户觉得有“半秒钟的迟钝感”，不丝滑。

**并发武器：`useTransition` 的降维打击！**
它允许你把状态更新分成**“高优先级”**和**“低优先级（过渡）”**！

```javascript
const [text, setText] = useState('');
const [isPending, startTransition] = useTransition();

function handleChange(e) {
  // 1. 高优先级更新：立刻让输入框显示出用户敲的字，绝不能卡！
  setText(e.target.value); 

  // 2. 低优先级更新：把那个会导致严重卡顿的庞大列表渲染，包裹在 startTransition 里
  startTransition(() => {
    setSearchQuery(e.target.value); 
  });
}
```

**底层发生了什么奇迹？**
当 React 开始算那个巨大列表的 Diff 时（这是低优先级的），一旦用户敲了下一个字母（触发了高优先级事件）。
**React 内部直接一脚踢翻那个还没算完的巨大列表任务（中断它！）**，跑去优先处理输入框的显示。等输入框没事了，再回头重算列表。

这就实现了：**输入框永远不卡，列表随你慢慢渲。** 
这就是 React Fiber 架构耗费数年心血换来的终极大招——时间切片与优先级调度在业务层的完美展现！

## Day 6 - 虚拟 DOM、Diff 算法与状态管理演进 (3.10)

> **今日策略**：这是 React 深度考察的最后一环。我们将彻底拆解 React 的心智基石——虚拟 DOM 为什么能变快？Diff 为什么需要 key？以及面试必考的“四大状态管理神兽”的底层哲学。

### 1. 虚拟 DOM（Virtual DOM）真的比操作真实 DOM 快吗？

这是大厂面试的“钓鱼题”！如果你回答“是的，因为操作真实 DOM 太慢了”，你直接就出局了。

**满分绝杀回答：**
> “不一定！**没有任何框架能比纯手工、极致优化的原生 DOM 操作更快。**”
> “虚拟 DOM 的本质，是在 JS 和真实 DOM 之间加了一层**内存缓存**。
> 
> 1. **它真正解决的痛点是‘心智负担’**：它让我们工程师可以像写状态机一样，只关心数据长什么样（声明式），而不需要去手动写繁琐的 `document.createElement` 和 `appendChild`（命令式）。它**保底了性能的下限**。
> 2. **极致的批量更新**：当你短时间内多次修改状态时，React 并不是立刻去改真实 DOM。它在内存里把一堆 Virtual DOM 的修改合并起来（批量更新），最后只对真实 DOM 做一次最少的、精细的 `patch` 打补丁操作。这避免了浏览器频繁触发重排（Reflow）。
> 3. **跨端基建**：因为 Virtual DOM 本质上只是一个纯 JS 的普通对象（包含 `type`, `props`, `children`），它完全脱离了浏览器的束缚！这使得 React 能够非常轻松地渲染到 iOS/Android（React Native）甚至终端命令行上。”

### 2. Diff 算法与 `key` 的底层奥秘

当组件状态改变时，React 需要对比新旧两棵虚拟 DOM 树，找出差异。如果用传统的树对比算法，时间复杂度是极其恐怖的 `O(n³)`（一千个节点要对比十亿次！）。
为了在浏览器里跑得动，React 强行把复杂度降到了极其暴力的 **`O(n)`**。

**它是怎么做到的？（三大假设策略）：**
1. **Tree Diff（只做同级对比）**：如果一个节点在树里的层级变了（比如从老爸的儿子变成了老爸的兄弟），React 根本懒得去挪动它，它会**直接把旧节点及其子树全部销毁，然后在新的位置重新创建一个全新的节点！**
2. **Component Diff（组件类型对比）**：如果把一个 `<Button>` 换成了一个 `<Header>`，React 认定它们结构肯定不同，直接销毁旧组件，新建新组件，**绝对不比较它们内部的 DOM 结构**。
3. **Element Diff（同级兄弟列表对比 —— 这里就是 `key` 的用武之地！）**

**灵魂拷问：列表渲染时，如果不加 `key` 或者把 `key` 设为数组的 `index`，会发生什么灾难？**

**灾难推演（用大白话解释）：**
假设你有一个数组 `[A, B, C]`，你把它渲染成了三个 `<li>`。
现在，你往数组的**最前面**插入了一个 `X`，变成了 `[X, A, B, C]`。

- **如果没有 `key`（或 `key` 是 `index` 0,1,2,3）**：
  React 的 Diff 算法极其傻白甜，它只会按顺序一个个比对：
  - 它拿新的第 1 个节点（X）和旧的第 1 个节点（A）比对。它一看，字变了！于是它强行把真实 DOM 里的 `A` 删掉，改写成 `X`。
  - 它拿新的第 2 个节点（A）和旧的第 2 个（B）比对。它又强行把 `B` 改成 `A`。
  - ...最后它在末尾新建了一个 `C`。
  **结果：所有的 DOM 节点都被极其消耗性能地“重写”了一遍！**

- **如果绑定了稳定唯一的 `key`（比如数据的 `id`）**：
  React 的 Diff 算法瞬间变成了带雷达的侦探！
  - 它看到新的列表里有一个带有 `key="X"` 的新节点，而旧列表里根本没有这个 `key`。
  - 接着，它发现旧列表里的 `key="A"`、`key="B"`、`key="C"`，在新列表里**依然存在**，只是位置往后挪了一格。
  - **奇迹发生**：React 绝对不去碰原本那三个真实 DOM 的内部内容，它只做一件事——**把新造好的 `X` 对应的 DOM，轻轻地“移动（插入）”到原来那三个 DOM 的最前面！**
  
**总结**：`key` 是 React 在列表 Diff 时的**唯一身份证**。有了它，React 才能识别出“哪些元素是新来的，哪些是仅仅改变了位置的老员工”，从而最大限度地复用已有 DOM，避免极其昂贵的推翻重绘。这就是为什么绝对不能用 `index` 做 `key` 的底层原因（因为一插入，所有老员工的身份证号全变了）！

### 3. 状态管理演进史（大厂极爱考架构选型）

面试官：“你们项目用的什么状态管理？能对比一下 Redux、MobX 和新兴的 Zustand/Jotai 吗？”

这是一道考验你“架构视野”的题目。不要背 API，要讲**设计哲学**：

#### 3.1 Redux（严谨古板的老派工程师）
- **核心哲学：单向数据流 & 纯函数。**
- **机制**：它强制要求所有状态变更必须派发一个 `Action`（命令），然后交给一个完全纯净的 `Reducer` 去计算出全新的状态（严格遵守 Immutable 不可变数据）。
- **痛点**：极其繁琐！改个状态要写三份文件（Action、Reducer、Store）。而且它是全局一棵巨大的树，如果组件不加优化地 `useSelector`，极易引发大面积的无用重渲染。
- **现状**：现在一般搭配 `@reduxjs/toolkit` 使用，通过内部集成 Immer.js 解决了手写不可变数据的痛苦。

#### 3.2 MobX（聪明的魔法师）
- **核心哲学：响应式（Reactive）。**（像极了 Vue！）
- **机制**：它在底层用 `Proxy`（或早期的 `defineProperty`）把数据包装成了响应式对象。你在组件里直接像改普通变量一样 `obj.name = "Tom"`，它就能精准拦截，并**只触发**用到了这个属性的组件去重新渲染。
- **痛点**：因为太像 Vue，破坏了 React “不可变数据”和“函数式编程”的心智模型。大厂在核心复杂项目中用得较少，因为这种魔法导致 Bug 极难追踪来源。

#### 3.3 Zustand（极简主义的现代救星）
- **核心哲学：轻量级原子化 / Hooks 驱动。**
- **机制**：彻底抛弃了 Redux 繁琐的 Provider 嵌套和 Reducer。直接创建一个包含状态和修改方法的 Hook。
- **优势**：学习成本几乎为 0，完美契合 React Hooks 的心智模型，体积极小，且默认解决了重新渲染的性能问题。它是目前大厂（如字节）新项目里极其推崇的替代品。

#### 3.4 Jotai / Recoil（真正的原子化碎片）
- **核心哲学：自下而上的原子（Atom）。**
- **机制**：不再像 Redux 那样维护一棵巨大的状态树，而是把状态打碎成一个个独立的"原子（Atom）"。需要什么原子，组件就订阅什么原子。
- **优势**：由于状态被极致打碎，组件的重渲染控制达到了变态级的精准。非常适合类似"Figma / 在线画布"这种页面上有一万个小零件，每个零件状态独立的高频交互场景。

## Day 7 - Vue3 核心机制（多栈融合考察）(3.11，周三)

> **大厂面试背景**：即使你主栈是 React，面试官也极大概率会问 Vue3 的响应式原理。这不仅是考察你的技术广度，更是测试你是否理解"响应式系统"这一前端核心设计模式。

### 1. Vue3 响应式原理：Proxy + Reflect 的完美协同

Vue3 彻底抛弃了 Vue2 的 `Object.defineProperty`，改用 ES6 的 `Proxy`。这是 Vue3 最核心的升级，也是大厂面试的必考点。

#### 1.1 为什么 Vue2 的 `defineProperty` 不行了？

**Vue2 的致命缺陷**：
1. **无法监听数组索引和长度变化**：`defineProperty` 只能拦截对象的属性访问，对于数组的 `push`、`pop`、`splice` 等方法，Vue2 只能通过**重写数组原型方法**来模拟响应式，极其 hack。
2. **无法监听对象属性的新增/删除**：如果你在运行时给对象动态添加属性（`obj.newProp = 'value'`），Vue2 完全监听不到，必须用 `Vue.set()` 这种特殊 API。
3. **性能瓶颈**：Vue2 在初始化时，必须递归遍历整个对象的所有属性，用 `defineProperty` 一个个包装。如果对象有 1000 个属性，就要执行 1000 次 `defineProperty`，初始化极慢。

#### 1.2 Proxy 的降维打击

**Proxy 是什么？**
`Proxy` 是 ES6 提供的"元编程"能力，它可以在**对象外层包一层拦截器**，拦截这个对象的所有操作（读取、赋值、删除、遍历等）。

**核心代码示例（极简版 Vue3 响应式）**：
```javascript
// Vue3 响应式系统的核心骨架
function reactive(target) {
  return new Proxy(target, {
    // 拦截"读取"操作（比如 obj.name）
    get(target, key, receiver) {
      // 1. 依赖收集：记录"谁在用这个属性"
      track(target, key);
      // 2. 用 Reflect 保证 this 指向正确
      return Reflect.get(target, key, receiver);
    },
    
    // 拦截"赋值"操作（比如 obj.name = 'newValue'）
    set(target, key, value, receiver) {
      // 1. 先赋值
      const result = Reflect.set(target, key, value, receiver);
      // 2. 派发更新：通知所有依赖这个属性的地方"数据变了，快更新！"
      trigger(target, key);
      return result;
    },
    
    // 拦截"删除"操作（比如 delete obj.name）
    deleteProperty(target, key) {
      const result = Reflect.deleteProperty(target, key);
      trigger(target, key);
      return result;
    }
  });
}
```

#### 1.3 为什么必须用 `Reflect`？

**面试官必问**：为什么 Vue3 在 Proxy 里还要用 `Reflect.get/set`，而不是直接用 `target[key]`？

**底层真相**：
1. **`this` 指向问题**：如果你在 Proxy 里直接返回 `target[key]`，当对象的属性是一个 `getter` 函数时，这个 `getter` 里的 `this` 会指向原始的 `target`，而不是被 Proxy 包装后的对象。这会导致嵌套对象的响应式失效！
2. **`Reflect` 的 `receiver` 参数**：`Reflect.get(target, key, receiver)` 的第三个参数 `receiver`，会强制把 `getter` 的 `this` 绑定到 `receiver`（也就是 Proxy 对象本身），从而保证响应式链路的完整性。

**代码示例（理解 this 指向问题）**：
```javascript
const obj = {
  _name: 'Tom',
  get name() {
    return this._name; // 这里的 this 指向谁？
  }
};

// 如果不用 Reflect，this 指向原始对象，响应式失效
// 用了 Reflect，this 指向 Proxy，响应式链完整
```

#### 1.4 依赖收集（track）与派发更新（trigger）的底层机制

**依赖收集（track）**：
- 当组件渲染时，如果模板里用到了 `obj.name`，Vue3 会执行 `get` 拦截器
- `track(target, 'name')` 会把这个组件（或 `effect` 函数）记录到一个"依赖地图"里：`{ target: { name: [effect1, effect2, ...] } }`
- 意思是："`name` 这个属性，被 `effect1` 和 `effect2` 两个地方依赖了"

**派发更新（trigger）**：
- 当你执行 `obj.name = 'newValue'` 时，`set` 拦截器被触发
- `trigger(target, 'name')` 会从依赖地图里找出所有依赖 `name` 的 `effect`，然后**依次执行它们**
- 这些 `effect` 执行时，会重新渲染组件，从而更新视图

**面试加分点**：Vue3 的响应式系统本质上是一个**发布-订阅模式**。`track` 是"订阅"，`trigger` 是"发布"。

### 2. Vue3 编译优化：静态提升与补丁标记

Vue3 在编译阶段做了大量优化，这是它性能碾压 Vue2 的另一个核心原因。

#### 2.1 静态提升（Static Hoisting）

**问题**：在 Vue2 中，每次组件重新渲染时，即使模板里有一些**永远不会变的静态内容**（比如 `<div class="header">标题</div>`），Vue2 也会重新创建这些虚拟 DOM 节点，造成无意义的性能浪费。

**Vue3 的解决方案**：
Vue3 的编译器会在编译时识别出所有静态节点，然后**把它们提升到组件函数外面**，只创建一次，后续渲染直接复用。

**代码对比**：
```javascript
// Vue2 编译后的伪代码（每次渲染都创建）
function render() {
  return h('div', [
    h('div', { class: 'header' }, '标题'), // 每次都创建
    h('div', this.dynamicContent) // 动态内容
  ]);
}

// Vue3 编译后的伪代码（静态节点只创建一次）
const _hoisted_1 = h('div', { class: 'header' }, '标题'); // 提升到外面

function render() {
  return h('div', [
    _hoisted_1, // 直接复用，不重新创建
    h('div', this.dynamicContent) // 只创建动态部分
  ]);
}
```

#### 2.2 补丁标记（PatchFlag）

**问题**：Vue2 在更新时，会对比整个虚拟 DOM 树，即使某个节点只有一个属性变了，也要对比这个节点的所有属性。

**Vue3 的解决方案**：
Vue3 的编译器会在编译时给每个节点打上"补丁标记"，标记这个节点**哪些属性是动态的**。更新时，Vue3 只需要对比标记过的属性，跳过静态属性。

**代码示例**：
```javascript
// 模板
<div class="static" :id="dynamicId" :title="dynamicTitle">内容</div>

// Vue3 编译后的虚拟 DOM（伪代码）
{
  type: 'div',
  props: {
    class: 'static', // 静态，不标记
    id: dynamicId,  // 动态，标记为 PatchFlag.PROPS（1）
    title: dynamicTitle // 动态，标记为 PatchFlag.PROPS（1）
  },
  patchFlag: 1 // 标记：只有 props 会变
}

// 更新时，Vue3 看到 patchFlag = 1，就知道只需要对比 props，class 直接跳过
```

#### 2.3 事件监听缓存（Event Handler Caching）

**问题**：在 Vue2 中，每次渲染时，即使事件处理函数没变，Vue2 也会重新创建函数对象。

**Vue3 的解决方案**：
Vue3 会把事件处理函数缓存起来，如果函数没变，直接复用，避免无意义的函数创建。

### 3. React vs Vue3：Diff 算法与更新粒度的根本差异

这是大厂面试的**超高频对比题**。不要背答案，要理解底层设计哲学。

#### 3.1 更新粒度的差异

**React**：
- **组件级更新**：React 的更新粒度是"组件"。只要组件的 `props` 或 `state` 变了，**整个组件树都会重新渲染**（虽然 React 会用 Diff 算法尽量复用 DOM，但虚拟 DOM 的创建和对比是逃不掉的）。
- **为什么这样设计**：React 追求"函数式编程"和"不可变数据"，它认为"重新渲染"是纯函数执行，副作用由 `useEffect` 等 Hooks 管理，逻辑更清晰。

**Vue3**：
- **属性级更新**：Vue3 的更新粒度是"属性"。因为响应式系统在编译时就知道"哪个组件依赖了哪个属性"，所以当 `obj.name` 改变时，**只有依赖了 `name` 的组件会更新**，其他组件完全不动。
- **为什么这样设计**：Vue3 追求"精准更新"，通过编译时分析和运行时依赖追踪，实现最小化更新范围。

**面试表达**：
> "React 是'推倒重建，但用 Diff 算法尽量复用'，Vue3 是'精准定位，只更新需要更新的部分'。React 的优势是逻辑清晰、易于调试；Vue3 的优势是性能更极致，但响应式系统的复杂度更高。"

#### 3.2 Diff 算法的差异

**React**：
- **全量 Diff**：React 会对整个虚拟 DOM 树进行 Diff，虽然用了三大假设（Tree Diff、Component Diff、Element Diff）把复杂度降到 O(n)，但对比范围仍然是"整个组件树"。

**Vue3**：
- **按需 Diff**：因为 Vue3 在编译时就知道哪些节点是动态的（PatchFlag），所以更新时只需要对比标记过的节点，静态节点直接跳过。

**性能对比（极端场景）**：
- 假设一个组件有 1000 个节点，只有 1 个节点是动态的
- **React**：需要对比 1000 个节点（虽然会复用，但对比过程逃不掉）
- **Vue3**：只需要对比 1 个节点（其他 999 个静态节点被 PatchFlag 标记，直接跳过）

### 4. 面试加分：Vue3 的 Composition API 设计哲学

虽然计划里没写，但大厂面试经常问："为什么 Vue3 要引入 Composition API？"

**核心答案**：
1. **逻辑复用**：Options API（`data`、`methods`、`computed`）会把相关逻辑拆分到不同选项里，导致"一个功能的代码散落各处"。Composition API 可以把一个功能的所有逻辑（状态、方法、副作用）**聚合在一个 `setup` 函数里**，形成可复用的"组合函数"。
2. **TypeScript 支持**：Composition API 的函数式写法，天然支持 TypeScript 的类型推导，而 Options API 的类型推导极其困难。
3. **性能优化**：Composition API 配合 `<script setup>`，可以在编译时做更多静态分析，进一步优化性能。

### 5. 手写核心：极简版 Vue3 响应式系统

**面试官可能会让你手写一个最基础的响应式系统**，核心就是 Proxy + 依赖收集：

```javascript
// 依赖地图：{ target: { key: [effect1, effect2, ...] } }
const targetMap = new WeakMap();
let activeEffect = null; // 当前正在执行的 effect

// 依赖收集
function track(target, key) {
  if (!activeEffect) return;
  
  let depsMap = targetMap.get(target);
  if (!depsMap) {
    targetMap.set(target, (depsMap = new Map()));
  }
  
  let deps = depsMap.get(key);
  if (!deps) {
    depsMap.set(key, (deps = new Set()));
  }
  
  deps.add(activeEffect); // 记录：这个 effect 依赖了这个 key
}

// 派发更新
function trigger(target, key) {
  const depsMap = targetMap.get(target);
  if (!depsMap) return;
  
  const deps = depsMap.get(key);
  if (deps) {
    deps.forEach(effect => effect()); // 执行所有依赖这个 key 的 effect
  }
}

// 响应式包装
function reactive(target) {
  return new Proxy(target, {
    get(target, key, receiver) {
      track(target, key);
      return Reflect.get(target, key, receiver);
    },
    set(target, key, value, receiver) {
      const result = Reflect.set(target, key, value, receiver);
      trigger(target, key);
      return result;
    }
  });
}

// effect 函数（类似 Vue 的 watchEffect）
function effect(fn) {
  activeEffect = fn;
  fn(); // 执行一次，触发依赖收集
  activeEffect = null;
}

// 使用示例
const state = reactive({ count: 0 });

effect(() => {
  console.log('count 变了:', state.count); // 依赖收集：这个 effect 依赖 state.count
});

state.count = 1; // 触发更新：执行上面的 effect，打印 "count 变了: 1"
```

- ✅ track/trigger 实现依赖收集与派发更新（发布-订阅模式）

## Day 8 - TypeScript 高级类型与体操（一）(3.12，周四)

> **大厂面试背景**：TypeScript 是大厂高级前端的必备技能。面试官会重点考察基础类型系统的理解（`any`/`unknown`/`never`/`void`）、`interface` vs `type`、类型断言坑点，以及泛型约束和条件类型的基础应用。这是区分"会用 TS"和"理解 TS"的关键。

### 1. 类型系统进阶：any、unknown、never、void 的深层区别

这是大厂面试的**超高频基础题**。不要只背定义，要理解它们的设计意图和使用场景。

#### 1.1 `any`：类型系统的"逃生舱"

**定义**：`any` 表示"任意类型"，TypeScript 会**完全关闭类型检查**。

**特性**：
- 可以赋值给任何类型
- 任何类型都可以赋值给它
- **完全失去类型安全**

**代码示例**：
```typescript
let a: any = 'hello';
let b: number = a; // ✅ 不报错，但运行时可能出错！
a.foo.bar; // ✅ 不报错，但运行时可能报错！
```

**使用场景**：
- 迁移旧代码时的临时方案
- 与第三方库交互（没有类型定义）
- **应该尽量避免使用**，因为失去了 TypeScript 的核心价值

**面试表达**：
> "`any` 是类型系统的逃生舱，但使用它会完全失去类型安全。我们团队在代码审查时会严格限制 `any` 的使用，优先考虑 `unknown` 或泛型。"

#### 1.2 `unknown`：类型安全的"顶层类型"

**定义**：`unknown` 表示"未知类型"，是类型系统的**顶层类型**（Top Type）。

**特性**：
- 任何类型都可以赋值给它
- **但它不能赋值给其他类型**（除了 `unknown` 和 `any`）
- 必须经过**类型收窄（Type Narrowing）**才能使用

**代码示例**：
```typescript
let a: unknown = 'hello';
let b: number = a; // ❌ 报错！unknown 不能直接赋值给 number

// 必须进行类型收窄
if (typeof a === 'string') {
  let b: string = a; // ✅ 通过类型守卫，TypeScript 知道 a 是 string
}

// 或者使用类型断言（不推荐，除非你确定类型）
let b: number = a as number; // ⚠️ 类型断言，绕过类型检查
```

**与 `any` 的区别**：
- `any`：完全关闭类型检查，**不安全**
- `unknown`：强制类型收窄，**安全**

**使用场景**：
- 处理来自 API 的未知数据
- 处理用户输入
- 替代 `any` 的最佳实践

**面试表达**：
> "`unknown` 是类型安全的顶层类型。它要求我们必须先进行类型检查才能使用，这比 `any` 更安全。在处理第三方数据或用户输入时，我们优先使用 `unknown`。"

#### 1.3 `never`：类型系统的"底层类型"

**定义**：`never` 表示"永远不存在的值"，是类型系统的**底层类型**（Bottom Type）。

**特性**：
- `never` 可以赋值给任何类型
- **但没有任何类型可以赋值给 `never`**（除了 `never` 本身）
- 表示函数永远不会返回（抛出异常、死循环等）

**代码示例**：
```typescript
// 场景 1：抛出异常的函数
function throwError(message: string): never {
  throw new Error(message);
  // 函数永远不会返回，所以返回类型是 never
}

// 场景 2：死循环
function infiniteLoop(): never {
  while (true) {
    // 永远不会结束
  }
}

// 场景 3：类型收窄的穷尽性检查（Exhaustive Check）
type Shape = 'circle' | 'square' | 'triangle';

function getArea(shape: Shape): number {
  switch (shape) {
    case 'circle':
      return Math.PI * 2;
    case 'square':
      return 4;
    case 'triangle':
      return 3;
    default:
      // 如果所有 case 都处理了，这里应该是 never
      // 如果 TypeScript 报错说不能赋值给 never，说明有遗漏的 case
      const _exhaustive: never = shape;
      throw new Error(`Unknown shape: ${_exhaustive}`);
  }
}
```

**使用场景**：
- 表示函数永远不会返回
- 类型收窄的穷尽性检查（确保所有分支都被处理）
- 表示不可能的类型（如空数组的类型）

**面试表达**：
> "`never` 是类型系统的底层类型，表示永远不存在的值。我们常用它来做穷尽性检查，确保联合类型的所有分支都被处理，避免遗漏 case。"

#### 1.4 `void`：表示"没有返回值"

**定义**：`void` 表示函数**没有返回值**（或返回 `undefined`）。

**特性**：
- 只能作为函数的返回类型
- 表示函数不返回任何有意义的值
- `undefined` 可以赋值给 `void`，但 `void` 不能赋值给 `undefined`（在 `strictNullChecks` 开启时）

**代码示例**：
```typescript
// 场景 1：没有返回值的函数
function log(message: string): void {
  console.log(message);
  // 没有 return，或者 return undefined
}

// 场景 2：事件处理函数
function handleClick(): void {
  // 处理点击事件，不需要返回值
}

// 场景 3：与 undefined 的区别
let a: void = undefined; // ✅
let b: undefined = a; // ❌ 在 strictNullChecks 下报错
```

**与 `undefined` 的区别**：
- `void`：表示"没有返回值"的语义
- `undefined`：表示"值是 undefined"的类型

**面试表达**：
> "`void` 表示函数没有返回值，主要用于函数返回类型。它与 `undefined` 的区别在于语义：`void` 强调'不需要返回值'，而 `undefined` 强调'值是 undefined'。"

#### 1.5 类型层次关系图

```
        any (可以赋值给任何类型，任何类型也可以赋值给它)
         ↑
    unknown (顶层类型，任何类型可以赋值给它，但它不能赋值给其他类型)
         ↑
    string | number | boolean | ... (具体类型)
         ↑
       never (底层类型，可以赋值给任何类型，但没有类型可以赋值给它)
```

### 2. 类型断言（Type Assertion）的坑点

**类型断言**：告诉 TypeScript"我比你更清楚这个值的类型"。

#### 2.1 两种语法

```typescript
// 语法 1：as 语法（推荐）
let value: unknown = 'hello';
let str: string = value as string;

// 语法 2：尖括号语法（不推荐，在 JSX 中会冲突）
let str: string = <string>value;
```

#### 2.2 常见坑点

**坑点 1：双重断言（Double Assertion）**
```typescript
let value: string = 'hello';
let num: number = value as any as number; // ⚠️ 双重断言，绕过类型检查
// 运行时可能出错！
```

**坑点 2：断言不等于类型转换**
```typescript
let value: string = '123';
let num: number = value as number; // ⚠️ 只是告诉 TypeScript，不会真正转换
console.log(num.toFixed(2)); // 运行时报错！value 仍然是字符串
```

**正确做法**：
```typescript
let value: string = '123';
let num: number = Number(value); // 真正的类型转换
console.log(num.toFixed(2)); // ✅ 正确
```

**坑点 3：非空断言（Non-null Assertion）的滥用**
```typescript
let element: HTMLElement | null = document.getElementById('app');
element.innerHTML = 'hello'; // ❌ 可能为 null

// 使用非空断言（不推荐，除非你确定不为 null）
element!.innerHTML = 'hello'; // ⚠️ 如果 element 是 null，运行时报错

// 正确做法：类型守卫
if (element) {
  element.innerHTML = 'hello'; // ✅ 安全
}
```

**面试表达**：
> "类型断言只是告诉 TypeScript 编译器，不会进行真正的类型转换。我们团队要求使用类型守卫而不是断言，因为类型守卫会在运行时检查，更安全。"

### 3. `interface` 与 `type` 的区别（大厂超高频）

这是大厂面试的**必考题**。不要只背区别，要理解它们的设计意图。

#### 3.1 基本区别

**`interface`（接口）**：
- 主要用于**定义对象的结构**
- 可以被**合并（Declaration Merging）**
- 可以被**扩展（extends）**
- 可以被**实现（implements）**

**`type`（类型别名）**：
- 可以定义**任何类型**（对象、联合、交叉、元组等）
- **不能被合并**
- 可以使用**联合类型（Union）**和**交叉类型（Intersection）**

#### 3.2 代码示例对比

**场景 1：定义对象类型**
```typescript
// interface 方式
interface User {
  name: string;
  age: number;
}

// type 方式
type User = {
  name: string;
  age: number;
}
// 这两种方式在定义对象时几乎等价
```

**场景 2：声明合并（Declaration Merging）**
```typescript
// interface 可以被合并
interface User {
  name: string;
}
interface User {
  age: number;
}
// 最终 User 包含 name 和 age

// type 不能被合并
type User = {
  name: string;
}
type User = { // ❌ 报错！重复定义
  age: number;
}
```

**场景 3：扩展**
```typescript
// interface 使用 extends
interface Animal {
  name: string;
}
interface Dog extends Animal {
  breed: string;
}

// type 使用交叉类型
type Animal = {
  name: string;
}
type Dog = Animal & {
  breed: string;
}
```

**场景 4：联合类型和交叉类型**
```typescript
// type 可以轻松定义联合类型
type Status = 'pending' | 'success' | 'error';

// interface 不能直接定义联合类型
interface Status { // ❌ 不能这样定义
  'pending' | 'success' | 'error';
}

// type 可以定义复杂的交叉类型
type A = { a: string };
type B = { b: number };
type C = A & B; // { a: string; b: number }
```

**场景 5：元组类型**
```typescript
// type 可以定义元组
type Tuple = [string, number];

// interface 也可以，但语法更繁琐
interface Tuple extends Array<string | number> {
  0: string;
  1: number;
  length: 2;
}
```

#### 3.3 使用建议

**优先使用 `interface` 的场景**：
- 定义对象的公共 API（可以被扩展、实现）
- 需要声明合并（如扩展第三方库的类型）

**优先使用 `type` 的场景**：
- 定义联合类型、交叉类型
- 定义元组类型
- 需要复杂的类型操作（如 `keyof`、`infer` 等）

**面试表达**：
> "`interface` 主要用于定义对象结构，支持声明合并和扩展，更适合定义公共 API。`type` 更灵活，可以定义联合类型、交叉类型等复杂类型。我们团队约定：对象类型优先用 `interface`，复杂类型操作用 `type`。"

### 4. 泛型的高级约束

#### 4.1 泛型约束（Generic Constraints）

**基础约束**：限制泛型必须满足某些条件。

```typescript
// 约束 T 必须有 length 属性
function getLength<T extends { length: number }>(arg: T): number {
  return arg.length;
}

getLength('hello'); // ✅ string 有 length
getLength([1, 2, 3]); // ✅ array 有 length
getLength(123); // ❌ number 没有 length
```

#### 4.2 使用 `keyof` 约束

```typescript
// 约束 K 必须是 T 的键
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: 'Tom', age: 20 };
getProperty(user, 'name'); // ✅
getProperty(user, 'email'); // ❌ 'email' 不是 user 的键
```

#### 4.3 条件类型（Conditional Types）

```typescript
// 如果 T 是数组，返回数组元素类型；否则返回 T 本身
type Flatten<T> = T extends Array<infer U> ? U : T;

type Str = Flatten<string[]>; // string
type Num = Flatten<number>; // number
```

#### 4.4 多重约束

```typescript
// T 必须同时满足多个条件
function process<T extends string & { length: number }>(arg: T): void {
  // T 必须是 string 类型，且有 length 属性
}
```

## Day 9 - TypeScript 高级类型与体操（二）(3.13，周五)

> **大厂面试背景**：TypeScript 类型体操是高级前端的加分项，但实际面试中更多考察的是理解常用工具类型的实现原理，而不是手写复杂的类型体操。重点掌握 `infer` 的用法和常用工具类型的理解。

### 1. `infer` 的妙用：提取类型信息

`infer` 是 TypeScript 条件类型中的关键字，用于**在条件类型中推断类型**。它是理解 TypeScript 工具类型（如 `ReturnType`、`Parameters`）的基础。

#### 1.1 `infer` 的基本用法

**核心思想**：在条件类型中，用 `infer` 声明一个类型变量，TypeScript 会自动推断出这个类型。

```typescript
// 基础语法
type ExtractReturnType<T> = T extends (...args: any[]) => infer R ? R : never;

// 使用示例
type Func = () => string;
type Return = ExtractReturnType<Func>; // string
```

#### 1.2 提取函数返回值类型：`ReturnType`

**内置工具类型 `ReturnType` 的实现原理**：

```typescript
// TypeScript 内置的 ReturnType 实现
type ReturnType<T extends (...args: any) => any> = 
  T extends (...args: any) => infer R ? R : any;

// 使用示例
function getUser() {
  return { name: 'Tom', age: 20 };
}

type User = ReturnType<typeof getUser>; // { name: string; age: number }
```

**面试表达**：
> "`ReturnType` 利用条件类型和 `infer`，从函数类型中提取返回值类型。它的实现原理是：如果 `T` 是一个函数类型，就用 `infer R` 推断出返回值的类型 `R`，否则返回 `any`。"

#### 1.3 提取函数参数类型：`Parameters`

**内置工具类型 `Parameters` 的实现原理**：

```typescript
// TypeScript 内置的 Parameters 实现
type Parameters<T extends (...args: any) => any> = 
  T extends (...args: infer P) => any ? P : never;

// 使用示例
function createUser(name: string, age: number) {
  return { name, age };
}

type Params = Parameters<typeof createUser>; // [string, number]
```

**面试表达**：
> "`Parameters` 利用 `infer` 提取函数参数类型，返回一个元组类型。这在需要复用函数参数类型时非常有用。"

#### 1.4 提取 Promise 的泛型类型

```typescript
// 提取 Promise 的泛型类型
type UnwrapPromise<T> = T extends Promise<infer U> ? U : T;

type Str = UnwrapPromise<Promise<string>>; // string
type Num = UnwrapPromise<number>; // number
```

---

### 2. 常用工具类型的理解（不需要手写）

实际面试中，面试官更多考察的是**理解这些工具类型的实现思路**，而不是手写复杂的类型体操。

#### 2.1 `Partial<T>`：所有属性变为可选

**实现思路**：
```typescript
type Partial<T> = {
  [P in keyof T]?: T[P];
};

// 使用示例
interface User {
  name: string;
  age: number;
}

type PartialUser = Partial<User>; // { name?: string; age?: number }
```

**理解要点**：使用 `keyof` 遍历所有属性，给每个属性加上 `?` 可选标记。

#### 2.2 `Required<T>`：所有属性变为必填

**实现思路**：
```typescript
type Required<T> = {
  [P in keyof T]-?: T[P];
};

// 使用示例
interface User {
  name?: string;
  age?: number;
}

type RequiredUser = Required<User>; // { name: string; age: number }
```

**理解要点**：使用 `-?` 移除可选标记，使所有属性变为必填。

#### 2.3 `Pick<T, K>`：选择部分属性

**实现思路**：
```typescript
type Pick<T, K extends keyof T> = {
  [P in K]: T[P];
};

// 使用示例
interface User {
  name: string;
  age: number;
  email: string;
}

type UserBasic = Pick<User, 'name' | 'age'>; // { name: string; age: number }
```

**理解要点**：使用 `K extends keyof T` 约束，只选择 `K` 中的属性。

#### 2.4 `Omit<T, K>`：排除部分属性

**实现思路**：
```typescript
type Omit<T, K extends keyof T> = Pick<T, Exclude<keyof T, K>>;

// 使用示例
interface User {
  name: string;
  age: number;
  email: string;
}

type UserWithoutEmail = Omit<User, 'email'>; // { name: string; age: number }
```

**理解要点**：使用 `Exclude` 排除 `K`，然后用 `Pick` 选择剩余属性。

#### 2.5 `DeepPartial<T>`：深度可选（理解思路即可）

**实现思路**（递归处理）：
```typescript
type DeepPartial<T> = {
  [P in keyof T]?: T[P] extends object ? DeepPartial<T[P]> : T[P];
};

// 使用示例
interface User {
  name: string;
  address: {
    city: string;
    street: string;
  };
}

type PartialUser = DeepPartial<User>;
// {
//   name?: string;
//   address?: {
//     city?: string;
//     street?: string;
//   };
// }
```

**理解要点**：
- 递归处理嵌套对象
- 如果属性是对象类型，递归调用 `DeepPartial`
- 否则直接使用原类型

**面试表达**：
> "`DeepPartial` 的核心思路是递归：如果属性是对象类型，就递归处理；否则直接使用原类型。实际项目中，我们更多使用现成的工具类型，而不是手写复杂的类型体操。"

## Day 10 - V8 引擎与 JS 高级异步 (3.14，周六，5h)

> **今日策略**：深入理解 V8 引擎的垃圾回收机制和事件循环的底层原理，这是理解 JavaScript 性能优化的基础。同时手写带并发数量限制的异步调度器，这是字节等大厂的高频手写题。

### 1. V8 引擎核心：垃圾回收算法

#### 1.1 为什么需要垃圾回收？

**问题**：JavaScript 是自动内存管理的语言，不需要手动释放内存。但如果不及时回收不再使用的内存，会导致内存泄漏，最终导致程序崩溃。

**垃圾回收（Garbage Collection）的作用**：
- 自动识别不再使用的内存
- 自动释放这些内存
- 让程序可以持续运行

#### 1.2 V8 的内存分区

**V8 把内存分成两个区域**：

1. **新生代（New Space）**：
   - 存放新创建的对象
   - 空间小（通常 1-8MB）
   - 回收频繁，速度快

2. **老生代（Old Space）**：
   - 存放存活时间长的对象
   - 空间大（通常几十到几百 MB）
   - 回收频率低，但耗时较长

#### 1.3 新生代垃圾回收：Scavenge 算法

**核心思想**：把新生代分成两个区域（From Space 和 To Space），每次只使用一个。

**工作流程**：

```
1. 新对象分配在 From Space
2. 当 From Space 快满时，触发垃圾回收
3. 把存活的对象复制到 To Space
4. 清空 From Space
5. 交换 From Space 和 To Space
```

**关键点**：
- **复制算法**：只复制存活的对象，死对象直接丢弃
- **速度快**：因为新生代空间小，复制很快
- **空间利用率低**：需要两倍空间（From + To）

**对象晋升**：
- 如果对象在新生代经过多次回收仍然存活，会被晋升到老生代
- 通常经过 2 次回收仍然存活的对象会被晋升

#### 1.4 老生代垃圾回收：标记清除（Mark-Sweep）与标记整理（Mark-Compact）

**标记清除（Mark-Sweep）**：

**工作流程**：
```
1. 标记阶段：从根对象（全局变量、调用栈）开始，标记所有可达对象
2. 清除阶段：遍历整个堆，清除所有未标记的对象
```

**优点**：
- 不需要移动对象
- 速度快

**缺点**：
- 会产生内存碎片
- 碎片多了会导致无法分配大对象

**标记整理（Mark-Compact）**：

**工作流程**：
```
1. 标记阶段：标记所有可达对象（同 Mark-Sweep）
2. 整理阶段：把所有存活对象移动到一端，清除边界外的内存
```

**优点**：
- 不会产生内存碎片
- 内存利用率高

**缺点**：
- 需要移动对象，速度较慢

**V8 的策略**：
- 优先使用 Mark-Sweep（速度快）
- 当内存碎片过多时，使用 Mark-Compact（整理碎片）

#### 1.5 增量标记（Incremental Marking）解决了什么痛点？

**问题**：老生代垃圾回收会**阻塞主线程**（Stop-The-World）。

**场景**：
```
[0ms] 开始垃圾回收（Mark-Sweep）
[100ms] 还在标记...
[200ms] 还在标记...
[300ms] 标记完成，开始清除
[350ms] 垃圾回收完成

这 350ms 内，主线程被完全占用
- 无法执行 JavaScript
- 无法渲染页面
- 用户感觉卡顿
```

**增量标记的解决方案**：

**核心思想**：把标记过程分成多个小步骤，每执行一小步就让出主线程。

**工作流程**：
```
[0ms] 开始标记（标记一部分）
[10ms] 让出主线程 → 执行 JavaScript
[20ms] 继续标记（标记一部分）
[30ms] 让出主线程 → 执行 JavaScript
...
[300ms] 标记完成
[350ms] 垃圾回收完成

总时间还是 350ms，但不会长时间阻塞主线程
```

**关键点**：
- 标记过程可以中断和恢复
- 每次只标记一小部分，然后让出主线程
- 让浏览器有机会执行 JavaScript 和渲染

**面试表达**：
> "增量标记把老生代垃圾回收的标记过程分成多个小步骤，每执行一小步就让出主线程，让浏览器有机会执行 JavaScript 和渲染。虽然总时间不变，但不会长时间阻塞主线程，解决了页面卡顿的问题。"

#### 1.6 并发标记（Concurrent Marking）

**进一步优化**：在**独立线程**中进行标记，完全不阻塞主线程。

**工作流程**：
```
主线程：
  [0ms] 执行 JavaScript
  [10ms] 执行 JavaScript
  [20ms] 执行 JavaScript

标记线程（独立线程）：
  [0ms] 开始标记
  [10ms] 继续标记
  [20ms] 继续标记
  [300ms] 标记完成

主线程：
  [300ms] 暂停执行，执行清除阶段（必须暂停，因为要修改堆）
  [350ms] 清除完成，继续执行 JavaScript
```

**关键点**：
- 标记在独立线程进行，不阻塞主线程
- 但清除阶段必须在主线程执行（因为要修改堆）

### 2. 事件循环进阶：Node.js vs Browser

#### 2.1 Browser 事件循环（回顾）

**执行顺序**：
```
1. 执行同步代码
2. 处理微任务队列（全部执行完）
3. 处理宏任务队列（执行一个）
4. 检查是否需要渲染（每 16.67ms）
5. 回到步骤 1
```

#### 2.2 Node.js 事件循环

**Node.js 事件循环分为 6 个阶段**：

```
┌───────────────────────────┐
│        timers             │ ← setTimeout、setInterval
├───────────────────────────┤
│     pending callbacks     │ ← 执行延迟的 I/O 回调
├───────────────────────────┤
│        idle, prepare      │ ← 内部使用
├───────────────────────────┤
│          poll             │ ← 获取新的 I/O 事件
├───────────────────────────┤
│        check              │ ← setImmediate 回调
├───────────────────────────┤
│    close callbacks        │ ← socket.on('close')
└───────────────────────────┘
```

**执行顺序**：
```
1. timers：执行到期的 setTimeout、setInterval 回调
2. pending callbacks：执行延迟的 I/O 回调
3. idle, prepare：内部使用
4. poll：获取新的 I/O 事件，执行 I/O 回调
5. check：执行 setImmediate 回调
6. close callbacks：执行 close 事件回调
7. 回到步骤 1
```

**关键点**：
- 每个阶段执行完毕后，会处理微任务队列
- 微任务包括：`process.nextTick`（优先级最高）、`Promise.then`

#### 2.3 Node.js vs Browser 的差异

**1. 宏任务队列不同**：

**Browser**：
- `setTimeout`、`setInterval`
- `I/O` 操作
- `UI 事件`

**Node.js**：
- `setTimeout`、`setInterval`（timers 阶段）
- `setImmediate`（check 阶段）
- `I/O` 操作（poll 阶段）

**2. 微任务执行时机不同**：

**Browser**：
- 每次事件循环只处理一次微任务队列
- 在宏任务之前执行

**Node.js**：
- 每个阶段执行完毕后，都会处理微任务队列
- `process.nextTick` 优先级最高（在每个阶段之间都会执行）

**3. 代码示例对比**：

```javascript
// Browser 环境
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// 输出：1, 4, 3, 2

// Node.js 环境
console.log('1');
setTimeout(() => console.log('2'), 0);
setImmediate(() => console.log('3'));
Promise.resolve().then(() => console.log('4'));
process.nextTick(() => console.log('5'));
console.log('6');
// 输出：1, 6, 5, 4, 2, 3
// process.nextTick 优先级最高
// Promise.then 在 setTimeout 之前
// setImmediate 在 setTimeout 之后（check 阶段在 timers 阶段之后）
```

#### 2.4 极端阻塞场景分析

**场景 1：同步代码阻塞**

```javascript

// 输出：1（等待 2 秒）2
```

### 3. 硬核手写：带并发数量限制的异步调度器（Scheduler）

这是字节等大厂的高频手写题。

#### 3.1 题目要求

**实现一个 Scheduler 类**：
- 可以添加异步任务
- 控制同时执行的任务数量（并发限制）
- 当有任务完成时，自动执行下一个任务

**使用示例**：

```javascript
const scheduler = new Scheduler(2); // 最多同时执行 2 个任务

const addTask = (time, order) => {
  scheduler.add(() => {
    return new Promise(resolve => {
      setTimeout(() => {
        console.log(order);
        resolve();
      }, time);
    });
  });
};

addTask(1000, '1');
addTask(500, '2');
addTask(300, '3');
addTask(400, '4');

// 输出：2, 3, 1, 4
// 解释：
// 1. 同时执行任务 1 和 2（并发限制为 2）
// 2. 任务 2 先完成（500ms），执行任务 3
// 3. 任务 3 完成（300ms），执行任务 4
// 4. 任务 1 完成（1000ms）
// 5. 任务 4 完成（400ms）
```

#### 3.2 实现思路

**核心思路**：
1. 维护一个任务队列
2. 维护一个正在执行的任务列表
3. 当有任务完成时，从队列中取出下一个任务执行

**代码实现**：

```javascript
class Scheduler {
  constructor(maxCount) {
    this.maxCount = maxCount; // 最大并发数
    this.runningCount = 0; // 正在执行的任务数
    this.queue = []; // 任务队列
  }

  add(task) {
    return new Promise((resolve, reject) => {
      // 包装任务，添加 resolve 和 reject
      this.queue.push({
        task,
        resolve,
        reject
      });
      
      // 尝试执行任务
      this.run();
    });
  }

  run() {
    // 如果正在执行的任务数达到上限，或者队列为空，直接返回
    if (this.runningCount >= this.maxCount || this.queue.length === 0) {
      return;
    }

    // 从队列中取出一个任务
    const { task, resolve, reject } = this.queue.shift();
    this.runningCount++;

    // 执行任务
    task()
      .then(resolve, reject)
      .finally(() => {
        this.runningCount--;
        // 任务完成后，尝试执行下一个任务
        this.run();
      });
  }
}
```

## Day 11 - 死磕 Promise 规范 (3.15，周日，5h)

> **今日策略**：Promise 是大厂面试的必考手写题。今天我们要完整实现一个符合 Promise A+ 规范的 Promise，这是理解异步编程的基础。

### 1. Promise A+ 规范的核心要求

#### 1.1 Promise 的三种状态

**Promise 有三种状态**：
1. **pending（等待）**：初始状态
2. **fulfilled（成功）**：操作成功完成
3. **rejected（失败）**：操作失败

**状态转换规则**：
- 只能从 `pending` → `fulfilled` 或 `pending` → `rejected`
- 状态一旦改变，就不能再改变

#### 1.2 Promise 的核心特性

**1. then 方法**：
- 返回一个新的 Promise
- 可以链式调用
- 支持成功和失败的回调

**2. 值穿透**：
- 如果 then 的回调不是函数，值会穿透到下一个 then

**3. 错误处理**：
- 如果 then 的回调抛出异常，会被下一个 catch 捕获

**4. 微任务**：
- then 的回调必须在微任务中执行

### 2. 完整手写 Promise A+ 规范

#### 2.1 基础结构

```javascript
class MyPromise {
  constructor(executor) {
    this.state = 'pending'; // 状态：pending、fulfilled、rejected
    this.value = undefined; // 成功时的值
    this.reason = undefined; // 失败时的原因
    this.onFulfilledCallbacks = []; // 成功回调队列
    this.onRejectedCallbacks = []; // 失败回调队列

    // 定义 resolve 和 reject 函数
    const resolve = (value) => {
      if (this.state === 'pending') {
        this.state = 'fulfilled';
        this.value = value;
        // 执行所有成功回调
        this.onFulfilledCallbacks.forEach(callback => callback());
      }
    };

    const reject = (reason) => {
      if (this.state === 'pending') {
        this.state = 'rejected';
        this.reason = reason;
        // 执行所有失败回调
        this.onRejectedCallbacks.forEach(callback => callback());
      }
    };

    // 执行 executor
    try {
      executor(resolve, reject);
    } catch (error) {
      reject(error);
    }
  }
}
```

#### 2.2 then 方法实现

```javascript
then(onFulfilled, onRejected) {
  // 值穿透：如果回调不是函数，使用默认函数
  onFulfilled = typeof onFulfilled === 'function' ? onFulfilled : value => value;
  onRejected = typeof onRejected === 'function' ? onRejected : reason => { throw reason; };

  // 返回新的 Promise
  const promise2 = new MyPromise((resolve, reject) => {
    if (this.state === 'fulfilled') {
      // 使用微任务执行回调
      queueMicrotask(() => {
        try {
          const x = onFulfilled(this.value);
          resolvePromise(promise2, x, resolve, reject);
        } catch (error) {
          reject(error);
        }
      });
    } else if (this.state === 'rejected') {
      queueMicrotask(() => {
        try {
          const x = onRejected(this.reason);
          resolvePromise(promise2, x, resolve, reject);
        } catch (error) {
          reject(error);
        }
      });
    } else {
      // pending 状态，把回调放入队列
      this.onFulfilledCallbacks.push(() => {
        queueMicrotask(() => {
          try {
            const x = onFulfilled(this.value);
            resolvePromise(promise2, x, resolve, reject);
          } catch (error) {
            reject(error);
          }
        });

        queueMicrotask(() => {
          try {
            const x = onRejected(this.reason);
            resolvePromise(promise2, x, resolve, reject);
          } catch (error) {
            reject(error);
          }
        });
      });
    }
  });

  return promise2;
}
```

#### 2.3 resolvePromise 函数（处理 then 返回值）

```javascript
function resolvePromise(promise2, x, resolve, reject) {
  // 如果 promise2 和 x 是同一个对象，循环引用，报错
  if (promise2 === x) {
    return reject(new TypeError('Chaining cycle detected for promise'));
  }

  // 如果 x 是 Promise，等待它完成
  if (x instanceof MyPromise) {
    x.then(resolve, reject);
    return;
  }

  // 如果 x 是对象或函数，可能是 thenable
  if (x !== null && (typeof x === 'object' || typeof x === 'function')) {
    let called = false; // 防止多次调用

    try {
      const then = x.then;
      
      if (typeof then === 'function') {
        // x 是 thenable，调用它的 then 方法
        then.call(
          x,
          (y) => {
            if (called) return;
            called = true;
            resolvePromise(promise2, y, resolve, reject);
          },
          (r) => {
            if (called) return;
            called = true;
            reject(r);
          }
        );
      } else {
        // x 是普通对象，直接 resolve
        resolve(x);
      }
    } catch (error) {
      if (called) return;
      called = true;
      reject(error);
    }
  } else {
    // x 是基本类型，直接 resolve
    resolve(x);
  }
}
```

```javascript
            reject(r);
          }
        );
      } else {
        resolve(x);
      }
    } catch (error) {
      if (called) return;
      called = true;
      reject(error);
    }
  } else {
    resolve(x);
  }
}
```

### 3. Promise 静态方法手写

#### 3.1 Promise.resolve

```javascript
static resolve(value) {
  // 如果 value 是 Promise，直接返回
  if (value instanceof MyPromise) {
    return value;
  }
  
  // 否则返回一个 fulfilled 状态的 Promise
  return new MyPromise(resolve => {
    resolve(value);
  });
}
```

#### 3.2 Promise.reject

```javascript
static reject(reason) {
  return new MyPromise((resolve, reject) => {
    reject(reason);
  });
}
```

#### 3.3 Promise.all

**核心要求**：
- 接收一个 Promise 数组
- 所有 Promise 都成功时，返回所有结果的数组
- 如果有一个失败，立即返回失败的原因

**实现**：

```javascript
static all(promises) {
  return new MyPromise((resolve, reject) => {
    if (!Array.isArray(promises)) {
      return reject(new TypeError('Argument must be an array'));
    }

    if (promises.length === 0) {
      return resolve([]);
    }

    const results = [];
    let completedCount = 0;

    promises.forEach((promise, index) => {
      // 处理非 Promise 值
      MyPromise.resolve(promise).then(
        (value) => {
          results[index] = value;
          completedCount++;
          
          // 所有 Promise 都完成
          if (completedCount === promises.length) {
            resolve(results);
          }
        },
        (reason) => {
          // 有一个失败，立即 reject
          reject(reason);
        }
      );
    });
  });
}
```

#### 3.4 Promise.race

**核心要求**：
- 接收一个 Promise 数组
- 返回第一个完成（成功或失败）的 Promise 的结果

**实现**：

```javascript
static race(promises) {
  return new MyPromise((resolve, reject) => {
    if (!Array.isArray(promises)) {
      return reject(new TypeError('Argument must be an array'));
    }

    promises.forEach(promise => {
      MyPromise.resolve(promise).then(resolve, reject);
    });
  });
}
```

#### 3.5 Promise.allSettled

**核心要求**：
- 接收一个 Promise 数组
- 等待所有 Promise 完成（无论成功还是失败）
- 返回所有结果的数组，每个结果包含 `status` 和 `value`/`reason`

**实现**：

```javascript
static allSettled(promises) {
  return new MyPromise((resolve) => {
    if (!Array.isArray(promises)) {
      return reject(new TypeError('Argument must be an array'));
    }

    if (promises.length === 0) {
      return resolve([]);
    }

    const results = [];
    let completedCount = 0;

    promises.forEach((promise, index) => {
      MyPromise.resolve(promise).then(
        (value) => {
          results[index] = { status: 'fulfilled', value };
          completedCount++;
          if (completedCount === promises.length) {
            resolve(results);
          }
        },
        (reason) => {
          results[index] = { status: 'rejected', reason };
          completedCount++;
          if (completedCount === promises.length) {
            resolve(results);
          }
        }
      );
    });
  });
}
```

### 4. 异步任务超时中断控制

**需求**：实现一个函数，如果异步任务在指定时间内没有完成，就中断它。

**实现思路**：
- 使用 `Promise.race` 让原任务和超时任务竞争
- 如果超时任务先完成，就 reject

**代码实现**：

```javascript
function timeoutPromise(promise, timeout) {
  return MyPromise.race([
    promise,
    new MyPromise((resolve, reject) => {
      setTimeout(() => {
        reject(new Error('Timeout'));
      }, timeout);
    })
  ]);
}

// 使用示例
const fetchData = () => {
  return new Promise(resolve => {
    setTimeout(() => {
      resolve('数据');
    }, 2000);
  });
};

timeoutPromise(fetchData(), 1000)
  .then(data => console.log(data))
  .catch(error => console.error(error)); // 1 秒后输出：Error: Timeout
```

**更完善的实现（支持取消）**：

```javascript
function timeoutPromise(promise, timeout) {
  let timeoutId;
  
  const timeoutPromise = new MyPromise((resolve, reject) => {
    timeoutId = setTimeout(() => {
      reject(new Error('Timeout'));
    }, timeout);
  });

  return MyPromise.race([
    promise.finally(() => {
      // 如果原任务完成，清除定时器
      clearTimeout(timeoutId);
    }),
    timeoutPromise
  ]);
}
```
