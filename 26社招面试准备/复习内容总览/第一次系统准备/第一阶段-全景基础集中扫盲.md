## Day 1 - JS 核心、闭包与原型底层机制 (3.5)

### 1. 执行上下文与 `var`/`let`/`const` 的底层机制

要想真正弄懂 `var`、`let`、`const` 的区别，绝不能只停留在“是否变量提升”、“能不能修改”的表面，必须深入 V8 引擎的**执行上下文（Execution Context）**。

#### 1.1 什么是执行上下文？
当 JS 代码执行时，引擎会创建一个“执行上下文”。它分为两个阶段：**创建阶段** 和 **执行阶段**。
在创建阶段，上下文中会生成两个重要组件：
1. **变量环境（Variable Environment）**：专门用来存储 `var` 声明的变量和 `function` 声明的函数。
2. **词法环境（Lexical Environment）**：专门用来存储 `let`、`const` 声明的变量，它采用栈结构来支持块级作用域。

#### 1.2 变量提升与暂时性死区（TDZ）的本质
- **`var` 的机制**：在代码执行前（创建阶段），引擎扫描到 `var` 声明，会直接在**变量环境**中给它分配内存，并初始化为 `undefined`。所以你在声明前打印它，不会报错，只会得到 `undefined`。这就是**变量提升**。
- **`let`/`const` 的机制**：引擎扫描到 `let/const` 时，也会在**词法环境**中给它们分配内存，但是**绝不进行初始化**。如果你在这个时候去访问它，引擎会发现它处于“未初始化”状态，直接抛出 `ReferenceError` 错误。
- **暂时性死区（TDZ）**：从进入当前块级作用域，到 `let/const` 变量声明被实际执行到的这段时间内，你都无法访问这个变量，这块区域就在物理和时间上构成了“暂时性死区”。

#### 1.3 `const` 的本质
`const` 保证的并不是变量的值不能改动，而是**变量指向的那个内存地址（引用）不能改动**。如果是基本类型，值就保存在那个地址里；如果是引用类型（对象/数组），地址里存的是个指针，只要指针没变，往对象里加减属性是完全允许的。

### 2. 闭包的本质与垃圾回收的羁绊

#### 2.1 闭包底层的诞生过程
我们在教科书上常看“函数嵌套函数就是闭包”，但这非常不准确。大厂要求你从**词法作用域（Lexical Scope）**角度解释：

1. 每个函数在创建时，它的内部会有一个隐藏属性 `[[Environment]]`，这个属性**保存了它被创建时的那个词法环境的引用**。
2. 正常情况下，一个函数执行完毕，它的执行上下文会被主线程的调用栈（Call Stack）弹出，里面定义的局部变量理应被垃圾回收（GC）销毁。
3. **但是！** 如果这个函数内部返回了一个内部函数，且这个内部函数引用了外部函数的变量。那么，内部函数的 `[[Environment]]` 指针就会死死拽住外部函数的词法环境。
4. **结果：** 外部函数虽然执行完了、上下文被弹栈了，但它的**词法环境对象却因为被内部函数引用着，依然存活在堆内存（Heap）中**。这就是闭包的底层物理表现。

#### 2.2 闭包导致内存泄漏的原因
V8 引擎的垃圾回收采用的是**“可达性分析（Reachability）”**算法。从根节点（如全局对象 Window）往下找，找不到的对象才会被回收。
因为闭包保留了对外部词法环境的引用，如果这个闭包函数（内部函数）本身被挂载到了全局变量、DOM 事件回调或定时器上，这就导致那条引用链一直存在，垃圾回收器就不敢去回收它，最终导致内存泄漏。
- **解法**：在不需要使用闭包时，手动将引用该闭包的变量置为 `null`，切断可达性链路。

### 3. 原型与原型链的终极本质

这是整个 JS 最具哲学思想的设计，也是大厂必考的基础。

#### 3.1 认清三个概念：`prototype`、`__proto__` 和 `constructor`
- **`prototype`（显式原型）**：**只有函数才有**这个属性（除箭头函数外）。它是一个对象，用来存放这个函数所有实例共享的属性和方法。
- **`__proto__`（隐式原型）**：**所有对象都有**这个属性（无论普通对象还是函数对象）。它指向创建该对象的构造函数的 `prototype`。
- **`constructor`**：存在于 `prototype` 对象中，指向这个函数本身。

#### 3.2 原型链的尽头在哪里？
当你访问对象 `obj.a` 时，如果在 `obj` 自己身上找不到，引擎就会顺着 `obj.__proto__` 去找，直到找到为止。这条链的终点是：
1. `Object.prototype.__proto__ === null`。**万物始于无，null 就是原型链的绝对终点。**
2. 那么函数本身的原型链呢？所有的函数（包括 `Object`、`Array` 等内置构造函数）其实都是由根构造函数 `Function` 创造出来的。所以：`Object.__proto__ === Function.prototype`。
3. 甚至 `Function` 本身也是函数：`Function.__proto__ === Function.prototype`。这构成了一个哲学闭环。

#### 3.3 继承的最优解：寄生组合式继承
早期有原型链继承（所有实例共享引用数据，一改全改）、构造函数继承（无法继承父类 prototype 上的方法）、组合继承（父类构造函数被执行了两次，浪费性能）。
**寄生组合式继承** 的核心：
只调用一次父类构造函数，并在子类原型上只放一个父类原型的副本。
```javascript
function Parent(name) {
  this.name = name;
}
Parent.prototype.say = function() { console.log(this.name); }

function Child(name, age) {
  Parent.call(this, name); // 继承实例属性
  this.age = age;
}

// 核心：创建一个空对象，它的原型指向 Parent.prototype
Child.prototype = Object.create(Parent.prototype); 
Child.prototype.constructor = Child; // 修复 constructor 指向
```

### 4. 彻底打通数据类型判断底层

#### 4.1 为什么 `typeof null` 会输出 `"object"`？
这其实是 JavaScript 第一版遗留下来的一个底层历史 Bug。
在 JS 初代底层实现中，数据在底层都是以 32 位机器码表示的，其中低位的 1-3 位用来表示类型信息。`000` 开头代表是一个对象。
而 `null` 在机器码里面全是 0。所以引擎直接把 `null` 当成了以 `000` 开头的对象来处理，返回了 `"object"`。官方后来为了兼容海量老代码，就一直没有修复这个 Bug。

#### 4.2 `instanceof` 的底层逻辑
`A instanceof B`，它的核心逻辑非常简单：**顺着 A 的隐式原型链 `__proto__` 一直往上找，看看能不能找到 B 的显式原型 `prototype`**。
- **缺陷**：它无法跨 iframe 或跨窗口工作（因为不同的全局执行环境有各自独立的 Array/Object 构造函数），且可以被手动修改原型的代码欺骗。

#### 4.3 终极判别法：`Object.prototype.toString.call()`
这是最靠谱的类型判断方案。
- **底层原理**：在 JS 规范中，所有内置对象都有一个内部属性 `[[Class]]`。当我们调用 `Object.prototype.toString()` 时，它会读取这个内部的 `[[Class]]` 属性，并返回一个字符串格式：`"[object Type]"`。
- **为什么必须加 `.call()`？**：因为如果不加 `call`，直接调用 `arr.toString()`，会调用数组重写后的 `toString` 方法（把数组转成逗号分隔的字符串）。使用 `call` 强行让 `Object` 原型上的 `toString` 方法在我们要判断的变量上下文中执行，从而暴露出真实的内部 `[[Class]]` 类型。

## Day 2 - JS 进阶、this与网络跨域基础 (3.6)

### 1. `this` 指向的终极心法：看“谁”在“哪”调用了它

在 JavaScript 里，`this` 就像个墙头草。要判断 `this` 是谁，不要看函数在哪里定义的，**只看函数在执行的那一刻，是被谁、用什么方式调用的**。

大厂面试必考的四大绑定规则（按优先级从低到高排列）：

#### 规则一：默认绑定（最底层、优先级最低）
**场景：** 孤零零地调用一个普通函数，没有任何前缀。
```javascript
function foo() { console.log(this); }
foo(); 
```
**结果：** 在非严格模式下，指向 `window`（浏览器）或 `global`（Node.js）；在严格模式下（`"use strict"`），指向 `undefined`。

#### 规则二：隐式绑定（最常见）
**场景：** 函数作为某个对象的方法被调用。谁点出来的，`this` 就是谁。
```javascript
const obj = {
    name: 'Tom',
    say: function() { console.log(this.name); }
};
obj.say(); // this 是 obj
```
**💥 致命陷阱（隐式丢失）：**
如果你把对象里的方法**赋值给了一个变量再调用**，它就失去了宿主，退化成了“默认绑定”！
```javascript
const fn = obj.say; // 把函数抠出来
fn(); // 这里其实就是 window.fn()，this 丢失了，变成 window！
```
这也就是为什么在 React 类组件中，传递 `onClick={this.handleClick}` 经常会报错 `this is undefined` 的根本原因。

#### 规则三：显式绑定（魔法绑定）
**场景：** 就是我们昨天学的 `call`、`apply`、`bind`。你用这三个大招，指着谁的鼻子，`this` 就是谁。
```javascript
function foo() {}
const obj = {};
foo.call(obj); // this 强制变成 obj
```

#### 规则四：`new` 绑定（优先级最高）
**场景：** 当函数前加了 `new` 关键字。
```javascript
function Foo() { this.a = 1; }
let f = new Foo(); // this 指向 new 出来的那个全新空对象
```

### 2. 箭头函数的 `this`（特立独行的存在）

箭头函数根本不参与上面这四场“选妃”游戏！
**箭头函数在底层设计时，根本就没有属于自己的 `this` 和 `arguments`。**

既然自己没有，它怎么办？
**它就像一个普通的变量一样，顺着“词法环境”往外层的执行上下文里找 `this`！**
也就是说，它在被**定义**的那一刻，周围的 `this` 是谁，它的 `this` 永远就是谁，谁也改变不了（连 `call` 和 `new` 都改不了它）！

### 3. 网络状态码的深度拷问

在深究具体状态码之前，必须先建立对 HTTP 状态码的**总括性上帝视角**（五大门派）：
- **1xx (信息类)**：服务器收到了请求，正在处理，请客户端继续等。（日常开发极少遇到，如 101 切换 WebSocket 协议）。
- **2xx (成功类)**：请求被成功接收、理解并处理。
  - 代表：`200 OK`（正常成功）、`204 No Content`（无内容返回，常见于 OPTIONS 预检请求）、`206 Partial Content`（分块下载，比如视频拖拽进度条）。
- **3xx (重定向/缓存类)**：需要客户端采取进一步的操作才能完成请求（通常是浏览器自动跳转或拿缓存）。
  - 代表：`301`（永久搬家）、`302`（临时出去）、`304`（拿本地缓存）。
- **4xx (客户端错误)**：你（前端/用户）把请求发错了，服务器表示无法处理。背锅侠是前端。
  - 代表：`400 Bad Request`（参数传错了）、`401 Unauthorized`（没带 Token 或登录过期）、`403 Forbidden`（有 Token 但没权限）、`404 Not Found`（接口地址写错了或资源不存在）、`405 Method Not Allowed`（接口只允许 POST 你却发了 GET）。
- **5xx (服务端错误)**：服务器自己内部出 Bug 了，或者挂了。背锅侠是后端或运维。
  - 代表：`500 Internal Server Error`（后端代码抛异常了没兜住）、`502 Bad Gateway`（Nginx 代理层没联系上后面的 Node/Java 服务）、`503 Service Unavailable`（服务过载）、`504 Gateway Timeout`（网关超时，后端太慢了）。

有了这个“大门派”的概念，大厂面试官很少直接问定义，他们专挑那些长得很像、但底层逻辑不同的状态码来问：

#### 3.1 301（永久重定向） vs 302（临时重定向）
这两个都是告诉浏览器：“你要找的东西搬家了，你去新地址（Location 响应头）找吧。”
- **301（永久）**：极其霸道。浏览器一旦收到 301，就会在本地**死死记住**新地址。下次你再访问老地址，浏览器**连请求都不会发**，直接自己把你偷偷转到新地址去。这对 SEO 极其重要，搜索引擎会把老域名的权重全部转移给新域名。
- **302（临时）**：浏览器知道这只是暂时的，每次还是会老老实实地先去请求老地址，等服务器说“你去那边”，它再去那边。

#### 3.2 极其高频：关于缓存的 200 与 304

- **强制缓存（200 OK - from memory/disk cache）**：
  你发请求前，浏览器先看一眼本地缓存。发现没过期（靠 `Cache-Control: max-age` 决定），浏览器**根本就不发网络请求**，直接把本地的数据扔给你，状态码显示 200，旁边标着 (from cache)。速度快到飞起。

- **协商缓存（304 Not Modified）**：
  如果浏览器发现本地缓存过期了，或者服务器设置了 `Cache-Control: no-cache`，浏览器就会向服务器发请求。
  但它会很聪明地带上一个凭证：`If-None-Match` (上次文件的哈希值 ETag) 或者 `If-Modified-Since` (上次修改时间)。
  服务器拿到这个凭证一对比，发现：“哟，你手里的文件和我服务器上的完全一样啊，根本没改过！”
  此时，服务器为了省流量，**绝对不把巨大的文件体传给你**，它只给你回一个极其轻量级的状态码：**304**。
  意思是：“兄弟，文件没变，你继续用你本地那个过期缓存吧。”

这就是大厂面试官想听到的：**304 代表了一次真实的网络请求，但只传了报文头，没传报文体（Body）。**

### 4. 安全与跨域的底层对抗

前端安全防线与跨域限制，是浏览器为了保护用户隐私而设置的两道城墙。

#### 4.1 XSS（跨站脚本攻击）与 CSRF（跨站请求伪造）
- **XSS（盗号的刺客）**：
  - **原理**：黑客在你的评论区或输入框里，提交了一段 `<script>` 代码。如果后端没做过滤直接存到数据库，其他用户打开这个页面时，浏览器就会当成正常代码执行它！这段代码可以偷偷读取用户的 `document.cookie`，然后发送到黑客的服务器。
  - **防御绝杀**：除了对输入和输出做转义（Escape），最底层的防御是**在服务器设置 Cookie 时加上 `HttpOnly` 标志**。只要加上它，前端用任何 JS 代码（如 `document.cookie`）都绝对读不到这个 Cookie，直接废了黑客的武功！

- **CSRF（借刀杀人的骗子）**：
  - **原理**：你刚登录了银行网站，没关网页。黑客诱导你点开一个黄色网站，这个网站里隐藏了一个向银行发起的转账请求。因为你的浏览器还保存着银行的登录状态（Cookie），浏览器在发跨站请求时，会**自动并且强制地带上**银行的 Cookie！银行服务器一看 Cookie 是你的，就乖乖把钱转了。黑客全程不需要知道你的密码和 Cookie 是什么。
  - **防御绝杀**：
    1. **SameSite Cookie**：在设置 Cookie 时加上 `SameSite=Strict` 或 `Lax`。它告诉浏览器：“只要这个请求不是我自家网站发出的，绝对不允许带我的 Cookie 出门！”
    2. **Token 校验**：抛弃 Cookie 鉴权，改用 JWT Token 放在请求头（Headers）里手动发送。因为跨站请求无法读取和操作你的请求头。

#### 4.1.1 扩展防线：其他必须知道的攻击方式
大厂面试经常会问：“除了 XSS 和 CSRF，你还了解哪些前端安全问题？”这三点是最佳加分项：
- **点击劫持（Clickjacking）**：黑客用不可见的 `iframe` 覆盖在诱饵按钮上，骗你点击其实是点了他的转账按钮。防御手段是后端设置 `X-Frame-Options: DENY`（禁止被 iframe 嵌套）。
- **CDN 劫持 / 供应链投毒**：引入的第三方免费 CDN 上的 JS 被黑客篡改，注入了挖矿或盗号代码。防御手段是在 `<script>` 标签加入 **SRI（Subresource Integrity）** 的 `integrity` 哈希校验属性。
- **中间人攻击（MITM）**：在不安全的免费 Wi-Fi 下，请求被拦截篡改。防御绝杀是强制全站 **HTTPS**，并配置 `HSTS` 头。

#### 4.2 CORS 跨域与神秘的 OPTIONS 预检请求
当我们在前后端分离的项目中（比如前端在 localhost:3000，后端在 localhost:8080），直接发请求会被浏览器的"同源策略"拦截。这就是跨域。

**CORS 全称**：**Cross-Origin Resource Sharing**（跨源资源共享）
为了合法跨域，后端会在响应头里加上 `Access-Control-Allow-Origin: *`，这就是 CORS。
**CORS 的核心机制**：
1. **服务器确实可以给不同域名的前端返回数据**，但关键是服务器必须在响应头中明确声明允许。
2. **浏览器的检查流程**：
   - 前端（比如 `localhost:3000`）向不同域名的后端（比如 `localhost:8080`）发请求
   - 后端服务器处理请求，返回数据，**同时在响应头里加上** `Access-Control-Allow-Origin: http://localhost:3000`（或者 `*` 表示允许所有域名）
   - 浏览器收到响应后，会**先检查响应头**：如果发现 `Access-Control-Allow-Origin` 的值匹配前端域名（或为 `*`），浏览器才会把响应数据交给前端
   - 如果服务器没有设置这个响应头，或者域名不匹配，**即使服务器已经返回了数据，浏览器也会拦截**，前端在 Network 面板能看到响应，但代码里拿不到数据，会报 CORS 错误

**简单记忆**：合法跨域 = 服务器主动在响应头里说“我允许”，浏览器检查通过后才放行数据给前端。
但大厂面试必问：**你发请求的时候，有没有在 Network 面板里看到过一个奇怪的 `OPTIONS` 请求？它是个什么鬼？**

- **简单请求 vs 复杂请求**：
  如果你发的是普通的 GET/POST，且 Header 里只有普通的字段，浏览器会直接发走，这叫"简单请求"。
  **但是！** 如果你用了 `PUT/DELETE`，或者你在 Header 里塞了自定义的字段（比如 `Authorization: Bearer <token>`），或者把**请求头（Request Headers）**中的 `Content-Type` 设为了 `application/json`，这就变成了**"复杂请求"**。

**⚠️ 关键澄清：请求的 Content-Type vs 响应的 Content-Type**
- **响应的 Content-Type**：服务器返回的数据格式（比如 `application/json`、`text/html`）。这个**不影响**简单/复杂请求的判断！
- **请求的 Content-Type**：你**发送给服务器**的数据格式。这个**会影响**简单/复杂请求的判断！

**为什么 `Content-Type: application/json` 会让请求变复杂？**

**简单请求的默认 Content-Type**：
- 当你用 `<form>` 表单提交，或者用 `fetch` 发送 `FormData` 时，浏览器默认会把请求头设置为 `Content-Type: application/x-www-form-urlencoded`（或者 `multipart/form-data`）
- 这是浏览器**原生支持**的格式，所以被认为是"简单请求"

**复杂请求的场景**：
- 当你用 `fetch` 或 `axios` 发送 JSON 数据时，你需要**手动设置**请求头：`Content-Type: application/json`
- 浏览器认为："这不是我原生的格式，可能是自定义的，我得先问问服务器同不同意！"
- 所以会触发 OPTIONS 预检请求

**代码示例对比**：
```javascript
// ✅ 简单请求：浏览器默认的 Content-Type
fetch('http://api.example.com/data', {
  method: 'POST',
  body: new FormData(), // 浏览器自动设置 Content-Type: multipart/form-data
  // 不会触发 OPTIONS 预检
});

// ❌ 复杂请求：手动设置 Content-Type: application/json
fetch('http://api.example.com/data', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json' // 手动设置，触发 OPTIONS 预检
  },
  body: JSON.stringify({ name: 'Tom' })
});
```

- **OPTIONS 预检（Preflight）的底层逻辑**：
  对于复杂请求，浏览器会非常谨慎：“这请求可能会对服务器造成破坏，我得先去探探路！”
  于是，浏览器会**自动**在你的真实请求之前，偷偷发一个方法为 `OPTIONS` 的请求去服务器。
  - 浏览器问：“服务器大哥，我要用 POST 方法跨域请求你，而且还带了自定义的 Token 请求头，你允许吗？”
  - 服务器如果配置正确，就会回复 200，并在响应头里带上：`Access-Control-Allow-Methods: POST` 和 `Access-Control-Allow-Headers: Authorization`。
  - 浏览器收到许可令：“好的！大哥同意了！” 这时，它才会把你的**真实业务请求**发出去。

如果你在开发时发现请求发送慢，或者被莫名其妙的 CORS 跨域报错拦住，大概率就是你的后端**没有处理好这个 OPTIONS 预检请求**！

### 1. React 核心基础扫盲

#### 1.1 JSX 编译的本质是什么？
面试官如果问：“浏览器认识 JSX 吗？”
你要回答：“完全不认识。JSX 只是 React 提供的一个**语法糖**。在构建阶段，Babel 会把我们的 HTML 标签一样的 JSX，编译成普通的 JS 函数调用。
- 在 React 17 之前，它会被编译成 `React.createElement('div', { className: 'app' }, 'Hello')`。这也是为什么以前即使组件里没用到 React，也必须在文件开头写 `import React from 'react'` 的原因。
- 在 React 17 之后，引入了全新的 JSX 转换（`jsx-runtime`），Babel 会自动引入一个特殊的 `_jsx()` 函数来执行转换，我们再也不用手动 import React 了。”

#### 1.2 类组件生命周期 vs Hooks 的心智模型差异
- **类组件（面向生命周期编程）**：你是在考虑“组件挂载时（`componentDidMount`）干什么”、“组件更新时（`componentDidUpdate`）干什么”。逻辑是被强行拆分在不同的生命周期钩子里的。
- **Hooks（面向状态同步编程）**：`useEffect` 不是生命周期的平替！它的设计哲学是“**状态同步**”。你不需要关心现在是 Mount 还是 Update，你只需要告诉 React：“当 `[依赖数组]` 里的变量发生变化时，请你帮我执行这行代码，把外部世界（比如真实 DOM、网络请求、定时器）与当前的状态**同步**起来。”

#### 1.3 合成事件（SyntheticEvent）与原生事件
我们在 React 里写的 `onClick` 并不是真正绑定在 DOM 元素上的。
- **底层机制**：React 为了抹平不同浏览器的兼容性差异，并且为了极致的性能，它实现了一套自己的事件系统（事件委托）。在 React 17 之前，它把所有事件都委托到了 `document` 上；在 React 17 之后，为了微前端的兼容，改为委托到**挂载 React 树的那个根容器（`rootNode`）**上。
- **注意点**：React 传给你的 `e` 是它自己包装的 `SyntheticEvent`，如果你想拿到原生事件，必须调用 `e.nativeEvent`。

### 2. CSS 核心扫盲（最容易忘的八股文）

#### 2.1 盒模型（Box Model）的致命区别
- **标准盒模型（`box-sizing: content-box`，默认）**：你设置的 `width` 和 `height`，**仅仅只是内容（content）的宽高**！如果你再加 
`padding` 和 `border`，这个盒子的实际占地面积会**膨胀**！这经常导致布局被撑破。
- **IE 盒模型（`box-sizing: border-box`，现代推荐）**：你设置的 `width` 就是这个盒子的**最终占地面积**。你往里加 `padding` 和 
`border`，它会向内挤压内容区，但**总宽高绝不变**！

**盒模型的四个组成部分（从内到外）**：
1. **Content（内容区）**：实际显示文本、图片的区域
2. **Padding（内边距）**：内容区与边框之间的空白区域
3. **Border（边框）**：围绕内边距的线条
4. **Margin（外边距）**：元素与其他元素之间的空白区域（**不计算在元素的总宽高内**）

**标准盒模型（`box-sizing: content-box`，默认）**：
- 你设置的 `width` 和 `height`，**仅仅只是内容（content）的宽高**！
- **计算公式**：
  - 元素总宽度 = `width` + `padding-left` + `padding-right` + `border-left` + `border-right` + `margin-left` + `margin-right`
  - 元素总高度 = `height` + `padding-top` + `padding-bottom` + `border-top` + `border-bottom` + `margin-top` + `margin-bottom`
- **致命问题**：如果你设置 `width: 100px; padding: 20px; border: 5px solid black;`，这个元素的实际宽度是 `100 + 20*2 + 5*2 = 150px`！这经常导致布局被撑破，特别是当你用百分比宽度时。

**IE 盒模型（`box-sizing: border-box`，现代推荐）**：
- 你设置的 `width` 就是这个盒子的**最终占地面积**（包含 content + padding + border）
- **计算公式**：
  - 元素总宽度 = `width`（已包含 padding 和 border）+ `margin-left` + `margin-right`
  - 元素总高度 = `height`（已包含 padding 和 border）+ `margin-top` + `margin-bottom`
- **优势**：如果你设置 `width: 100px; padding: 20px; border: 5px solid black;`，这个元素的实际宽度**就是 100px**！`padding` 和 `border` 会向内挤压内容区，但总宽高绝不变。这就是为什么现代 CSS Reset 都会写 `* { box-sizing: border-box; }`。

**代码示例对比**：
```css
/* 标准盒模型（content-box） */
.box1 {
  width: 200px;
  padding: 20px;
  border: 5px solid black;
  /* 实际宽度 = 200 + 20*2 + 5*2 = 250px */
}

/* IE 盒模型（border-box） */
.box2 {
  box-sizing: border-box;
  width: 200px;
  padding: 20px;
  border: 5px solid black;
  /* 实际宽度 = 200px（内容区被压缩为 200 - 20*2 - 5*2 = 150px） */
}
```

#### 2.1.1 Margin 合并（Margin Collapse）的底层机制

**什么是 Margin 合并？**
当两个**垂直相邻**的块级元素的 margin 相遇时，它们会**合并成一个 margin**，取两者中的较大值。

**触发条件**：
1. **必须是垂直方向**：只有 `margin-top` 和 `margin-bottom` 会合并，`margin-left` 和 `margin-right` 不会合并
2. **必须是块级元素**：`display: block` 或 `display: list-item`
3. **必须是相邻**：中间没有 `padding`、`border`、`inline` 元素等阻隔

**经典场景**：
```css
/* 场景 1：兄弟元素合并 */
.div1 {
  margin-bottom: 20px;
}
.div2 {
  margin-top: 30px;
}
/* 结果：两个 div 之间的间距是 30px（取较大值），而不是 50px！ */

/* 场景 2：父子元素合并 */
.parent {
  margin-top: 20px;
}
.child {
  margin-top: 30px;
}
/* 结果：父元素的 margin-top 被"吞掉"，实际 margin-top 是 30px（取较大值）！ */
```

**如何避免 Margin 合并？**
1. 给父元素加 `padding` 或 `border`（阻隔父子合并）
2. 给父元素触发 BFC（`overflow: hidden`、`display: flex` 等）
3. 使用 `padding` 代替 `margin`（如果场景允许）

#### 2.1.2 负 Margin 的妙用（面试加分项）

**负 Margin 的行为**：
- **负 margin-top/margin-left**：元素会**向上/向左移动**，可能覆盖其他元素
- **负 margin-bottom/margin-right**：元素本身位置不变，但会**缩小元素占据的空间**，后面的元素会"挤上来"

**经典应用场景**：
```css
/* 场景 1：圣杯布局（中间自适应，左右固定宽度） */
.container {
  padding: 0 200px; /* 为左右栏留出空间 */
}
.main {
  width: 100%;
  float: left;
}
.left {
  width: 200px;
  float: left;
  margin-left: -100%; /* 移动到最左边 */
  position: relative;
  left: -200px; /* 再向左移动自身宽度 */
}
.right {
  width: 200px;
  float: left;
  margin-left: -200px; /* 移动到最右边 */
  position: relative;
  right: -200px; /* 再向右移动自身宽度 */
}

/* 场景 2：垂直居中（配合绝对定位） */
.center {
  position: absolute;
  top: 50%;
  left: 50%;
  margin-top: -50px; /* 元素高度的一半 */
  margin-left: -50px; /* 元素宽度的一半 */
  width: 100px;
  height: 100px;
}
```

#### 2.1.3 盒模型的实际应用与常见坑点

**坑点 1：百分比宽度的计算基准**
- `width: 50%` 的基准是**父元素的 content 宽度**（标准盒模型）或**父元素的总宽度**（border-box）
- `padding: 10%` 的基准是**父元素的宽度**（无论水平还是垂直方向！）

**坑点 2：`min-width` 和 `max-width` 的优先级**
- `min-width` > `width` > `max-width`
- 即使设置了 `width: 100px`，如果 `min-width: 200px`，元素宽度仍然是 200px

**坑点 3：`box-sizing` 的继承问题**
- `box-sizing` **不会继承**！如果父元素设置了 `border-box`，子元素默认仍然是 `content-box`
- 现代最佳实践：在 CSS Reset 中全局设置 `* { box-sizing: border-box; }`

**面试表达**：
> "盒模型是 CSS 布局的基础。标准盒模型的问题是 `width` 只包含内容，加上 `padding` 和 `border` 后实际宽度会膨胀，导致布局被撑破。现代开发都用 `border-box`，让 `width` 包含 `padding` 和 `border`，布局更可控。另外，垂直方向的 `margin` 会合并，这是 CSS 规范的设计，可以通过触发 BFC 或使用 `padding` 来避免。"

#### 2.2 BFC（块级格式化上下文）到底是个啥？
**大白话翻译**：BFC 就是一个“**绝对封闭的隔离结界**”。
一旦某个元素触发了 BFC，它内部的子元素无论怎么翻江倒海（比如浮动 `float`，或者外边距合并 `margin collapse`），都**绝对不会影响到这个元素外面的布局**！

- **触发条件（背几个最常用的）**：
  1. `overflow` 不是 `visible`（比如 `hidden`、`auto`）
  2. `display` 是 `flex` 或 `grid`（这俩是自带结界的现代布局）
  3. `position` 是 `absolute` 或 `fixed`
- **经典应用**：解决父元素高度塌陷（子元素全 float 跑了，父元素没高度了，给父元素加 `overflow: hidden` 触发 BFC 即可包住子元素）、解决相邻元素的 margin 塌陷（重叠）。

#### 2.3 垂直水平居中的终极万能方案
不要去背那些乱七八糟的古老方案，大厂直接甩这两个最现代的：

**方案 A（最无脑，Flexbox）：**
```css
.parent {
  display: flex;
  justify-content: center; /* 水平 */
  align-items: center;     /* 垂直 */
}
```

**方案 B（未知宽高，绝对定位 + Transform）：**
```css
.parent { position: relative; }
.child {
  position: absolute;
  top: 50%;
  left: 50%;
  transform: translate(-50%, -50%); /* 往回走自己宽高的一半，核心！ */
}
```

### 3. 白板手写代码复健（大厂一面必考）

#### 3.1 终极版深拷贝（Deep Clone）
大厂绝不接受 `JSON.parse(JSON.stringify(obj))`，因为它会丢掉函数、`undefined`、正则，并且遇到循环引用（`obj.a = obj`）会直接爆栈死循环。

**满分基建代码（必须掌握）：**
```javascript
function deepClone(target, hash = new WeakMap()) {
    // 1. 如果是基本类型或 null，直接返回
    if (target === null || typeof target !== 'object') return target;
    
    // 2. 处理特殊对象：Date 和 RegExp
    if (target instanceof Date) return new Date(target);
    if (target instanceof RegExp) return new RegExp(target);
    
    // 3. 解决循环引用（核心大坑！）
    // 如果这个对象我之前已经拷贝过了，直接从 Hash 表里把拷贝好的成品拿出来返回，死循环破解！
    if (hash.has(target)) return hash.get(target);

    // 4. 创建新壳子（根据目标是数组还是对象来创建）
    // target.constructor 可以完美拿到它的老爸（Array 还是 Object）
    let cloneTarget = new target.constructor();
    
    // 把当前正在克隆的壳子记录到 Hash 表里
    hash.set(target, cloneTarget);

    // 5. 递归拷贝里面的每一层
    // Reflect.ownKeys 可以拿到包括 Symbol 在内的所有私有属性
    Reflect.ownKeys(target).forEach(key => {
        cloneTarget[key] = deepClone(target[key], hash);
    });

    return cloneTarget;
}
```
**亮点考问**：为什么要用 `WeakMap` 而不是 `Map`？
**满分回答**：因为 `WeakMap` 的键是“弱引用”。当被拷贝的原始对象在外部被销毁时，由于 `WeakMap` 不阻碍垃圾回收（可达性分析断裂），这个哈希表里的记录也会自动释放，不会造成内存泄漏。

#### 3.2 节流（Throttle）与防抖（Debounce）

这俩的本质都是限制高频触发的事件（如滚动、输入）。
- **防抖（Debounce）**：“技能读条被打断”。你一直按，它一直不放，直到你停手超过 N 秒，它才放出最后一次。
- **节流（Throttle）**：“技能冷却 CD”。不管你按多快，它只保证每隔 N 秒匀速放一次。

**手写防抖（支持首次立即执行）：**
```javascript
function debounce(fn, wait, immediate = false) {
    let timer = null;
    
    return function(...args) {
        // 如果有老定时器，掐死它（打断读条）
        if (timer) clearTimeout(timer);
        
        // 核心：如果是立即执行版，且当前没有定时器，立刻干活！
        if (immediate && !timer) {
            fn.apply(this, args); // 记得用 apply 绑定 this！
        }
        
        // 重新开始读条
        timer = setTimeout(() => {
            // 如果不是立即执行版，读条结束才干活
            if (!immediate) fn.apply(this, args);
            
            // 读条结束，冷却完毕
            timer = null; 
        }, wait);
    }
}
```

**手写节流（时间戳版，最直观）：**
```javascript
function throttle(fn, delay) {
    let lastTime = 0; // 记录上次放技能的时间
    
    return function(...args) {
        let now = Date.now();
        // 如果当前时间距离上次放技能，已经超过了 CD（delay）
        if (now - lastTime >= delay) {
            fn.apply(this, args); // 放技能！
            lastTime = now;       // 刷新放技能的时间
        }
    }
}
```
