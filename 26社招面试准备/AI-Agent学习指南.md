# 第一部分：一张图看懂全局

## 1.1 先破除一个误解

很多人以为"AI Agent"是某个很高深的新技术。其实它是**一层一层叠加**出来的，每一层都只解决上一层的一个缺陷。你只要理解"每一层补了什么短板"，整条链路就通了。

```
纯 LLM          →  会聊天，但没记忆、不知道你的私有信息、不能动手做事
  + 多轮对话     →  有了上下文记忆
  + Prompt 工程  →  能稳定地按你要的格式/角色输出
  + RAG          →  能基于"你的私有数据"回答，不瞎编
  + Tool Calling →  能调用外部能力（查数据库、发消息、算数……）真正"动手"
  + 循环控制      →  能自己规划多步、边做边调整 = Agent
```

## 1.2 一句话定义

- **LLM（大语言模型）**：一个"文字接龙"引擎。给它一段文字，它预测接下来最可能的文字。它本身**没有记忆、不能上网、不能执行任何操作**。
- **AI Agent（智能体）**：以 LLM 为"大脑"，外接了"记忆 + 知识 + 工具"，并且能**自主决定调用哪些工具、分几步完成一个目标**的系统。

> 关键区别：LLM 只会"说"，Agent 会"想 + 说 + 做"。让 LLM 会"做"的那个东西，就是 **Tool Calling（工具调用）**；让它"做得对"的那个东西，就是 **RAG（喂对知识）** 和 **规划循环**。

## 1.3 用你的项目类比

你要做的「AI 岗位匹配器」正好完整走过这几层：

| 层 | 匹配器里的体现 |
|----|---------------|
| LLM | 让模型读 JD 和简历，生成一段匹配分析 |
| Prompt 工程 | 要求它输出固定的 JSON（分项打分 + 亮点 + 总结） |
| RAG | 从你的博客/简历/项目故事里检索最相关的经历，作为打分依据 |
| Tool Calling | 根据匹配度自动调用"推送联系方式 / 婉拒话术"等操作 |
| 循环控制 | 先检索 → 再打分 → 再判断 → 再决定调哪个工具，串成一条链 |

# 第二部分：六个核心概念（稍深）

这是整份文档的主干。每个概念讲三件事：**是什么、为什么需要、面试深挖点**。

## 2.1 LLM API：一切的起点

### 是什么
你通过 HTTP 请求把文字发给模型服务商（OpenAI / DeepSeek / 通义等），拿回模型生成的文字。最常用的是 **Chat Completions** 接口。

> 注意：这里说的"HTTP 请求"是广义的协议大类。**真实调用一定走 HTTPS**（端点都是 `https://` 开头），因为请求要携带 API Key 和对话内容，必须加密传输，否则会被截获盗刷。

请求体的核心是一个 `messages` 数组，每条消息有 `role` 和 `content`：

```json
{
  "model": "deepseek-chat",
  "messages": [
    { "role": "system",    "content": "你是一个严谨的招聘匹配分析助手" },
    { "role": "user",      "content": "这是JD：……这是简历：……请打分" },
    { "role": "assistant", "content": "（模型上一轮的回复，多轮时才有）" }
  ],
  "temperature": 0.3,
  "stream": false
}
```

三种 role 要分清：
- **system**：设定角色和规则，整段对话只在开头设一次，权重最高。
- **user**：用户说的话。
- **assistant**：模型说过的话（多轮对话时把历史回复也塞回去，模型才有"记忆"）。

### 哪些字段是必须的？不写会怎样？
上面那个请求体不是每个字段都必填。分清楚：

| 字段 | 是否必须 | 不写会怎样 |
|------|---------|-----------|
| `model` | **必须** | 报错，得指定用哪个模型 |
| `messages` | **必须** | 报错，这是你要问的内容 |
| `system` 那条消息 | **可选** | 不报错，模型用它自带的"出厂默认人格"回答 |
| `temperature` | 可选 | 用默认值（通常 1） |
| `stream` | 可选 | 默认 `false`，一次性返回 |

所以最精简的合法请求可以只有一条 user 消息：
```json
{
  "model": "deepseek-chat",
  "messages": [ { "role": "user", "content": "你好" } ]
}
```

> 格式兼容性：`model` + `messages` 是 OpenAI 定的 Chat Completions 标准，**DeepSeek、通义、智谱等大多数国产模型都兼容**，学一套基本通用。少数厂商（Anthropic 原生接口、Gemini）字段名略有不同，但"role + content 的消息数组"这个核心思想一致。

### 那"身份/角色"到底是谁设的？
你平时用豆包、ChatGPT 时只打了一句话，并没有设 system，为什么模型还是有"人格"？因为**设身份发生在"应用层"，不是终端用户做的**。中间有三层：

```
① 模型厂商（训练时）
   给模型打的基础"性格"和安全规则（不说脏话、不教危险内容等）
   —— 模型自带的底子，改不了

② 应用/产品层（后端开发者）   ← 身份就是这一层设的
   ChatGPT 网页、豆包 App、你要做的匹配器……
   它们的后端在每次请求里，偷偷替你塞一条 system 消息
   （如"你是 XX 助手，回答简洁友好"），你在界面上看不到

③ 终端用户（你）
   你在输入框打的字 = user 消息
   你看不到、也不用管 system 那条
```

**对照你的场景：**
- 你在**豆包/ChatGPT 里聊天**：你只提供 user 内容，system 那条是厂商后端替你加的。
- 你以后做**AI 岗位匹配器**：**你就是"应用层"**。面试官只粘贴 JD（user 消息），而"你是一个严谨的招聘匹配分析助手，请对照简历打分并输出 JSON……"这条 **system 消息，是你在后端代码里写死、每次请求自动带上的**，面试官看不到，但它决定了模型行为。

一句话：**终端用户只给 user 内容；system（身份/规则）由做产品的一方在后端注入；再往下的基础性格是厂商训练时给的。** 你现在是用户所以感觉"没人设身份"；等你做匹配器，设身份的人就是你自己。

### 为什么关键
- **模型无状态**：它不会记得你上一句说过什么。所谓"记忆"完全靠你每次请求**把历史 messages 再传一遍**。这点是新手最容易懵的地方。
- **temperature**：0～2 的随机度。做匹配打分这种要稳定的场景用低值（0～0.3）；做创意文案用高值。
- **token**：模型按 token（约等于 0.5～1 个汉字 / 4 个英文字符）计费和计长度。输入 + 输出都算钱，也都有上限（上下文窗口）。

### 面试深挖点
- 「多轮对话的记忆怎么实现？」→ 靠客户端累积 messages 数组回传，模型本身无状态。
- 「上下文太长怎么办？」→ 裁剪历史、做摘要、或用 RAG 只取相关片段（引出 RAG）。
- 「怎么控制成本？」→ 控制历史长度、用更小的模型、缓存、限制 max_tokens。

## 2.2 多模态（Multimodal）：让模型不止能读文字

### 先厘清一个术语问题
- **LLM** 严格按字面是 Large Language Model = 大**语言**模型，最原始的定义**只处理文字**。
- 能同时读文字 + 图片（甚至音频、视频）的模型，业界叫 **LMM（Large Multimodal Model，大多模态模型）** 或"多模态大模型"。像 GPT-4o、Gemini、Claude、通义千问 VL 都是这类。
- 口头上大家常把它们也统称"LLM"，因为内核仍是从语言模型发展来的。**精确说：多模态模型是 LLM 的扩展。**

### "模态（Modality）"是什么
模态 = 信息的形式/类型。常见的有：

| 模态 | 例子 |
|------|------|
| 文本 | 打字、文档 |
| 图像 | 照片、截图、图表 
| 音频 | 语音、音乐 |
| 视频 | 视频流 |

"多模态"就是一个模型能**同时处理并关联**这些不同形式的信息。你给它一张报错截图 + 打字问"这是什么错"，它能把图里的界面/文字和你的问题结合起来分析——这就是多模态。

### 它怎么做到的（面试可能问）
关键机制：**不管什么模态，最后都被转成模型能理解的同一种"数字表示"（向量）**。
- 文字 → 分词后变成 token 向量
- 图片 → 经过**视觉编码器**（如 ViT，Vision Transformer）切块、编码成一串向量
- 不同模态的向量被映射到**同一个语义空间**，再一起喂给模型核心网络处理

打比方：图片和文字本是两种"语言"，模型先把它们都翻译成一种"内部通用语"（向量），之后处理就不分彼此了。

> 这和 2.5 RAG 里的 **embedding 是同源思想**——都是"把信息转成向量，在同一空间里比较/处理"。理解一个，另一个就通了。

### 和你项目的关系（已确定采用）
匹配器**正式支持面试官粘贴 JD 截图**（不止纯文字），直接用支持视觉的多模态模型解析，**不走 OCR 中转**。这样：
- 交互更顺：面试官从招聘网站直接截图丢进来即可
- 是实打实的加分项：面试时能讲"匹配器支持多模态输入，用视觉模型直接读 JD 截图"

具体模型选型见第四部分 4.3。

### 面试深挖点
- 「LLM 和多模态模型什么关系？」→ 多模态模型（LMM）是 LLM 的扩展，能处理文字之外的图/音/视频。
- 「多模态是怎么把图和文字一起理解的？」→ 各模态分别编码成向量，映射到同一语义空间后统一处理；图片用视觉编码器（如 ViT）。
- 「读图为什么可以不用 OCR？」→ 视觉模型直接理解图像内容（含图中文字、版式、图表），OCR 只能抠出纯文字、丢版式且可能识别错。

## 2.3 Streaming（流式输出）：前端的核心竞争力

### 是什么
默认情况下，模型要把整段回答生成完才一次性返回，用户要干等好几秒。开启 `stream: true` 后，模型**逐字/逐词地推送**，前端边收边渲染，就是你在 ChatGPT 里看到的"打字机效果"。

技术上通常用 **SSE（Server-Sent Events）**：服务端保持一个长连接，一段段把数据推给前端。前端用 `EventSource` 或 `fetch` 的 `ReadableStream` 逐块读取。

### 为什么对你尤其重要
《跳槽行动指南》第十一节明确写了"AI 产品交互（Streaming UI）"是你作为前端的差异化竞争力。后端同学能调通 LLM，但**把流式数据优雅地渲染成打字机效果、处理中断/报错/loading，是前端的活**。这是你在 AI 团队里的立足点之一。

### 面试深挖点
- 「Streaming 用什么协议？」→ 一般 SSE（单向、够用、比 WebSocket 轻）；也可以用 WebSocket（双向）。
- 「前端怎么接？」→ `fetch` 拿 `response.body.getReader()` 逐块解码，或用 `EventSource`。
- 「用户中途关闭怎么办？」→ `AbortController` 取消请求，避免后端继续烧 token。

## 2.4 Prompt 工程：让模型"听话"

### 是什么
Prompt 就是你发给模型的指令。Prompt 工程 = 用结构化的方式写指令，让模型**稳定地**产出你要的东西。

几个高频技巧：
- **角色设定**：system 里明确"你是谁、遵守什么规则"。
- **结构化输出**：明确要求"只返回 JSON，格式如下……"，并给出 schema。做匹配器必用。
- **Few-shot（少样本示例）**：给 1～2 个"输入→输出"的例子，模型模仿得更准。
- **约束与兜底**：如"信息不足时某项打分给 null，不要编造"。

### 为什么关键
匹配器要的是**可被前端解析的结构化结果**（分数、亮点数组、总结）。如果 prompt 写得松，模型一会儿返回 JSON 一会儿返回大段散文，前端就没法稳定渲染。Prompt 工程就是把这种不确定性压下去。

### 面试深挖点
- 「怎么保证模型一定返回合法 JSON？」→ prompt 强约束 + 用服务商的 JSON mode / response_format + 后端做解析校验和重试。
- 「Prompt 和微调（fine-tune）怎么选？」→ 先用 prompt，能满足就不碰微调；微调贵、要数据、迭代慢。

## 2.5 RAG（检索增强生成）：让模型知道"你的事"

### 是什么
RAG = Retrieval-Augmented Generation。核心思路：**先检索，再生成**。模型不知道你的私有数据（你的博客、简历、项目细节），那就在提问前，先从你的资料库里**捞出最相关的几段**，拼进 prompt 一起发给模型。

四个环节：
1. **切块（Chunking）**：把你的博客/简历切成一小段一小段（比如每段 300～500 字）。
2. **向量化（Embedding）**：用一个 embedding 模型把每段文字转成一串数字（向量），语义相近的文字，向量距离也近。
3. **检索（Retrieval）**：用户提问也转成向量，在库里找**距离最近**的几段（余弦相似度）。
4. **生成（Generation）**：把检索到的片段 + 用户问题一起塞进 prompt，让模型基于这些"证据"回答。

### 为什么关键（这是匹配器的可信度来源）
- 不用 RAG：模型只能泛泛地说"候选人有前端经验"，还可能**幻觉**（编造你没做过的事）。
- 用 RAG：模型能引用"候选人在 XX 项目做过首屏优化，首屏提升 3%"——**有出处、可信、不瞎编**。

> 小项目阶段不必上专业向量数据库。资料少的时候，直接在内存里存向量、算余弦相似度就够了。规模大了再上 Faiss / pgvector / 专业向量库。

### 面试深挖点
- 「为什么要用向量而不是关键词搜索？」→ 向量匹配的是**语义**。用户问"性能优化经验"，能匹配到写着"首屏加载提速"的段落，哪怕没有"性能"两个字。
- 「切块太大/太小有什么影响？」→ 太大：检索到的片段夹带无关信息，浪费 token 也稀释重点；太小：语义被切碎，丢上下文。要权衡。
- 「RAG 和把全部资料塞进 prompt 有什么区别？」→ 全塞：贵、可能超上下文窗口、无关信息干扰模型。RAG：只取相关的，省钱、聚焦、可扩展。

## 2.6 Tool Calling + Agent 循环：从"会说"到"会做"

### Tool Calling 是什么（Agent 的分水岭）
让模型能调用你提供的"工具"（其实就是你代码里的函数）。**注意：模型自己不执行函数**，它只是"决定要调哪个、参数是什么"，真正执行的是你的代码。完整闭环有五步：

```
1. 你把工具的"说明书"(JSON schema)连同问题发给模型
   例：工具 sendContactInfo(渠道) —— 当匹配度高时推送联系方式

2. 模型判断需要调工具，返回：「我要调 sendContactInfo，参数 渠道=微信」
   （此时模型还没有答案，它在"请求"你帮它执行）

3. 你的代码真正执行 sendContactInfo("微信")，拿到结果

4. 你把执行结果作为一条新消息（role: tool）塞回 messages，再发给模型

5. 模型基于工具返回的结果，生成最终自然语言回复
```

### Agent 循环（ReAct）是什么
单次工具调用还不算完整 Agent。Agent 的精髓是**循环**：

```
Reason（想）→ Act（调工具）→ Observe（看结果）→ Reason（再想）→ …… → 完成
```

模型每一步都根据当前结果**决定下一步做什么**，直到任务完成或达到停止条件。这个"想-做-看"的循环模式叫 **ReAct**。

举例（匹配器的完整 Agent 流程）：
```
用户贴入 JD
 → 模型想：我需要先了解候选人经历 → 调 RAG 检索工具
 → 观察：拿到 3 段相关项目经历
 → 模型想：证据够了，开始打分 → 生成匹配矩阵
 → 模型想：综合分 89，属于高匹配 → 调 sendContactInfo 工具
 → 观察：联系方式已推送
 → 生成最终回复给访客
```

### 为什么关键
这一层就是你说的交互核心：「匹配就推联系方式、不太匹配就挽留、不匹配就婉拒」——这些**差异化动作用工具调用实现，就是真正的 Agent 行为**，而不只是一个会打分的聊天框。

### 面试深挖点
- 「Tool Calling 里模型会自己执行函数吗？」→ 不会。它只输出"想调用的函数名+参数"，执行由你的后端完成，结果再回喂给模型。这是安全和可控的关键。
- 「怎么防止 Agent 无限循环？」→ 设最大步数上限、设停止条件、对异常工具结果兜底。
- 「ReAct 是什么？」→ Reasoning + Acting 交替：模型边推理边行动，用行动结果修正下一步推理。

# 第三部分：学习路线（先学什么后学什么）

原则：**别先啃理论，用一个能跑的 chat demo 打通链路，再逐层叠加能力**。每一步都是上一步的叠加，不要跳。

| 步骤 | 学习内容 | 学到什么程度 | 大概耗时 |
|------|----------|-------------|---------|
| 第 0 步 | 跑通一次 LLM API 调用 | 发一句话，拿到一句回复并打印 | 半天 |
| 第 1 步 | 多轮对话 + 流式输出 | 有记忆的聊天 + 打字机效果 | 1～2 天 |
| 第 2 步 | Tool Calling | 定义 1 个工具并完成调用闭环 | 2～3 天 |
| 第 3 步 | RAG | 基于自己博客/简历的问答 | 3～5 天 |
| 第 4 步 | Agent 循环（ReAct） | 能口述循环流程 + 一个组合示例 | 1～2 天（理解为主） |

### 各步骤的"产出物"（也是简历素材）
- 第 0～1 步做完：一个带流式效果的聊天框 → 已达到简历"完成 AI 小项目"门槛。
- 第 2 步做完：能通过对话操作数据的 demo → 能讲"工具调用闭环"。
- 第 3 步做完：基于你私有内容的问答 → 能写进简历、能讲 RAG。
- 第 4 步：主要是**概念能口述**，不必写重框架。

### 时间投入提醒
《跳槽行动指南》里 AI 是"辅助先决、不阻塞投递"，准备期只占 15～20% 时间。所以：
- **别追求做大**。第 0～2 步就足够 demo 和讲故事。
- RAG 是加分亮点，投递后有空再补。
- 优先保证"能 demo + 能讲清核心概念"，而不是功能堆多。

> 多模态（读 JD 截图）不单独占一个学习步骤：它是在做 L1 时，把"发文字"换成"发图片 + 文字"给视觉模型，多学的是模型选型和图片传参，概念上在 2.2 已讲清。

# 第四部分：项目落地 —— AI 岗位匹配器分层设计

> 这是把上面全部概念串起来的实战项目。设计成**分层**，每层单独可用、单独可讲，逐层加深。

## 4.1 项目一句话

在个人网站首页放一个「AI 岗位匹配器」：访客（面试官）**粘贴 JD 文字，或直接丢一张 JD 截图** → 系统对照你的简历/博客/项目经历，自动分析匹配度，输出匹配矩阵和综合分；再根据匹配程度触发差异化交互（高匹配推联系方式、中匹配挽留、低匹配礼貌婉拒并留联系方式）。

> 输入方式已确定：**同时支持文字和图片两种输入**。图片走支持视觉的多模态模型直接解析，**不用 OCR 中转**。

## 4.2 为什么这个项目适合你

1. **数据现成**：已有 `public/resume.md`、博客文章、项目故事文档，RAG 语料不用另造。
2. **技术栈现成**：React 18 + 现成后端 API（`localhost:3001`），加个匹配接口即可。
3. **前端亮点突出**：匹配矩阵动画 + 流式输出，正好展示 Streaming UI 能力。
4. **故事完整**：一个 demo 讲透 Prompt → 多模态 → RAG → Tool Calling → Agent 全部 P2 概念。
5. **面试官即用户**：交互对象就是面试官本人，比普通聊天框更有记忆点。
6. **多模态加分**：支持直接粘贴 JD 截图，用视觉模型解析，面试时是实打实的能力展示点。

## 4.3 分层设计（每层对应一个概念）

### L1 基础版 —— Prompt + 结构化输出 + Streaming + 多模态输入
- **做什么**：贴 JD 文字**或传 JD 截图** → 模型对照简历，流式输出匹配矩阵 JSON（分项分数 + 亮点数组 + 总结）。
- **多模态**：截图走视觉模型直接解析，不用 OCR。前端支持文字框 + 图片上传/粘贴两种入口。
- **前端**：分数条动画填充、打字机式渲染总结。
- **学到**：Prompt 结构化输出、Streaming UI、多模态输入。
- **本质**：一次（可能带图的）结构化 LLM 调用。**注意：这一层严格说还不算 Agent**，是 LLM 应用。做完就能 demo、能截图、能写简历。

### L2 加 RAG —— 让匹配有真凭实据
- **做什么**：把博客 + 简历 + 项目故事切块、向量化；JD 进来先检索最相关的几段经历，再让模型基于检索结果打分。
- **效果差异**：从"你有前端经验"升级到"候选人在 XX 项目做过首屏优化，提升 3%"——有出处、可信、不幻觉。
- **学到**：切块、Embedding、向量检索。
- **实现建议**：语料少，先用内存向量 + 余弦相似度，不必上向量数据库。

### L3 加 Tool Calling —— 真正成为 Agent
- **做什么**：根据匹配度，让模型自主决定调用哪个工具：
  - 高匹配 → `sendContactInfo`（推送微信/邮箱）、`bookInterview`（生成约面话术）
  - 中匹配 → `explainGap`（针对最差的一项，从经历里找可迁移证据来"挽留"）
  - 低匹配 → `politeDecline`（礼貌婉拒 + 留联系方式，体现"预填意愿"）
- **学到**：Tool Calling 闭环。这层是"从会打分的聊天框"变成"真 Agent"的分水岭。

### L4（可选，讲得出即可）—— ReAct 循环
- **做什么**：把 L2、L3 串成循环：RAG 查经历 → 打分 → 判断匹配档位 → 调对应工具，多步自主完成。
- **学到**：Agent 规划循环。面试能口述流程即可，不必写重框架。

## 4.4 模型选型（已确定：一步到位用视觉模型）

因为要支持 JD 截图，**主模型直接选支持视觉的多模态模型**，不再用纯文本模型 + OCR 的方案。

候选（都支持图片输入，按国内可用性/性价比排序，动手前再确认当下的接口与价格）：

| 模型 | 说明 |
|------|------|
| **通义千问 VL**（qwen-vl-max 等） | 阿里，国内直连、有免费额度、中文与视觉都不错，个人项目首选之一 |
| **智谱 GLM-4V** | 国内可用，支持视觉 |
| **GPT-4o** | 视觉能力强，但需国外支付/网络 |
| **Gemini** | 视觉强、免费额度大方，但需国外网络 |

选型注意：
- **优先国内可直连、带免费额度**的（通义 VL / 智谱），省去网络和支付的麻烦，适合放在你公开的线上网站。
- 一个系统里**可以按能力用不同模型**：读图/打分用视觉模型，若某步纯文本推理也可换更便宜的模型。学习期先用一个视觉模型跑通即可，别过早拆分。
- embedding（RAG 用）通常是**单独的向量模型**，和对话/视觉模型分开选。

> 具体选哪个，等真正动手前我们再一起定并确认接口文档。

# 第五部分：动手前的避坑清单

## 5.1 安全（最重要）
- **API Key 绝对不能放前端**。前端能看到的东西全世界都能看到。必须走你自己的后端中转，Key 只存在后端环境变量里。
- 这个匹配器对公网开放（面试官在线上用），要防滥用。

## 5.2 成本
- 公开的 LLM 接口可能被刷，每次调用都花钱。上线要加**限流**（按 IP 限次数）或轻量验证。
- 控制历史 messages 长度、限制 `max_tokens`、低频场景用小模型。

## 5.3 工程
- **模型输出不一定是合法 JSON**：后端要做解析校验，失败时重试或兜底。
- **流式要处理异常**：网络中断、用户关闭页面（用 `AbortController` 取消，别让后端继续烧 token）。
- **RAG 切块**：太大浪费 token 且稀释重点，太小丢上下文，需要调。

## 参考答案

> 建议先自己答，再对照。答案是"能讲清"的要点，不用背原话。

**概念题**

1. **没有记忆。** 模型是无状态的，它不记得上一句。多轮对话的"记忆"靠客户端每次请求**把历史 messages 数组再传一遍**，模型每次都是重新读一遍完整上下文。

2. **system**：开头设定角色和规则，整段对话设一次，权重最高；**user**：用户说的话；**assistant**：模型说过的话。多轮时把历史的 user/assistant 都带上，模型才有上下文。

3. **temperature 低（0～0.3）** 输出稳定、可复现，适合打分、抽取、分类这类要确定性的场景；**高（0.7～1+）** 输出更发散有创意，适合写文案、头脑风暴。匹配器打分用低值。

4. **token** 是模型处理文字的最小单位，约 0.5～1 个汉字 / 4 个英文字符。它关系成本是因为**输入+输出都按 token 计费**；关系长度是因为模型有**上下文窗口**上限（一次能容纳的 token 总数有限），超了就要裁剪或摘要。

5. **多模态模型（LMM）是 LLM 的扩展**：LLM 严格指只处理文字，LMM 能同时处理文字+图片（甚至音频视频）。**"模态"指信息的形式**——文本、图像、音频、视频各是一种模态。

6. **各模态先分别编码成向量，再映射到同一个语义空间统一处理**：文字分词成 token 向量，图片经视觉编码器（如 ViT）切块编码成向量，两者进同一空间后模型就能关联理解。本质和 RAG 的 embedding 同源。

7. **视觉模型直接"看懂"图片内容**（含图中文字、版式、图表、颜色），一步到位；**OCR 只能抠出纯文字**，丢掉版式且可能识别错，还多一个环节。取舍：视觉模型体验好、能理解复杂版面，但通常更贵、图片也占 token；OCR+文本模型更省钱但信息有损。匹配器已定用视觉模型、不走 OCR。

8. **一般用 SSE**（Server-Sent Events，服务端单向持续推送，比 WebSocket 轻）。前端用 `fetch` 拿 `response.body.getReader()` 逐块读取解码，或用 `EventSource`。用户中途离开用 **`AbortController` 取消请求**，避免后端继续生成、白烧 token。

9. 三招叠加：**Prompt 里强约束**（"只返回 JSON，格式如下…"并给 schema）+ **用服务商的 JSON mode / response_format**（能强制合法 JSON）+ **后端做解析校验**，失败就重试或兜底。

10. **切块 → 向量化 → 检索 → 生成**：① 把资料切成小段；② 用 embedding 模型把每段转成向量存起来；③ 提问也转向量，按相似度找最相关的几段；④ 把检索到的片段拼进 prompt，让模型基于它生成回答。

11. **向量匹配的是语义，关键词匹配的是字面。** 问"性能优化经验"，向量检索能命中写着"首屏加载提速"的段落（意思相近），而关键词搜索因为没有"性能"二字就漏掉了。

12. **省钱、聚焦、可扩展、不超窗口。** 全塞：贵（每次都发全部）、可能超上下文窗口、无关信息干扰模型判断；RAG 只取相关片段，成本低、重点突出，资料再多也能撑。

13. **函数是你的代码执行的，不是模型。** 模型只输出"想调哪个函数、传什么参数"。闭环 5 步：① 把工具 schema+问题发给模型；② 模型返回要调的函数和参数；③ 你的代码执行该函数拿结果；④ 把结果作为一条 `role: tool` 消息塞回 messages 再发给模型；⑤ 模型基于结果生成最终回复。

14. **ReAct = Reasoning + Acting**，模型"想-做-看"交替循环：推理→调工具→观察结果→再推理，直到完成。**单次工具调用是一锤子买卖**（调一次就出答案）；**Agent 循环能多步、根据每步结果动态决定下一步**，这才是 Agent 的核心。

15. **设最大步数上限**（超了强制停）+ **设明确的停止条件**（任务完成即结束）+ **对异常/空的工具结果做兜底**，避免模型反复调同一个工具死循环。

**项目题**

16. **L1（贴 JD → 出分数）算 LLM 应用**，因为它只是一次结构化调用，没有工具、没有多步决策；**L3 加了 Tool Calling（根据匹配度自主调推联系方式/婉拒等工具）才算 Agent**，因为模型开始"自主决定做什么动作"。分水岭是**有没有自主调用工具去改变外部状态**。

17. **靠 RAG。** 不检索的话模型只能泛泛说"有前端经验"甚至编造；接了 RAG 后，先从我的简历/博客/项目故事里检索相关经历，模型**基于真实片段打分并引用具体项目和数据**，有出处、可追溯，大幅降低幻觉。

18. **靠 Tool Calling。** 给模型定义几个工具（`sendContactInfo`、`explainGap`、`politeDecline`），模型根据综合分档位**自主决定调哪个**：高匹配调推联系方式、中匹配调挽留话术、低匹配调礼貌婉拒。差异化动作 = 不同工具，这就是 Agent 行为。

19. **因为要支持面试官直接贴 JD 截图**，视觉模型能一步解析、体验最顺，也是面试加分点。选型考量：① 是否真支持图片输入；② **国内能否直连、有无免费额度**（放在公开线上网站，省网络和支付麻烦）；③ 中文能力和性价比。所以优先通义千问 VL / 智谱 GLM-4V 这类国内可用的。

20. **只能放后端，存在后端环境变量里，前端通过自己的后端中转调用。** 因为前端代码和网络请求用户都能看到，Key 放前端等于公开，会被盗刷额度。

21. **加限流和防护**：按 IP/会话限调用次数、限 `max_tokens`、加轻量验证码或人机校验；后端做请求校验，必要时设每日总量上限。核心是别让公开接口被脚本无限刷爆产生费用。

# 第七部分：术语表

| 术语 | 通俗解释 |
|------|---------|
| **LLM** | 大语言模型，一个"文字接龙"引擎，无记忆、不能自己动手；严格指纯文字 |
| **模态（Modality）** | 信息的形式/类型：文本、图像、音频、视频等 |
| **多模态 / LMM** | 能同时处理并关联多种模态（文字+图片等）的模型，是 LLM 的扩展 |
| **视觉编码器（如 ViT）** | 把图片切块编码成向量的组件，让图像能进入模型的语义空间 |
| **Token** | 模型处理文字的最小单位，约 0.5～1 个汉字；计费和长度都按它算 |
| **上下文窗口（Context Window）** | 一次请求能容纳的最大 token 数（输入+输出） |
| **Prompt** | 你发给模型的指令 |
| **System Prompt** | 开头设定角色和规则的那条消息，权重最高 |
| **Few-shot** | 在 prompt 里给几个"输入→输出"示例，让模型模仿 |
| **Temperature** | 输出随机度，0 最稳定，越高越发散 |
| **Streaming（流式）** | 模型逐字推送、边生成边显示，即打字机效果 |
| **SSE** | Server-Sent Events，服务端单向持续推送数据的协议，常用于流式 |
| **Embedding（向量化）** | 把文字转成一串数字，语义相近的文字向量也相近 |
| **向量（Vector）** | 一串代表文字语义的数字 |
| **余弦相似度** | 衡量两个向量方向接近程度的算法，用来判断语义相似度 |
| **Chunking（切块）** | 把长文档切成小段，便于向量化和检索 |
| **RAG** | 检索增强生成：先从私有资料检索相关片段，再喂给模型生成回答 |
| **幻觉（Hallucination）** | 模型一本正经地编造不存在的事实 |
| **Tool Calling / Function Calling** | 模型决定调用哪个外部函数、传什么参数；执行由你的代码完成 |
| **Agent（智能体）** | 以 LLM 为大脑，能调工具、分多步自主完成目标的系统 |
| **ReAct** | Reasoning + Acting，模型"想-做-看"交替循环的模式 |
| **微调（Fine-tune）** | 用数据再训练模型改变其行为；贵、慢，能用 prompt 就别先碰 |
