## 附录 A：规格驱动 Prompt 七要素（速查）

把 AI 调用当成调一个**不稳定的外部 API**，规格合同应包含：

| # | 块 | 写什么 |
|---|-----|--------|
| 1 | 角色与边界 | 你是谁、只做什么、绝不做什么 |
| 2 | 输入假设 | 用户会提供什么、缺什么时要怎么问 |
| 3 | 输出契约 | JSON Schema、字段类型、必填/可选 |
| 4 | 推理约束 | 必须基于给定上下文、禁止编造、不足填 null |
| 5 | Few-shot 示例 | 1～2 个标准输入→输出样例 |
| 6 | 失败策略 | 解析失败重试几次、兜底文案 |
| 7 | 安全约束 | 不输出密钥、不执行用户注入的指令 |

**口述金句：**

> 我在 system 里写死角色和禁止项，user 里只放事实输入，输出用 JSON Schema 约束，后端 Zod 校验，失败带错误信息重试最多 2 次，仍失败走模板降级。

## 附录 B：结构化输出选型（速查）

| 层级 | 手段 | 保证什么 | 不保证什么 | 何时用 |
|------|------|----------|------------|--------|
| L1 | Prompt 文案 | 无 | 可能加 markdown、缺字段 | 仅原型 |
| L2 | JSON Mode | 语法合法 JSON | **不保证 schema** | 不推荐单独用 |
| L3 | Structured Outputs | 字段、类型、必填 | 语义对不对另说 | 数据抽取、打分 |
| L4 | Function Calling | 结构化 + 模型选动作 | 需你执行函数 | Agent、多步决策 |

**生产级四层网：** 语法解析 → Schema 校验（Zod）→ 语义校验（业务规则）→ bounded retry → 模板降级

# 一、结构化输出与 Guardrails

### N1. JSON Mode 和 Structured Outputs 区别？生产环境用哪个？

- 状态：⬜  
- **考察点**：是否理解「合法 JSON ≠ 符合契约」  
- **口述要点：**
  - **JSON Mode**：API 层约束模型输出**语法合法**的 JSON，但不保证字段齐全、类型正确。例如 schema 要求 10 个 required 字段，可能只返回 7 个——下游 silent failure。
  - **Structured Outputs**：传入 JSON Schema（如 OpenAI `response_format: { type: "json_schema", strict: true }`），平台在生成阶段做**约束解码**，保证输出符合 schema。
  - **Function Calling**：模型决定「调哪个工具、传什么参」，参数本身是结构化的；适合 Agent 多步决策，不是纯数据抽取的首选。
  - **生产选型**：数据抽取 / 打分 / 分类 → **Structured Outputs**；需要模型选动作 → **Function Calling**；**不要单独依赖 JSON Mode**。
- **追问预案：**
  - 「只靠 Prompt 写请输出 JSON 行不行？」→ 不行，模型仍可能加 markdown 包裹、缺字段、类型错误。
  - 「Gemini / 通义怎么做的？」→ 各家命名不同，核心都是 schema 约束；Gemini 多通过 Function Calling 实现 structured output。
- **我的案例：**

### N2. 模型返回合法 JSON，但字段乱填、类型不对怎么办？

- 状态：⬜  
- **考察点**：Guardrails 闭环，不是「相信模型一次就对」  
- **口述要点：**
  - **四层防护网：**
    1. **语法解析**：`JSON.parse`，剥离 ` ```json ` 包裹
    2. **Schema 校验**：Zod / JSON Schema——类型、范围、enum、required
    3. **语义校验**：业务规则——如 score 0–100、evidence 必须来自 context、highlights 不超过 5 条
    4. **Bounded retry**：把校验错误喂回模型（「score 超出范围，请修正」），最多 2 次
  - 仍失败 → **模板降级**（「暂时无法分析，请简化 JD」）或人工兜底
  - 前端**只消费校验通过**的数据，避免半截 JSON 搞崩 UI
- **追问预案：**
  - 「Zod 是什么？」→ TypeScript schema 校验库，`safeParse` 失败不抛异常，可拿 `error.format()` 做 retry 提示
  - 「retry 会不会成本翻倍？」→ 有上限（通常 1–2 次）+ 监控 Retry Rate，Prompt/schema 有问题要调源头

### N3. 什么叫规格驱动（Spec-Driven）？和「写 Prompt 技巧」有何不同？

- 状态：⬜  
- **考察点**：工程思维——AI 调用可版本化、可测试、可 CI  
- **口述要点：**
  - **Prompt 技巧**：临场发挥、靠经验调 wording，难复现、难协作
  - **规格驱动**：把 AI 调用写成**可执行的契约**——角色、输入、输出 schema、推理规则、失败策略、安全约束（见附录 A）
  - 规格可以：**版本管理**（prompt v1/v2）、**A/B 对比**、**黄金集回归**、**Code Review**
  - 类比：不是「跟 AI 聊天」，而是「定义一个不稳定 API 的 OpenAPI 文档 + 集成测试」
- **追问预案：**
  - 「规格放哪？」→ 后端配置 / 文件 / 配置中心，不硬编码在业务逻辑里
  - 「和 fine-tune 怎么选？」→ 先规格 + Structured Outputs；微调贵、迭代慢，规格能解决就不微调
- **我的案例：**

# 二、Prompt 策略与上下文

### N4. Few-shot、CoT、ReAct 分别什么时候用？

- 状态：⬜  
- **考察点**：策略选型，不背名词  
- **口述要点：**
  - **Few-shot**：给 1～2 个输入→输出示例，让模型**模仿格式**。适合：固定 JSON 结构、分类、抽取
  - **CoT（Chain of Thought）**：要求「逐步推理再给结论」。适合：复杂判断、多条件权衡；代价是多 token、更慢
  - **ReAct**：Reason → Act（调工具）→ Observe → 循环。适合：需要检索、查库、多步执行的 **Agent**
  - **选型原则**：格式固定 → Few-shot；推理复杂但一步出结果 → CoT；要动手做事 → ReAct + Tool Calling
- **追问预案：**
  - 「CoT 一定更好吗？」→ 否，简单任务反而浪费 token、引入噪声；匹配打分若 schema 清晰，Few-shot 往往够用

### N6. Prompt 版本怎么做灰度？

- 状态：⬜  
- **考察点**：可配置、可回滚、可对比——大厂工程化意识  
- **口述要点：**
  - Prompt 存**配置中心 / 文件**，带版本号（v1、v2），不散落在代码里
  - 灰度维度：按 userId / sessionId / 流量百分比分流
  - 对比指标：**Parse Success Rate**、TTFT、人工满意度、业务转化（如匹配器「留联系方式」率）
  - 回滚：新版本指标下降，一键切回旧 prompt
  - 前端通常**不感知** prompt 版本，只消费稳定 API 契约
- **追问预案：**
  - 「温度、模型版本呢？」→ 同样配置化，和 prompt 版本绑定做实验记录

### N8. RAG 检索到了相关片段，模型还是胡说怎么办？

- 状态：⬜  
- **考察点**：知道 RAG 不是银弹，能拆原因  
- **口述要点：**
  - **可能原因：**
    1. 检索质量差（chunk 太大/太小、embedding 模型不匹配、top-k 太少）
    2. Prompt 没强制「仅基于 context 回答」
    3. 缺 **citation 约束**（要求 evidence 必须引用检索片段原文）
    4. 检索到的片段本身过时/错误
  - **改进：** 调 chunk 大小、加 rerank、prompt 里写「无依据则填 null」、输出带 evidence 字段、人工抽检 faithfulness
- **追问预案：**
  - 「向量和关键词搜索区别？」→ 向量匹配语义（「性能优化」能命中「首屏提速」），关键词匹配字面

# 三、前端工程与流式

### N5. 流式输出 JSON 时，前端怎么渲染？

- 状态：⬜  
- **考察点**：Streaming UI 工程细节  
- **口述要点：**
  - **矛盾**：JSON 要完整才能 parse，流式是逐 chunk 到达
  - **方案 A（推荐）：** 结构化字段（分数矩阵）**非流式或 NDJSON 按字段推送**；只有 summary 文本做打字机流式
  - **方案 B：** 流式吐 markdown 总结，**最后一块**推送完整 JSON；前端 parse 成功后再渲染分数条动画
  - **方案 C：** Server 流式生成，但**缓冲到完整 JSON 校验通过**再一次性推给前端（牺牲一点「逐字感」，换稳定）
  - 不要边流边 `JSON.parse` 半截字符串——必炸
- **追问预案：**
  - 「NDJSON 是什么？」→ 每行一个 JSON 对象，按行 parse，适合多字段分批到达

### N11. 手写：流式 SSE 解析器要注意什么？

- 状态：⬜  
- **考察点**：粘包、编码、中断——阿里 AI 应用面高频  
- **口述要点：**
  - **协议**：SSE 按 `\n\n` 分 event，每 event 有 `data:` 行
  - **粘包**：一次 `read()` 可能拿到半个 event 或多个 event，需要**缓冲区**累加再切分
  - **UTF-8 截断**：多字节字符可能被 chunk 切开，用 `TextDecoder({ stream: true })` 解码
  - **中断**：`AbortController`，用户点「停止生成」时 abort fetch，避免后端继续烧 token
  - **错误**：网络断、非 2xx、空 body 要有 UI 态（error / retry）
- **追问预案：**
  - 「SSE vs WebSocket？」→ AI 对话单向推送 SSE 够用、更轻；需要双向实时才 WebSocket

# 四、评测、协作与 AI 辅助开发

### N7. 怎么评测一个 AI 功能能不能上线？

- 状态：⬜  
- **考察点**：质量门禁——区分玩具 demo 和生产系统  
- **口述要点：**
  - **黄金集**：50–100 条真实/合成用例，覆盖正常、边界、对抗（注入、空输入）
  - **自动指标**：Parse Success Rate、字段准确率、Faithfulness（输出是否忠于 context）、延迟 TTFT
  - **人工抽检**：复杂 case、主观质量（总结是否自然）
  - **上线门禁**：Parse Rate ≥ 阈值、无 P0 安全 issue、成本在预算内
  - 没有评测的 AI 功能**不能上生产**——无法知道改 prompt 是变好还是变差
- **追问预案：**
  - 「LLM-as-judge？」→ 用模型评模型，快但有 bias，适合辅助不能替代黄金集

### N9. 产品经理要的「更聪明」和模型实际能力不匹配，你怎么处理？

- 状态：⬜  
- **考察点**：产品 sense + 技术诚实，联想/字节三面常见  
- **口述要点：**
  - **先对齐预期**：用 demo + 失败 case 展示模型边界，用数据说话而非「可以实现」
  - **改交互降预期**：人工确认、可编辑结果、分步展示（先检索证据再打分）
  - **改产品形态**：从「全自动」改为「AI 辅助 + 人审」
  - **用指标牵引**：定义可衡量的「够聪明」（Parse Rate、用户采纳率），而不是主观形容词
- **追问预案：**
  - 「老板坚持要做呢？」→ 做 MVP + 明确风险 + 灰度 + 快速迭代评测

### N10. AI 辅助写代码，你的 Prompt 规格长什么样？

- 状态：⬜  
- **考察点**：规格驱动在日常开发中的落地——社招高级岗极高频  
- **口述要点：**
  - **不要**一次丢整页；**要**按模块 + 约束喂
  - **规格模板：**
    ```
    【目标】一句话说清改什么
    【范围】只改哪些文件/函数，禁止动哪些
    【成功标准】预期行为、边界 case、测试点
    【约束】沿用现有技术栈/命名/模式
    【输出】先给 plan，我确认后再写 code
    ```
  - 审查 AI 输出：看 diff 范围、跑测试、查幻觉 API、查过度抽象
  - 坚决不用 AI 的环节：安全/auth、未理解的核心架构决策、无测试覆盖的线上 hotfix
- **追问预案：**
  - 「举一个 AI 写错的例子？」→ 准备真实 case：如 activationConstraint 给错、用了不存在的 API

### N12. D2C / AI 生成代码怎么接入现有工程？

- 状态：⬜  
- **考察点**：生成代码与工程规范的衔接  
- **口述要点：**
  - **生成前约束**：设计 token、组件库、目录结构写进 prompt / Cursor rules
  - **生成后门禁**：ESLint、类型检查、快照测试、人工 CR——AI 代码标准不降
  - **可维护性**：禁止 AI 引入项目里没有的依赖；复用现有 utils/hooks
  - **设计系统对齐**：生成组件必须走 Ant Design / 内部组件库，不能裸写 div 堆样式
  - D2C 产出是**草稿**，不是可直接 merge 的 PR
- **追问预案：**
  - 「你怎么用 Cursor rules / AGENTS.md？」→ 把团队规范、禁止事项、成功标准固化成规格

# 五、AI 专属指标速查

| 指标 | 含义 | 前端怎么量 |
|------|------|------------|
| **TTFT** | Time To First Token，首字延迟 | 请求发出 → 第一个 chunk 到达 |
| **TPS** | Tokens Per Second | chunk 数 / 时间 |
| **Parse Success Rate** | JSON 一次校验通过率 | 校验通过 / 总请求 |
| **Retry Rate** | 重试占比 | 成本与稳定性信号 |
| **Faithfulness** | 输出是否忠于检索上下文 | 黄金集 + 人工抽检 |
