## 一、浏览器与 JavaScript

### 浏览器的线程模型

这题没被单独问，但它是 setTimeout 那道追问的真正落点——面试官问的是「**它是什么时候放到宏任务队列的**」，你答「首先需要定时器，3 秒之后把它放到宏任务队列」，其实已经摸到门口了，只是没说出「定时器线程」这个词。

答这题**先分进程再说线程**，否则被追问「那网络请求到底是线程还是进程」就乱了。浏览器是多进程架构：浏览器主进程（界面、地址栏、子进程管理）、渲染进程（每个站点一个，Site Isolation）、网络进程、GPU 进程、插件进程。通常问的「浏览器线程」，指的是**渲染进程内部**的线程。

五个经典线程：

- **GUI 渲染线程** — 负责 Layout、Paint
- **JS 引擎线程** — 执行 JS，和 GUI 渲染线程**互斥**，这是「JS 阻塞渲染」的物理原因
- **定时器线程** — setTimeout / setInterval 的**计时由它负责**，计时到了才把回调推进宏任务队列。所以 JS 引擎再忙也不影响计时，只影响回调什么时候被取出来执行
- **事件触发线程** — 把满足条件的回调放进任务队列
- **异步 HTTP 请求线程** — 请求完成后把回调交给事件触发线程

再补三个，大部分候选人答不出来，是明确的加分项：**合成线程（Compositor Thread）**，`transform` 和 `opacity` 动画只走它，主线程卡死动画照样流畅；**光栅化线程池（Raster Threads）**，把图层切片转成位图；**Worker 线程**，Web Worker 和 Service Worker，独立 JS 运行环境，没有 DOM 访问权。

一句边界值得主动说：Chrome 真实实现里并没有一个叫「定时器线程」的东西，定时器由消息循环（TaskRunner）按到期时间调度，网络请求也早就搬到独立的网络进程了。这套五线程模型是教学抽象，照着答没问题，但被追问实现细节时主动点破比被问穿好。

**怎么记**：别背列表，背一张「任务队列进出图」。队列画在中间，每个线程只做三件事之一——**投递**（定时器线程和异步 HTTP 线程干完活，都经由事件触发线程往队列里扔回调，两个生产者加一个投递员）、**取出**（只有 JS 引擎线程，唯一消费者，单线程）、**抢位**（GUI 渲染线程和 JS 引擎共用主线程，JS 不让位它就画不了）。合成线程在图外面，完全不参与这个循环。口诀：**三个投、一个取、一个抢，外加一个不参与的合成线程。**

四个自检问题，能答出来就不用背了：没有定时器线程会怎样（JS 忙的时候计时就停了，`setTimeout(1000)` 变成「JS 空闲后才开始数一秒」）；没有事件触发线程会怎样（回调没人送进队列）；GUI 和 JS 不互斥会怎样（JS 改 DOM 的同时渲染线程在读，读到撕裂的中间状态）；没有合成线程会怎样（动画全要主线程参与，一个长任务就卡）。

记住这个模型，四道题串成一条线：setTimeout 不准、JS 阻塞渲染、Web Worker 为什么能解决卡顿（展开见「Web Worker」节）、transform 动画为什么不卡。

### 事件循环

一轮的完整顺序是：取一个宏任务 → 执行 → 清空整个微任务队列 → 判断是否需要渲染 → 取下一个宏任务。首次执行时整个 `<script>` 本身就是一个宏任务。

两个容易被追问的细节：微任务队列清空是「一直清到空」，期间新产生的微任务也要在本轮执行完；渲染时机在微任务清空之后，且通常每轮事件循环最多渲染一次。Node 的事件循环是分 phase 的（timers、poll 等），和浏览器不是一套，别混着答。

`requestAnimationFrame` 的回调在**渲染之前**执行，它既不是宏任务也不是微任务，是渲染流程里的一个固定时机。

### 宏任务与微任务的分类

宏任务：script 整体、setTimeout / setInterval、I/O、postMessage、UI rendering。
微任务：Promise 的 then / catch / finally、queueMicrotask、MutationObserver，Node 里还有优先于 Promise 的 process.nextTick。

两个坑：`new Promise(fn => fn())` 里的同步部分是立即执行的，只有 `.then` 的回调才进微任务；`async` 函数在第一个 await 之前是同步执行，await 之后的代码相当于 `.then`，进微任务。

经典输出题：`setTimeout(() => log(1), 0); Promise.resolve().then(() => log(2)); log(3)` 输出 3、2、1。

### 微任务过多会怎样 ⚠️

上场只说了「可能阻塞渲染」，太薄。

关键因果是：每轮宏任务之后必须把微任务队列**清空**才能进入渲染阶段，所以如果微任务里不断产生新微任务，渲染永远轮不到——这叫 render starvation，表现是白屏、卡顿、点击没反应。影响的指标不只是「刷新变慢」，而是 INP 和 TTI 这类交互指标。

解法三个方向：把长微任务链拆开，用 `setTimeout(0)` 主动让出一个宏任务；不紧急的活交给 `requestIdleCallback`；计算量大的搬进 Web Worker。排查靠 Performance 面板看 Long Task。

### setTimeout 为什么不是精确 3 秒 ⚠️

机制理解是对的，但上场表达乱、来回绕。按这个顺序讲五条：

第一，计时到期只代表「可以入队」，不等于立刻执行。第二，入队之后要等当前宏任务跑完、以及它带的整个微任务队列清空。第三，队列里可能还排着别的宏任务，轮到你之前都在等。第四，浏览器主动节流——后台标签页最小延迟会被拉到 1000ms 以上，嵌套超过 5 层的 setTimeout 最小间隔变成 4ms。第五，定时器本身就是毫秒级近似，不是实时系统保证。

### 怎么让定时更准 ❌

上场答的是「setInterval 设一次循环 3 秒好像可以」，这是错的——setInterval 同样漂移，而且回调执行时间超过间隔还会**堆积**。

按场景给方案：

- 动画、倒计时这类 UI：`requestAnimationFrame` 配 `performance.now()` 自己算已过时长
- 不能被主线程阻塞的计时：放进 Web Worker（展开见下一节）
- 防堆积：用**递归 setTimeout** 代替 setInterval，每次执行完再排下一次
- 过期任务：`clearTimeout` 主动取消
- 需要绝对时间对齐的（订单倒计时、支付超时）：以**服务端截止时间**为准，客户端只负责展示，别拿本地 timer 做关键逻辑

```javascript
// 用 rAF 做更准的延迟
function delay(ms) {
  return new Promise(resolve => {
    const start = performance.now();
    function tick(now) {
      if (now - start >= ms) resolve();
      else requestAnimationFrame(tick);
    }
    requestAnimationFrame(tick);
  });
}
```

再补一条：页面 `document.hidden` 时应该暂停计时逻辑，回到前台再校准。

### Web Worker

前面「线程模型」和「怎么让定时更准」都点到了它，这里展开。

**是什么** — 浏览器给 JS 的真·多线程能力：主线程之外开一条独立线程跑 JS，有自己的事件循环、自己的任务队列、自己的内存堆。两边**不共享变量**，只能 `postMessage` 传消息，数据走结构化克隆算法拷贝一份过去。所以不存在传统多线程的锁和竞态，代价是大对象拷贝很贵。

**能力边界**（最常被追问的点）— Worker 里**没有 DOM、没有 `window`、没有 `document`**。能用的是 `self`、`location`、`navigator`、`fetch`、`XHR`、`WebSocket`、`IndexedDB`、`setTimeout` / `setInterval`、`importScripts`、Performance API。创建用 `new Worker('worker.js')`，受同源限制，必须是独立文件或 Blob URL，现代写法加 `{ type: 'module' }` 用 ESM。

三种 Worker 要能分清：

| 类型 | 作用域 | 典型用途 |
|---|---|---|
| Dedicated Worker | 创建它的那一个页面独占 | 重计算、精确计时 |
| Shared Worker | 多个同源页面共享一个实例 | 跨标签页通信、共享连接 |
| Service Worker | 拦在页面和网络之间的代理 | 离线缓存、推送、PWA |

**成本要主动说** — 启动有开销（几毫秒到几十毫秒）、额外占内存、`postMessage` 的序列化反序列化在数据量大时本身就是长任务。所以它适合**大块计算**（加解密、图片处理、Excel 解析、大数组 diff、语法高亮），不适合高频传小数据，那种情况通信成本会超过计算收益。想避开拷贝成本用 Transferable Objects，`ArrayBuffer` 能零拷贝转移所有权。

#### 为什么 Worker 能「精准计时」

先把前提讲清楚：**Worker 没有让定时器本身变准，它让回调能准时被取出来执行。** 这两件事不一样，说破这层就赢一半。

回到上一节 setTimeout 不准的五条原因，Worker 解决的是**最关键的一条：队列被堵**。Worker 有自己独立的事件循环和任务队列，而这条队列里通常**只有计时回调**——没有 React 渲染、没有用户事件、没有业务逻辑，队列几乎永远是空的，定时器一到期回调立刻被取出来执行。主线程那边哪怕正在跑 500ms 的长任务也不受影响。Worker 也不参与 GUI 渲染线程的互斥，不会被 Layout 和 Paint 挤占。

两点必须诚实讲出来，否则容易答过头：**4ms 的嵌套钳制在 Worker 里同样生效**，规范对 `WorkerGlobalScope` 一视同仁；「后台标签页不节流」这个常见说法已经不可靠，各浏览器对 Worker 的后台节流一直在收紧，不同版本行为不一致，不能当保证。所以稳妥架构是 **Worker 只负责计时和报时，绝对时间以服务端截止时间为准，回到前台主动校准一次**。

还有一个加分的深度点：`postMessage` 发回主线程的消息**仍然要进主线程的任务队列**。所以 Worker 保证的是「计时准」，不保证「显示准」——主线程卡在长任务上时 UI 更新照样延迟。只有主线程能改 DOM，这是物理限制，Worker 突破不了。

顺着这点必须想清楚一个问题：**那 Worker 相比「主线程 + `performance.now()` 自校正」到底赢在哪？** 单论 UI 倒计时的显示效果，两者几乎一样，都卡在同一个主线程上。Worker 真正不可替代的是三种情况——**主线程持续繁忙而非偶发卡顿时，自校正方案连 `performance.now()` 都没机会跑，根本不知道时间到了，而 Worker 能保证「到期」这个判定准时发生**；到期后要做的事不需要主线程（fetch 上报、WebSocket 心跳、会话超时登出、支付超时关单），Worker 里直接做，完全绕开主线程队列；计时之外还有计算量，顺手一起搬过去。纯 UI 倒计时用自校正就够，上 Worker 是过度设计。

#### 关键写法：自校正的递归 setTimeout

光把 `setInterval` 搬进 Worker 不够，误差照样累积。要每次根据**实际流逝时间**算下一次间隔：

```javascript
// timer.worker.js
let timerId = null;

self.onmessage = ({ data }) => {
  if (data.type === 'stop') { clearTimeout(timerId); return; }

  const start = performance.now();
  const { duration } = data;

  const tick = () => {
    const elapsed = performance.now() - start;
    const remaining = duration - elapsed;
    if (remaining <= 0) return self.postMessage({ type: 'done' });

    self.postMessage({ type: 'tick', remaining });
    // 自校正：对齐到下一个整秒边界，误差不累积
    timerId = setTimeout(tick, 1000 - (elapsed % 1000));
  };
  tick();
};
```

```javascript
// 主线程只管收消息改 UI
const worker = new Worker(new URL('./timer.worker.js', import.meta.url));
worker.onmessage = ({ data }) => {
  if (data.type === 'tick') setRemaining(data.remaining);
};
worker.postMessage({ type: 'start', duration: 60_000 });
```

两个要点：用**递归 setTimeout** 而非 `setInterval`，避免回调耗时超过间隔时堆积；间隔用 `1000 - (elapsed % 1000)` 而非固定 `1000`，每次把误差吃掉，一小时也不漂。

**一句话记忆**：Worker 解决卡顿和解决计时不准是同一件事的两面——**它给你换了一条没人排队的队列**。卡顿是主线程队列里活太多，计时不准是计时回调在那条队列里排不到位，把活挪走或把计时挪走，都是让关键任务不用排队。

### 从输入 URL 到页面可交互 ⚠️

主链路答出来了，缺 TCP/TLS 和渲染树那几步。完整的是：

解析 URL → DNS 查询 → TCP 三次握手 → TLS 握手（HTTPS）→ 发 HTTP 请求 → HTML 字节流返回 → 边下边解析构建 DOM → 解析 CSS 构建 CSSOM → DOM 加 CSSOM 合成 Render Tree → Layout → Paint → Composite → load 事件 → JS 绑定交互 → 主线程空闲即可交互。

一处表述要纠正：CSS **阻塞渲染**，但不阻塞 DOM 解析。上场说成了「阻塞加载」又自己改口，讲清楚这个区别就够。

但只说这两条还不完整，CSS 其实有**第三条**规则，也是最能体现理解深度的一条：**CSS 阻塞它后面的同步 script 执行**。因为脚本里可能调 `getComputedStyle` 读样式，浏览器必须保证 CSSOM 已就绪才敢执行它。于是形成一条间接阻塞链——`<link>` 没加载完 → 后面的 `<script>` 不能执行 → 主解析器卡在这个 script 上 → DOM 解析跟着停。所以「CSS 不阻塞 DOM 解析」只在没有同步脚本横在中间时才成立，这个转折点正是追问的落点。

script 的三种行为：默认会阻塞 HTML 解析，下载并立即执行；`defer` 并行下载，在 HTML 解析完毕之后、DOMContentLoaded 之前按文档顺序执行；`async` 并行下载，下完立刻执行（执行那一刻会打断解析），多个 async 之间顺序不保证。这也是 CSS 放 head、JS 放 body 底部或加 defer 的原因。

| 写法 | 下载 | 执行时机 | 多个之间顺序 | 打断 HTML 解析 |
|---|---|---|---|---|
| `<script>` | 并行（预解析器提前发起） | 下载完立即 | 文档顺序 | 是 |
| `defer` | 并行 | 解析完毕后、DCL 前 | 文档顺序 | 否 |
| `async` | 并行 | 下载完立即 | 不保证 | 执行那一刻会 |
| `type="module"` | 并行 | 同 defer | 文档顺序 | 否 |

默认选 `defer`（要操作 DOM、脚本间有依赖顺序的业务代码都归它），完全独立的第三方脚本（统计、埋点、广告）用 `async`，必须抢在渲染前跑的（polyfill、防主题闪烁）才用同步内联。三个坑：`defer` 和 `async` 对**内联脚本无效**，只对带 `src` 的外部脚本生效；`document.createElement('script')` 动态插入的脚本**默认就是 async**，要保顺序得手动设 `script.async = false`；`@import` 的 CSS 是串行下载，一次往返变两次，生产别用。

顺带把事件分界记住：`DOMContentLoaded` 的条件是 DOM 构建完成且所有 defer 脚本执行完毕，它**不等图片**也不等 async；`load` 要等全部资源回来。

还有一个能加分的点：**预解析器（preload scanner）**。你上场说「遇到 JS 时浏览器线程停止、去下载 JS」，这话只对了一半——主解析器确实停了，但浏览器有一个独立的预解析器会继续往后扫 HTML，提前把后面的 CSS、JS、图片资源发起下载。所以阻塞的是**解析和执行**，不是**下载**。这正是你当时自己改口「不是阻塞加载，是要先同步下载」想表达但没说清的东西。

**怎么记这一整块**：三种 script 的下载阶段其实是一样的（预解析器一上来就全发出去了），差异只在「执行点落在时间轴的哪里」——同步是「立刻执行，解析器原地等」，async 是「下完就执行，解析器被半路打断」，defer 是「排到队尾执行，解析器一路畅通」。CSS 那边配一句：**不挡 DOM，挡画面，还顺手挡住后面的同步 JS**。

延伸能聊的：关键渲染路径、preload / prefetch / preconnect 的区别、HTTP/2 多路复用之后「资源阻塞」讨论的变化。

### 「展示出来」和「可以操作」的区别 ⚠️

上场的第一反应是「这不是同一个时间点吗」，方向摸对了但没说出指标名。

展示出来对应 FCP 和 LCP，可以操作对应 TTI 以及 FID / INP。两者之间的差距来自：JS 还没执行完、SSR 页面 Hydration 还没做完、长任务占着主线程、骨架屏已经画出来但事件还没绑上。SSR 是最典型的例子——FCP 很漂亮，TTI 很难看。

TTI 的判定方式值得记一下：找一个安静窗口（比如 5 秒内没有 long task）且关键网络请求已完成的时刻。优化方向是代码分割、减少主线程工作量、非关键 JS 延后。

Core Web Vitals 三个指标是 LCP、INP、CLS，顺手记住。

### 性能指标全景

上一节是这场真实问到的那个切面，这节把指标摊开。**按一条时间轴记，别按字母表记**。

| 指标 | 测的是什么 | 好的阈值 | 类型 |
|---|---|---|---|
| TTFB | 导航开始到收到第一个字节，网络 + 服务端 | ≤ 800ms | 现场可测 |
| FCP | 第一个**内容**被绘制（文本 / 图片 / SVG / 非空 canvas） | ≤ 1.8s | 现场可测 |
| LCP | 视口内**面积最大**的内容元素渲染完成 | ≤ 2.5s（> 4s 差） | **CWV** |
| TBT | FCP 到 TTI 之间，所有长任务**超出 50ms 的部分**之和 | ≤ 200ms | 仅实验室 |
| TTI | 安静窗口（5s 无长任务 + 在途请求 ≤ 2）回溯到最后一个长任务结束 | ≤ 3.8s | 仅实验室 |
| INP | 全生命周期中接近最差的那次交互，从操作到**下一帧绘制完** | ≤ 200ms（> 500ms 差） | **CWV** |
| CLS | 累积布局偏移 | ≤ 0.1（> 0.25 差） | **CWV** |

两个必须带出的前提：FP 和 FCP 的区别是 FP 可能只是一个背景色，FCP 必须是内容；Core Web Vitals 取的是**真实用户的 75 分位**，不是平均数。

**实验室指标和现场指标的分界**是个加分点：TTI 和 TBT 只能在实验室测，因为「网络安静窗口」在真实用户环境里判定不了。这正是 CWV 选 INP 而不选 TTI 的原因，也是 Lighthouse 10 之后把 TTI 从评分移除、权重转给 TBT 和 CLS 的原因。实验室看 Lighthouse / WebPageTest，现场看 CrUX 或自己用 `web-vitals` 库采。采集底层都是 `PerformanceObserver`，订阅 `largest-contentful-paint`、`layout-shift`、`event` 几个 entry type，TTFB 和 load 从 Navigation Timing API 取——这条直接接到后面「前端监控采集什么」的性能层。

**LCP 测哪个元素、怎么优化**（高频追问）——候选是 `<img>`、SVG 里的 `<image>`、`<video>` 的 poster、带 `url()` 背景图的元素、含文本节点的块级元素。取视口内可见面积最大的那个，加载过程中会变，用户首次交互后停止记录。

优化的标准框架是把 LCP **拆成四段**，说出这个拆法就能看出是真懂：

```
TTFB → 资源加载延迟 → 资源加载时长 → 元素渲染延迟
 ↓          ↓              ↓              ↓
CDN     fetchpriority   WebP/AVIF     去掉阻塞渲染的
缓存    preload         srcset        CSS 和 JS
```

一个高频事故：**LCP 元素被加了 `loading="lazy"`**，首屏图片懒加载是典型的负优化。

**CLS 的成因与优化** —— 四个成因：图片 / iframe 没写尺寸、动态插入的广告或提示条把内容顶下去、Web Font 切换时字形宽度变化、异步数据回填撑开容器。对应手段是图片写死 `width`/`height` 或用 `aspect-ratio`、给动态内容预留占位高度、字体 `font-display: optional` 配预加载、动画只用 `transform` 不改 `top`/`left`。骨架屏能避免 CLS 的**前提是骨架尺寸和真实内容一致**，对不上的骨架屏反而制造偏移。细节：用户输入后 500ms 内的偏移不计入，那被认为是用户预期内的。

**INP 为什么取代 FID** —— FID 两个硬伤：只测第一次交互，且只测「延迟」那一段，不含事件回调的处理时间和渲染时间，所以分数普遍虚高，体感很卡的页面 FID 也可能是绿的。INP 覆盖全生命周期所有交互，并把一次交互拆成三段：**输入延迟**（主线程忙，回调还没开始跑）→ **处理时间**（回调执行）→ **呈现延迟**（到下一帧绘制完）。优化就按这三段下手：拆长任务让出主线程（`scheduler.yield` 或 `setTimeout(0)`）、非紧急更新包进 `startTransition`、减少 DOM 节点数、别在事件回调里做大计算。这条和前面「微任务过多导致 render starvation」是同一个病根。

**怎么记：六问法**。别背指标名，顺着时间轴问六句——**回得快不快**（TTFB）→ **看见东西没有**（FCP）→ **主要内容看全没有**（LCP）→ **能点了没有**（TTI / TBT）→ **点了灵不灵**（INP）→ **整个过程稳不稳**（CLS）。阈值只记 CWV 三个：**LCP 2.5 秒、INP 200 毫秒、CLS 0.1**。

### 性能优化手段

指标是「测什么」，这节是「怎么改」。被问「首屏慢怎么优化」时按这四层说，比零散报名词有条理。

**网络层** — CDN 就近分发、HTTP/2 多路复用或 HTTP/3、`preconnect` 和 `dns-prefetch` 提前建连、Brotli 压缩、缓存策略（HTML no-cache + 静态资源 contenthash 强缓存）。

**资源层** — 代码分割配路由级懒加载、Tree Shaking 砍死代码、图片转 WebP / AVIF 加 `srcset` 响应式、非首屏图片懒加载（首屏绝不加）、字体子集化加 `font-display: swap`、第三方脚本 `async` 并评估是否必要。

**渲染层** — 关键 CSS 内联、非关键 CSS 异步加载、JS 一律 `defer`、SSR / SSG 提前产出 HTML、流式渲染让首屏更早可见、首屏接口收敛（按模块筛选或上 BFF）。

**运行时层** — 长任务拆分让出主线程、长列表虚拟滚动、重计算搬进 Web Worker、高频事件防抖节流、动画只用 `transform` 和 `opacity` 走合成线程、`content-visibility` 跳过屏外渲染。

排查的固定套路：Performance 面板看 Waterfall 哪一段长、看 Long Task 分布，Lighthouse 跑一遍拿 Opportunities，`webpack-bundle-analyzer` 看包体积构成。**先测再改，别凭感觉优化**——这句话本身就是答题时的加分项。

你有现成抓手：订单详情页 20 个模块那题就是首屏收敛加懒加载的真实案例，被问优化手段时直接拿它举例，比背清单可信得多。

### 强缓存与协商缓存 ⚠️

上场把 `max-age` 说到协商缓存里去了，`no-cache` 和 `no-store` 也没分清。

强缓存**不发请求**，命中时响应显示 200（from memory cache / from disk cache），控制头是 `Cache-Control: max-age` 或老的 `Expires`。
协商缓存**会发请求**，带上验证头，服务端没变就回 304 Not Modified，浏览器用本地副本，控制头是 `ETag` 和 `Last-Modified`。优先级是先看强缓存，过期了才走协商。

两个必须理顺的：`no-cache` 的意思是**可以存，但每次使用前必须向服务器验证**，通常配 ETag，它不等于「协商缓存」这个概念本身；`no-store` 才是完全不缓存。

延伸：ETag 在多机或 CDN 场景可能因为 inode 不同而失效，所以更稳的做法是靠文件名 contenthash；另外还有 `Vary` 头和 Service Worker 的缓存策略。

### 发版后用户一直加载旧资源 ⚠️

上场只答了用户侧——无痕窗口、清缓存、要用户 ID 查日志看命中哪个镜像。这些不算错，但缺了工程视角，显得像客服而不是开发。

工程侧才是根治：JS/CSS 文件名带 **contenthash**，一次新部署就是一批新 URL，物理上不可能命中旧缓存；HTML 入口**不做长期强缓存**（用 no-cache 让它每次校验）；必要时刷 CDN。用 query 参数带版本号是下位替代，不如 hash 文件名。

排查侧按这个顺序：看 Response Headers 的 `Cache-Control`、`Age`、`X-Cache`（判断是浏览器缓存还是 CDN 缓存）→ 比对实际加载的 `app.xxx.js` hash 和最新发布版本 → 检查 Service Worker 是不是在 serve 旧 cache → 排除浏览器扩展和公司代理。

用户侧兜底才是硬刷新和清站点数据。

一句最佳实践收口：**HTML 用 no-cache，JS/CSS 用 contenthash 强缓存一年**。另外如果监控里采集了 buildId，直接就能定位用户加载的是哪个版本，不用靠猜。

## 二、React

### 什么情况下会触发重新渲染 ⚠️

上场第一反应答到 useEffect 依赖上去了，被追问「还有其他方式吗」时答了「加 key 吗」，子组件 state 那问也是先说不会、后来才改口。

五条触发条件：自身的 useState / useReducer 被 dispatch；父组件 re-render（子组件默认跟着 render）；订阅的 Context 值变化；类组件 forceUpdate，或父组件改了 key 导致 remount；父组件传入的 props 引用变化。

三个边界要说清：

- useEffect 依赖变化只让 effect 重跑，**不是** render 的原因，这两件事别混
- 子组件自身 setState 只 re-render 它自己那棵子树，**不会**带动父组件或兄弟组件（除非它通过回调改了父组件的 state）
- key 变化不是 re-render，是 unmount + remount，state 会被重置

顺带记住：re-render 不等于 remount，也不等于 DOM 更新，diff 之后 DOM 可能完全复用。React 18 会自动批处理多次 setState 合成一次 render，开发环境 StrictMode 下组件会故意 double render。

### setState 之后 render 里没用到这个 state ❌

上场答的是「页面没用到这个值就不会重新渲染」——这是错的。

正确口径：setState 一定会 schedule 该组件 re-render，组件函数重新执行，**和 render 里是否读取这个 state 无关**。React 不做 Vue 那种细粒度依赖追踪，它的更新粒度是组件，不是表达式。

唯一的例外是 bail out：新旧 state 用 `Object.is` 比较相等时，React 可以跳过本次更新。

所以性能优化的手段是 `React.memo`、拆分组件、状态下沉到用得到的地方，而不是指望「反正 render 里没读到就不会渲染」。

### 「组件重新渲染」和「页面重新渲染」不是一回事 ⚠️

上场这里有个信号很明确：你被问「触发 setState 时整个组件会重新渲染吗」，反问了一句「这个重新渲染指的是页面的重新渲染是吗」，面试官答「对」。**这个反问暴露的是三层概念混在一起了**，而面试官顺势用它验证你的心智模型。

分清三层：

1. **Render 阶段** — 组件函数重新执行，产出新的 React Element 树，然后和上一棵做 reconcile（diff）。这一层是纯计算，不碰 DOM，可被 Concurrent 模式中断。
2. **Commit 阶段** — React 把 diff 出来的差异真正写进 DOM。如果 JSX 输出和上次完全一致，这一层可能什么都不做。
3. **浏览器绘制** — DOM 变了之后浏览器才走 Layout / Paint / Composite，对应回流和重绘。

所以「组件 re-render」是第 1 层，「页面重新渲染」是第 3 层，中间隔着两道可能什么都不发生的关卡。完整口径是：setState 必然触发第 1 层；第 2 层取决于 diff 结果；第 3 层取决于 DOM 是否真变、以及变的是布局属性（回流）还是纯绘制属性（重绘）。

**一个必须防住的歧义**：Render 阶段产出的**不是**浏览器那棵 Render Tree。组件函数返回的是 React Element（`{ type, props, key }` 形式的普通 JS 对象），React 拿它和当前 Fiber 树比对，构建出新的 Fiber 树并在节点上打副作用标记（插入 / 更新 / 删除），全程一个 DOM 节点都没碰。浏览器的 **Render Tree 是 DOM 加 CSSOM 合成的**，和 React 的产物完全是两回事，只是名字撞了。完整词链：

```
React Render 阶段   组件函数 → React Element 树 → Fiber 树（打标记）
React Commit 阶段   按标记写入真实 DOM
浏览器              DOM + CSSOM → Render Tree → Layout → Paint → Composite
```

连带记住 `render` 这个词在前端的**三个含义**，答题时不区分很容易被认为概念混乱：**React 的 render** 是「执行组件函数算出要什么」，**浏览器的 rendering** 是「从 HTML 到像素的整条流水线」，**paint** 才是「真正画像素」。

这条链路还能顺势接到性能题：`transform` 和 `opacity` 只触发 Composite，不走 Layout 和 Paint，所以动画优先用它们。再往下一层是**合成线程**——这类动画跑在合成线程上，不占主线程，所以主线程被长任务占死时它们依然流畅。

### useMemo / useCallback / React.memo ❌

上场完全混了，还答过 useCallback 返回 Promise，被追问「它们返回的东西是一个东西吗」时也没兜住。这是本场最严重的失分点。

| | 缓存什么 | 返回什么 | 用在哪 |
|---|---|---|---|
| `useMemo(fn, deps)` | 函数的**执行结果** | 任意类型：对象、数组、数字 | 昂贵计算；给下游一个稳定的引用 |
| `useCallback(fn, deps)` | 函数的**引用** | 函数本身 | 传给 memo 子组件的回调 |
| `React.memo(Cmp)` | 组件的 render 结果 | 包装后的组件 | props 浅相等就跳过 render |

一条等式帮你彻底记牢：`useCallback(fn, deps)` 就是 `useMemo(() => fn, deps)`。

经典场景是父组件一个输入框加一个 memo 包的列表：父组件每次输入都 re-render，如果回调是行内箭头函数，每次引用都新的，memo 的浅比较必然失败，等于白包——这时候才需要 useCallback。

再留一句「滥用有害」：memo 化本身有 deps 比较的成本，普通组件不必全包。React 19 的 Compiler 能自动做这件事，手写 memo 化的必要性在下降。

（更完整的 Hooks 体系见本节末尾「Hooks 系统梳理」）

### 请求竞态 ⚠️

场景是输入框或筛选项连续发请求，B 后发但先回，A 先发后回，结果把 B 的结果覆盖了。

上场答的「保存当前筛选条件，请求回来跟当前选中比对」是可行方案，但漏掉了最标准的答案，而且先绕了一圈防抖。按优先级应该是：

1. **AbortController** — 发新请求前 abort 旧的，最干净，从源头消灭过期响应
2. **递增 requestId** — 每次请求拿一个自增 id，回来时对不上最新 id 就丢弃
3. **防抖节流** — 只是减少请求数量，**不解决**结果正确性，不能单独当答案
4. **React Query / SWR** — queryKey 变化时自动忽略旧结果
5. 后端层面做幂等，或按 session 只返回最新

```javascript
// AbortController
useEffect(() => {
  const ctrl = new AbortController();
  fetch(url, { signal: ctrl.signal })
    .then(r => r.json())
    .then(setData)
    .catch(e => { if (e.name !== 'AbortError') throw e; });
  return () => ctrl.abort();
}, [keyword]);

// requestId
let latestId = 0;
async function load(keyword) {
  const id = ++latestId;
  const data = await fetch(`/api?q=${keyword}`).then(r => r.json());
  if (id !== latestId) return;   // 过期响应直接丢弃
  setData(data);
}
```

配套细节：loading 态也要只对最新请求生效，否则会出现请求都回来了 loading 还在转；防抖和 abort 可以组合使用；订单详情切换 ID 也是同一类竞态。

上场有个动作是对的——你先反问了「这两个请求必须同时发吗」，先确认约束再给方案，保留这个习惯。

### Hooks 系统梳理

前面几节是这场真实问到的切面，这节把 Hooks 摊开。**先记底层机制，所有规则和坑都是从它推出来的。**

#### 为什么会有「Hooks 规则」

Hooks 的 state 存在 Fiber 节点的 `memoizedState` 上，是一条**单向链表**——不是按名字存的键值对，是按**调用顺序**串起来的节点。每次组件函数重新执行，React 从链表头开始，第一次 `useState` 取第一个节点，第二次取第二个，依此类推。

这一句解释了所有规则：**不能写在条件语句、循环、嵌套函数里**，因为某次 render 少调用一个 Hook，后面所有 Hook 读到的就全是别人的 state，错位且无法恢复。也解释了为什么 `useState` 不需要名字——位置就是它的身份。`eslint-plugin-react-hooks` 的 rules-of-hooks 查的就是这件事。

被追问「为什么不能写在条件里」时，答「**链表按顺序读取，错位会读到别的 state**」，比答「React 规定的」高好几个层次。

#### 状态类：useState

`useState` 本质是 `useReducer` 的特例。三个细节：

**函数式更新** — `setCount(c => c + 1)` 拿到的是最新值，`setCount(count + 1)` 用的是当前闭包里的快照。连续调用多次时差异暴露，这也是闭包陷阱的解法之一。

**惰性初始化** — `useState(expensiveInit())` 会**每次 render 都执行**（只是返回值被丢弃），正确写法是 `useState(() => expensiveInit())`。常见性能暗坑。

**bail out** — 新旧 state `Object.is` 相等时可跳过更新，但有时仍会多渲染一次才稳定。

#### 状态类：useReducer

```jsx
function reducer(state, action) {
  switch (action.type) {
    case 'add':   return { ...state, count: state.count + 1 };
    case 'reset': return initialState;
    default:      throw new Error('unknown action');
  }
}

const [state, dispatch] = useReducer(reducer, initialState);
// 第三个参数做惰性初始化：init(initialArg) 只在首次调用
const [state, dispatch] = useReducer(reducer, initialArg, init);
```

reducer 必须是**纯函数**，不能发请求、不能改外部变量——StrictMode 下 React 会故意调两次来帮你发现不纯的实现。

最值得记的一条：**`dispatch` 的引用是 React 保证稳定的**，永远不变。所以传给 `React.memo` 子组件不需要 `useCallback`（`setState` 返回的 setter 同理）。这条说得出来说明真的用过。

和 `useState` 的分界：状态字段之间有约束关系（比如 `loading` / `data` / `error` 三者互斥），或者同一个动作要同时改多个字段，就该换。额外好处是把「怎么变」集中到纯函数里，**`reducer` 可以脱离 React 单独做单测**——这是个很好的加分角度。`useReducer` 配 `Context` 就是轻量版 Redux，小应用不用引状态库。

#### 副作用类：三个 Effect 的执行顺序

除了 `useEffect` 和 `useLayoutEffect`，还有第三个 `useInsertionEffect`。完整时序是：

```
Render 阶段（纯计算，可中断）
  ↓
Commit 阶段
  ├─ before mutation  →  useInsertionEffect   注入 <style>，此时读不到新 DOM
  ├─ mutation         →  React 真正改 DOM
  └─ layout           →  useLayoutEffect      同步执行，可读布局、可同步改
  ↓
浏览器绘制
  ↓
useEffect（passive effect，异步）
```

`useInsertionEffect` 专为 CSS-in-JS 库设计——styled-components 这类库要在浏览器读布局**之前**把 `<style>` 插进去，否则触发额外的 layout 计算。业务代码几乎用不到，但知道它为什么排在 `useLayoutEffect` 前面，能体现对 commit 阶段的理解是完整的。

这张图直接接第一节「组件 re-render 和页面 re-render 不是一回事」——那里的 Render / Commit / 浏览器绘制三层正是这张图的骨架。

#### 副作用类：useEffect 的心智模型要先换掉

**最重要的一句：useEffect 不是生命周期函数，它是「把 React 状态同步到外部系统」的工具。** 官方刻意回避「componentDidMount 的替代品」这个说法，因为用生命周期思维写 effect 会写出一堆问题。外部系统指 DOM 事件监听、定时器、网络连接、第三方库实例、浏览器 API——凡是 React 管不到的东西。

**执行时机**和 useLayoutEffect 对比着记：

| | 执行时机 | 阻塞绘制 | 用在哪 |
|---|---|---|---|
| `useEffect` | commit 之后、**浏览器绘制之后**，异步 | 否 | 绝大多数场景 |
| `useLayoutEffect` | commit 之后、**绘制之前**，同步 | 是 | 读 DOM 布局并同步改，避免闪烁 |

典型的 `useLayoutEffect` 场景是 tooltip 定位：先读目标元素位置再决定自己摆哪，用 `useEffect` 的话用户会先看到它出现在错误位置再跳过去。代价是阻塞绘制，滥用拖慢首屏。

**依赖数组**三种形态：不传，每次 render 后都执行；`[]`，只在 mount 后执行一次；`[a, b]`，a 或 b 用 `Object.is` 比较变化时执行。

**清理函数**调用时机有两处：下一次 effect 执行**之前**，以及组件卸载时。用来取消订阅、`clearTimeout`、abort 请求、移除事件监听。开发环境 StrictMode 下 React 故意走一遍 mount → unmount → mount，专门暴露没写清理函数的 effect——这是设计不是 bug。

#### 副作用类：useEffect 闭包陷阱（必考）

```jsx
const [count, setCount] = useState(0);

useEffect(() => {
  const id = setInterval(() => console.log(count), 1000);
  return () => clearInterval(id);
}, []);   // 永远打印 0
```

原因是 effect 函数捕获的是**那一次 render 时的 count 快照**。依赖为空，effect 不重建，闭包永远停在首次 render 的世界里。

三种解法，取舍不同：把 `count` 加进依赖（每次变化销毁重建 interval，最直接但有开销）；改用函数式更新 `setCount(c => c + 1)`（不需要读外部值，最优雅）；用 `useRef` 存最新值，effect 里读 `ref.current`（适合「要读最新值但不想重建 effect」，比如事件回调）。

#### 副作用类：你可能不需要 useEffect

React 官方专门写了一整篇文档的主题，面试问到的频率在上升：

**派生状态** — 能从 props 或现有 state 算出来的，直接在 render 里算，别用 effect 加 setState。那会多触发一次渲染，中间还有一帧显示旧值。算得贵就包 `useMemo`。

**响应用户事件** — 点击要做的事写在事件处理函数里。用 effect 监听 state 变化来间接响应，因果关系难追，而且「同样的值再点一次」不触发。

**重置状态** — 切换用户要清空表单，用 `key` 让组件 remount，别用 effect 手动清。

**数据请求** — 手写 effect 要自己处理竞态、loading、错误、缓存、重复请求（见上面「请求竞态」节）。现在推荐 React Query / SWR，或 RSC。

#### 副作用类：依赖数组的坑

对象和函数作为依赖时，每次 render 都是新引用，`Object.is` 必然不等，effect 无限执行。解法是用 `useCallback` / `useMemo` 稳定引用，或者把对象拆成原始值当依赖（`[user.id, user.name]` 而不是 `[user]`），后者往往更简单。

`exhaustive-deps` 这条 lint 警告别无脑关。它报警通常说明 effect 职责不清——真正的解法是拆分 effect 或改用 ref，而不是删依赖。

#### 性能类：memo 两件套

`useMemo` 和 `useCallback` **不是语义保证，是性能提示**——React 某些情况下可以丢弃缓存重算，不能依赖它们保证「这个值一定不变」。真正需要它们的只有三种情况：传给 `memo` 子组件、作为其他 Hook 的依赖、昂贵计算。

#### 性能类：useTransition

```jsx
const [isPending, startTransition] = useTransition();

function handleChange(e) {
  setQuery(e.target.value);              // 紧急更新：输入框必须立即响应
  startTransition(() => {
    setResults(search(e.target.value));  // 非紧急：可被打断
  });
}
```

机制是被 `startTransition` 包裹的 `setState` 被标记为**低优先级**。React 渲染这部分时如果来了更紧急的更新（用户又敲了一个字），会**丢弃当前渲染重新开始**。所以输入框永远跟手，列表尽力而为。`isPending` 用来显示过渡态（列表变灰、细进度条）。

**和防抖的区别**是爱问的点：防抖是「**延迟开始**」，用户停手 300ms 才动；transition 是「**立即开始但可被打断**」，CPU 有空闲就立刻完成。所以快设备上 transition 感觉是瞬时的，防抖永远有那 300ms 固定延迟。两者可组合——防抖减请求数，transition 保证渲染不卡手。

一个限制：`startTransition` 回调里只能放**同步**的 `setState`，`await` 之后的更新不被标记（React 19 支持异步 transition）。

#### 性能类：useDeferredValue

```jsx
const deferredQuery = useDeferredValue(query);
const results = useMemo(() => search(deferredQuery), [deferredQuery]);

<input value={query} onChange={e => setQuery(e.target.value)} />
<ResultList items={results} />   {/* ResultList 必须是 memo 的 */}
```

它返回一个**滞后版本**的值：紧急更新时先拿旧值渲染一遍，再在后台用新值重渲染。

**和 `useTransition` 的分工**：`useTransition` 要求你能改到 `setState` 的调用处；`useDeferredValue` 用于**只拿得到值、拿不到 setter** 的场景，最典型是值从 props 传进来。

**必须知道的坑**：`useDeferredValue` 只有配合 `React.memo` 才有效。子组件没被 memo 包，父组件重渲染时它照样跟着渲染，延迟就白费了。踩过的人才答得出来。

这两个直接对应第一节性能那块的 INP 优化——解决的正是「主线程被渲染占住导致交互没响应」。

#### useContext 的性能坑

value 变化时**所有消费者都 re-render，而且 `React.memo` 挡不住**。两个必知的坑：`value` 写成对象字面量的话每次 Provider render 都是新引用，所有消费者跟着重渲染，要用 `useMemo` 包；频繁变化的值和稳定的值要拆成两个 Context，否则一个变动牵连全部。

#### 逃生舱类：先理解「逃生舱」的定义

官方文档里 **`useEffect` 其实也被归在 Escape Hatches 章节**。逃生舱的定义不是「冷门」，而是「**跳出 React 的声明式数据流去直接操作外部世界**」。按这个定义 `useEffect` 确实是。

#### 逃生舱类：useRef

一是存 DOM 引用，二是存**变化时不触发渲染的可变值**。`ref.current` 怎么改都不 re-render，这既是价值也是风险。

和 `useState` 的取舍很好判断：**这个值要显示在 UI 上吗**？要，用 `useState`；只是暂存（定时器 id、上一次的值、最新回调、是否首次渲染的标记），用 `useRef`。

#### 逃生舱类：useImperativeHandle

```jsx
const FormInput = forwardRef((props, ref) => {
  const inputRef = useRef(null);
  useImperativeHandle(ref, () => ({
    focus:    () => inputRef.current.focus(),
    validate: () => inputRef.current.value.length > 0,
  }), []);
  return <input ref={inputRef} />;
});

// 父组件只能调到这两个方法，碰不到 DOM 节点
formRef.current.validate();
```

用途是**收窄暴露面**：不把整个 DOM 节点交给父组件，只暴露设计好的几个方法。典型场景是表单暴露 `validate()` / `reset()`、弹窗暴露 `open()` / `close()`、播放器暴露 `play()` / `pause()`。

为什么算逃生舱：它是**命令式**的，父组件在「命令」子组件做事，而不是通过 props 描述状态。判断标准很明确——**能用 props 表达的状态就别用它**，只有天然是「动作」而非「状态」的东西（聚焦、播放、滚动到某处）才适合。

React 19 之后 `ref` 可以直接作为普通 prop 传递，`forwardRef` 不再必需。

#### 逃生舱类：useSyncExternalStore

```jsx
const value = useSyncExternalStore(
  subscribe,          // (onChange) => unsubscribe
  getSnapshot,        // () => 当前值
  getServerSnapshot   // SSR 时用的初始值
);
```

**它解决 tearing（撕裂）问题**，这个概念讲清楚很加分。并发渲染下，React 渲染一棵树的过程**可以被中断**。假设组件 A 和 B 都读同一个外部 store，渲染完 A 后被打断，这期间 store 变了，恢复后渲染 B——同一次渲染里 A 显示旧值、B 显示新值，界面自相矛盾。这就是撕裂。

`useSyncExternalStore` 强制同步读取并在值变化时放弃当前渲染重来，保证一次渲染读到一致的快照。Redux、Zustand、Jotai 内部都用它适配 React 18。

自己写的典型场景是订阅浏览器状态：

```jsx
function useOnlineStatus() {
  return useSyncExternalStore(
    cb => {
      window.addEventListener('online', cb);
      window.addEventListener('offline', cb);
      return () => {
        window.removeEventListener('online', cb);
        window.removeEventListener('offline', cb);
      };
    },
    () => navigator.onLine,
    () => true,
  );
}
```

必踩的坑：**`getSnapshot` 必须返回能用 `Object.is` 比较的稳定值**。写成 `() => ({ x: store.x })` 每次返回新对象，React 认为值一直在变，直接无限循环报错。要么返回原始值，要么在 store 侧缓存对象。

#### 其他：useId 与 React 19 新增

`useId` 生成服务端和客户端一致的唯一 id，用于无障碍属性关联，SSR 必需。

React 19 新增的知道名字和用途即可：`use()`（可以在条件语句里调用，读 Promise 或 Context，打破了 Hooks 规则）、`useOptimistic`（乐观更新）、`useActionState` 和 `useFormStatus`（表单提交状态）。

#### 自定义 Hook

本质就是**函数复用**，没有魔法。关键认知：两个组件用同一个自定义 Hook，它们的 state **完全独立**，复用的是逻辑不是状态。命名必须 `use` 开头，否则 lint 识别不出来，也就无法校验 Hooks 规则。

#### 选型速查

| 你的需求 | 用什么 |
|---|---|
| 值要显示在 UI 上 | `useState` |
| 多个字段互相约束、动作驱动 | `useReducer` |
| 存值但不想触发渲染 | `useRef` |
| 同步外部系统（订阅、定时器、连接） | `useEffect` |
| 读 DOM 布局并同步修改，避免闪烁 | `useLayoutEffect` |
| 注入样式（CSS-in-JS 库作者） | `useInsertionEffect` |
| 某次更新不紧急，能改到 setState | `useTransition` |
| 某个值不紧急，只拿得到值 | `useDeferredValue`（必须配 `memo`） |
| 向父组件暴露动作而非状态 | `useImperativeHandle` |
| 订阅 React 之外的数据源 | `useSyncExternalStore` |

#### 怎么记：四类对应数据流的四个环节

**状态类**（`useState` / `useReducer`）负责「数据从哪来」；**副作用类**（`useEffect` / `useLayoutEffect` / `useInsertionEffect`）负责「数据同步到外部」；**性能类**（`useMemo` / `useCallback` / `useTransition` / `useDeferredValue`）负责「渲染什么时候做、做不做」；**逃生舱类**（`useRef` / `useImperativeHandle` / `useSyncExternalStore`）负责「React 管不到的地方怎么办」。

记住这个映射，遇到陌生的新 Hook 也能自己归类——`useOptimistic` 一看就是状态类，`useFormStatus` 是状态类的读取侧。

四类之外记一条总纲：**所有 Hook 的规则和坑，根源都是「链表按顺序读」和「闭包捕获快照」这两件事。** 顺序问题产生了 Hooks 规则，快照问题产生了闭包陷阱和依赖数组。

## 三、工程化

### Webpack 代码分割与拆包判断 ⚠️

上场在被问「Webpack 有了解过吗」时答了「知道一些打包的东西」，结果面试官顺势深挖代码分割，答得比较散，靠猜「import 比较多的相关性大」。

分割方式五种：多入口（多个 entry 出多个 chunk）；**动态 `import()`**，语法级触发，Webpack 自动拆成 async chunk；**SplitChunksPlugin**，按 cacheGroups 提取 vendors 和 common；externals 排除依赖、运行时从 CDN 取；Module Federation 运行时跨应用加载。

拆包的判断逻辑不是「谁 import 得多」，而是：从 entry 出发构建**模块依赖图** → 某模块被至少 `minChunks` 个 chunk 共享 → 体积达到 `minSize` → 命中 cacheGroups 规则（比如路径含 `node_modules` 就归到 vendors）。

一句权衡：拆得过细会导致 HTTP 请求数暴涨，得平衡。分析工具是 `webpack-bundle-analyzer`。Vite 生产环境走 Rollup，思路一样，靠动态 import 加 manualChunks。

你有个现成抓手别浪费——做精准测试插桩时改过 webpack 配置，在解析阶段命中目标包插入规则，可以顺势聊 loader 和 plugin 的钩子时机。以后被问「有了解吗」，要么给这种具体抓手，要么直接说清边界，别答「知道一些」，那等于主动递梯子。

### React 应用的打包

上一节是拆包的通用判断逻辑，这节按**面试官实际会问的问题**组织，比列知识点好用。

#### 「你们项目怎么做代码分割的？」

路由级 `React.lazy` 配 `Suspense` 是基本盘，动态 `import()` 触发 Webpack 自动拆 async chunk。加一句就拉开差距：`lazy` 只在渲染到那一刻才发请求，用户会看到一次 loading，所以要在鼠标 hover 导航链接或路由空闲时**提前调一次 import 函数**预热 chunk。

#### 「打包产物怎么拆的？为什么这么拆？」

核心答案是**按变更频率分层，不是按体积分**：

```js
cacheGroups: {
  framework: { test: /node_modules[\\/](react|react-dom|scheduler)/, priority: 40 },  // 几乎不变
  lib:       { test: /node_modules/, priority: 30 },                                   // 季度级
  common:    { minChunks: 2, priority: 20, reuseExistingChunk: true },                 // 周级
}
```

目的是让变动最少的那部分在用户浏览器里长期命中缓存。

#### 「改一行业务代码，为什么所有文件 hash 都变了？」

最能区分水平的一题。原因是 Webpack 的 runtime（模块映射表）默认打进 entry chunk，模块 id 一变 runtime 跟着变，**所有 chunk 的 contenthash 连锁失效**，用户长期缓存一次性作废。

```js
runtimeChunk: 'single',        // runtime 抽成独立文件
moduleIds: 'deterministic',    // 模块 id 由路径哈希决定，不用递增数字
```

配套记清三种 hash：`hash` 是整次构建一个值，`chunkhash` 按 chunk 算（CSS 和 JS 会互相牵连），**只有 `contenthash` 适合长期缓存**。这条直接接第一节「HTML no-cache + JS/CSS contenthash 强缓存一年」——那边讲缓存头，这边讲构建侧怎么产出这些文件名。

#### 「生产包为什么比开发包小一半？」

`DefinePlugin` 把 `process.env.NODE_ENV` 替换成字符串字面量 `'production'`，React 源码里大量 `if (process.env.NODE_ENV !== 'production') { warning(...) }` 条件恒假，Terser 整块 DCE 掉——开发警告、PropTypes 校验、调试辅助全部消失。忘了设 `mode` 导致生产包带开发版 React，是真实会发生的事故。

这和 Tree Shaking 是同一个机制家族：**Webpack 创造可删条件，Terser 执行删除**。

#### 「包太大怎么优化？」

先 `webpack-bundle-analyzer` 看构成，再对照常见元凶：moment 的全量 locale（换 dayjs 或 `IgnorePlugin`）、lodash 整体导入（换 `lodash-es` 或精确到 `lodash/debounce`）、core-js polyfill 全量引入（`useBuiltIns: 'usage'` 配准确 targets）、echarts 和图标库按需注册、重复依赖用 `pnpm dedupe` 收敛。

工程上加 `size-limit` 做 CI 门禁，超阈值卡住 MR——这和你做覆盖率门禁是同一类思路，可以并提。

#### 「构建太慢怎么办？」

收益最大的是 Webpack 5 的 `cache: { type: 'filesystem' }` 持久化缓存。再往上把 babel-loader 换成 `swc-loader` 或 `esbuild-loader`，或直接换 Vite（开发走 esbuild 预构建加原生 ESM，生产走 Rollup）。Rspack、Turbopack 知道名字和定位即可。

#### 两个可能的追问

**JSX transform** — React 17 引入 automatic runtime，产物从 `React.createElement` 变成从 `react/jsx-runtime` 导入的 `jsx()`，所以现在不用在文件顶部写 `import React`。配置在 `@babel/preset-react` 的 `runtime: 'automatic'`。

**SSR 是两套构建配置** — client bundle 正常打，server bundle 用 `target: 'node'` 并把 node_modules 设成 externals（服务端直接 require，不打进去），两端产物必须对应否则 hydration mismatch。

### 前端监控采集什么

这题答得不错，错误、接口异常、白屏、LCP/FCP、埋点、多语言漏翻都提到了。按层次整理一遍更有条理：

**错误层** — JS runtime error、unhandled rejection、静态资源 404、接口 5xx 和业务错误码、接口超时。
**性能层** — FP / FCP / LCP / CLS / INP / TTFB、长任务、慢接口。
**稳定性层** — 白屏检测（按根节点元素数采样判断）、崩溃率。
**业务层** — 埋点、漏斗、PV/UV。
**环境层** — UA、应用版本号、buildId、用户 ID、当前路由。这层上场没提，但它是排查问题的关键，尤其 buildId 直接解决「用户加载的是哪个版本」。
**质量层** — i18n 漏翻（你们出海项目切语言后页面残留中文的检测）、核心链路可用性。

延伸能聊：错误上报要采样、要用 source map 还原堆栈、要和 release 关联；RUM（真实用户监控）和合成监控的区别。

### 埋点会不会影响业务性能

你的回答里「在 webpack 里单独拆包、页面出来之后再加载埋点」这个思路很好，答案方向是对的。补完整就是：

会影响，影响在四处——包体积变大、主线程多了执行、多了网络请求、极端情况下拖累 INP。

优化手段五个：埋点 SDK **异步加载**、单独拆 chunk；上报**批量合并**，配 `requestIdleCallback` 在空闲时发；按**采样率**上报（比如 10% 用户）；页面卸载时用 `navigator.sendBeacon`，避免 unload 里发请求被浏览器丢掉；核心路径上绝不做同步埋点。

再往外一层是埋点治理：schema 统一、防重复上报、隐私合规和字段脱敏。

### Monorepo 的取舍

这题你讲得实在，甚至代价部分比优势讲得更好，保持。补一点工具链层面的优势就完整了。

优势：代码共享（你们的跨端 Model 层、utils、组件库）、**原子提交**（跨包改动放一个 PR，不用多仓库对版本）、统一依赖版本和 lint / test / CI、跨项目重构容易。

代价：CI 变慢，需要 affected detection 或 Turborepo 这类缓存；发布流程复杂（你们是 build 时抽出共享 Model 加各端代码，再 push 到各端独立发布仓库）；权限边界模糊。

工具栈：pnpm workspace 配 `--filter`，changesets 管版本。选型原则是团队耦合度高、需要频繁跨包改动就用 monorepo。

## 四、藏在项目和场景题里的八股

这几个上场是以项目追问的形式出现的，但考的都是通用知识，换个公司可能直接当八股问。

### 代码覆盖率与插桩原理（问精准测试时深挖的）

原理是构建阶段的 AST 改写：`babel-plugin-istanbul` 这类插件在每一行语句、每个分支处注入计数器，运行时页面执行到哪里就累加哪个计数器，最后把 hit 信息上报，生成覆盖率报告。

覆盖率有四种口径，别只会说「行覆盖」：statement（语句）、branch（分支）、function（函数）、line（行）。**分支覆盖**是最容易漏的，常见漏点是 `if/else` 只走了一半、可选链 `?.` 短路、三元表达式只命中一侧。

**增量覆盖率**的定义是：本次 diff 涉及的语句里被执行到的比例。它和全量覆盖率的区别很关键——老项目存量代码覆盖率注定很低，全量数字没有行动指导性,增量能直接指向「你这次改的哪几行没点到」。

代价：插桩会增大 bundle、略微拉低运行性能，所以只在测试环境开启。

和单测的边界要说清：单测是在 Node / JSDOM 环境跑用例，验证的是**断言正确性**；插桩覆盖是在真实浏览器里统计**真实操作路径**执行到了哪些代码，它不验证结果对不对。所以「覆盖率高不等于没 bug」——只说明代码被执行过。

### 测试分层

被问到「有没有做 E2E 或者用 Agent 做页面 E2E」时，最好的答法是先摆出分层再说现状：

| 层级 | 代表方案 | 强项 | 短板 |
|---|---|---|---|
| 单元测试 | Jest / Vitest | 快、稳定、可断言 | 前端 UI 逻辑难 mock |
| 插桩覆盖 | Istanbul + diff | 贴近真实操作、增量可视 | 不验证结果正确性 |
| E2E | Playwright / Cypress | 端到端真实 | flaky、维护贵、CI 慢 |
| AI 生成用例 | Agent + 用例库 | 降低编写成本 | 输出不稳定，需人工审核 |

E2E 推不开的通用原因有三个：选择器脆弱、环境和数据依赖强、用例 flaky。对应的缓解手段是 Page Object 模式、测试数据隔离、retry 策略。真要推的话，选一到两条核心链路加稳定选择器，纳入 MR 门禁，而不是一上来铺全量。

AI 生成用例目前的合理定位是生成初版和补边界，不适合无人值守直接上线。

### 大型详情页的模块化与按需加载（订单 20 模块那题）

这题表面是架构题，里面全是通用知识点：

**首屏收敛** — 首屏只请求必要模块，接口支持按模块名筛选（`?modules=resource,traveler`），或者上 BFF 做聚合。
**非首屏懒加载** — 触发方式用 `IntersectionObserver` 观察占位元素，比监听 scroll 更稳，也别用定时器。
**代码层面** — 模块组件用动态 `import()`，各自独立 chunk，React 里配 `React.lazy` 加 `Suspense`。
**容错隔离** — 每个模块套 Error Boundary，一个模块挂掉不能带崩整页。这点上场没提到，是明显的加分项。
**避免布局跳动** — 模块级骨架屏，别让内容回填时页面往下窜（对应 CLS 指标）。
**可扩展** — 用模块注册表把模块名映射到组件，新模块接入只改配置；注册表上还能挂 `visible` 做权限控制（供应商只能看部分模块）。

选型对比也要会说：20 个模块同团队维护，模块化加懒加载就够了，不需要 qiankun 或 Module Federation；只有跨团队独立发布才值得上微前端。

### 模块间通信的方案选型

上场答的是「更新组件 state」加「项目里有 EventBus」，有真实例子但没成体系。按场景归纳：

- 父子、简单兄弟：props 加回调
- 跨多层：Context 或全局 Store
- 一对多、需要解耦：EventBus 或自定义事件
- 复杂联动：状态机（XState）或单向数据流
- 服务端状态：React Query / SWR，自带缓存和失效

你项目里那个例子正好是 EventBus 的典型适用场景：主接口只给了 clientId，往下翻要展示姓名身份证时单独调出行人接口，回来后按 ID 匹配，通知前面的模块刷新。

但要主动说出 EventBus 的代价：链路难追踪、难调试，而且**监听必须注销**否则内存泄漏。判断标准是——强一致的状态放 Store（有 devtools 可追踪），EventBus 只用于 fire-and-forget 的通知。

### 状态管理选型与 useEffect 的边界（问「UI 状态管理用什么」时）

你们的方案是 Rematch 加内部的跨端 Model 层。讲的时候要点出**为什么**，而不只是叫什么名字。

Rematch 是 Redux 之上的封装，内置 model、reducers、effects，主要价值是消掉 Redux 的样板代码。你们的 Model 层是跨端共享的业务逻辑层，PC 和 H5 的 Controller 分别注入同一个 Model 并挂上下文，View 层只负责 UI 和 dispatch——本质是同构场景下的分层：View / Model / Service。

「为什么少用 useEffect」这个点答得好，但理由要说透：副作用集中放在 Model 的 effects 里统一管理，避免 PC 和 H5 各写一套 effect 导致行为不一致。组件内的 useEffect 只留给纯 UI 副作用，比如监听 resize、局部展开收起。

可能的追问「为什么不用 Zustand / Jotai / Redux Toolkit」：答历史生态加内部 Model 层沉淀加双端同构需求，然后把话头引回**分层设计**——面试官真正想听的是你能不能讲清分层，不是你用了哪个库。

## 五、每个考点的下一层追问

字节的习惯是顺着一个点往下挖三层，上场很多题之所以只挖了一层，是因为你在第一层就卡住了，面试官没必要往下走。下次答顺了，下一层大概率会来。按考点列出最可能的追问：

**事件循环** → 手写一个 Promise（至少 then 的链式和状态机）→ async/await 是怎么被编译成 Promise 链的 → 写一个并发数受限的任务调度器。

**宏微任务** → `await` 后面跟一个 thenable 和跟一个 Promise，微任务轮数差几轮 → `queueMicrotask` 和 `Promise.resolve().then` 有什么区别。

**setTimeout 精度** → 让你手写一个精确倒计时 → 怎么做一个「页面切后台也能对齐」的倒计时 → requestAnimationFrame 和 16.6ms 帧预算的关系。

**URL 到可交互** → 首屏慢怎么排查（Performance 面板 + Waterfall 看哪一段长）→ 白屏怎么监控 → preload / prefetch / preconnect 分别什么时候用 → HTTP/2 之后还需要雪碧图和域名分片吗。

**性能指标** → LCP 具体测的是哪个元素、怎么优化 → CLS 由什么造成、骨架屏怎么避免 → INP 取代 FID 的原因。（这三问已在第一节「性能指标全景」里答完）

**缓存** → 一次完整的 HTTP 请求都有哪些缓存层（浏览器 → Service Worker → CDN → 网关）→ CDN 回源策略 → 为什么 ETag 在多机部署会失效。

**React re-render** → Fiber 为什么要做成链表、可中断意味着什么 → diff 的三条假设、为什么 index 当 key 会出问题 → Hooks 为什么不能写在条件语句里（链表顺序，已在「Hooks 系统梳理」答完）。

**memo 化三件套** → useEffect 的闭包陷阱怎么解 → useRef 和 useState 的取舍 → React 19 Compiler 自动 memo 之后这三个 API 还有必要吗。（前两问已在「Hooks 系统梳理」答完）

**请求竞态** → 手写带超时和重试的请求封装 → 怎么做请求去重（同一个 key 并发只发一次）→ 并发请求怎么限流。

**Webpack** → Loader 和 Plugin 的区别、各自在哪个阶段生效 → Tree Shaking 为什么依赖 ESM、`sideEffects` 起什么作用 → 手写一个简单 Plugin（你有插桩经验，这题是主场）。

**监控** → source map 怎么在不泄露源码的前提下还原堆栈 → 错误怎么聚合去重（按堆栈指纹）→ 上报量太大怎么采样又不丢关键错误。

**Monorepo** → CI 怎么只跑受影响的包（affected detection）→ pnpm 的硬链接和幽灵依赖 → changesets 怎么管版本。

## 六、本场没问、但同一档位大概率会问的

一定要意识到：**一场面试是抽样，不是完整题库**。这场四十多分钟里，有几个前端面试的主菜整块没被碰到，不代表下一场不问。尤其面试官自己在反问环节说了「基础能力一定还是得有」，等于明确表态基础轮会继续考。

**JS 语言基础整块没问** — this 绑定规则、原型链与继承、闭包、作用域、`new` 的过程、类型转换。手写题一道都没出：防抖节流、深拷贝（循环引用怎么处理）、柯里化、`call/apply/bind`、`Promise.all` / `allSettled` / `race`、数组扁平化。字节的编码轮出手写题的频率比出算法题还高，这块是明显的暴露面。

**CSS 完全没问** — 而面试官在反问里专门拿「校招同学连 CSS 选择器都答不上」举例，说明他心里 CSS 是基础线的一部分。至少要有：盒模型、BFC、flex 的三个属性含义、居中方案、层叠上下文、选择器优先级、`position` 各值、移动端 1px 和适配。

**网络只问了缓存** — 没问 HTTP/1.1 vs 2 vs 3、跨域（CORS 预检、Nginx 代理、为什么 JSONP 过时了）、HTTPS 握手、TCP 三次握手为什么是三次、XSS 和 CSRF 的防御。缓存这一题你答得磕磕绊绊，面试官很可能只是没时间继续往网络挖。

**React 原理层没问**（Hooks 部分已补，见第二节「Hooks 系统梳理」）— 这次全是使用层（re-render、memo 化、竞态）。原理层的 Fiber 设计动机、Render/Commit 双阶段、Hooks 的链表实现、Diff 算法与 key、闭包陷阱，一道都没出。**还缺 Fiber 和 Diff 这两块**。以你简历上「高级前端」的定位，下一场大概率会挖这里。

**性能只问了指标没问手段**（已补，见第一节「性能指标全景」「性能优化手段」）— 问了 FCP/LCP/TTI 是什么，没问怎么优化。首屏优化、包体积治理、长列表虚拟滚动、大数据量渲染、图片优化，都得准备。你项目里有真实的详情页优化经验，这块本该是加分项。

**浏览器渲染细节没问** — 回流与重绘的触发条件、合成层、`will-change`、requestIdleCallback。

**TypeScript 没问** — 泛型、条件类型、`infer`、`unknown` vs `any`、类型体操入门。B 端项目基本都用 TS，这题问到的概率不低。

这一节不是让你现在就全补——是让你知道这份文档的边界：它把**这一场被问到的**梳理干净了，但它不是一份完整的八股复习范围。完整范围看 `复习内容总览/前端面试知识大纲.md`。

### React

```
useMemo     → 缓存「计算结果」，返回任意类型
useCallback → 缓存「函数引用」，返回函数本身
React.memo  → 包组件，props 浅相等则跳过 render
useCallback(fn, deps) === useMemo(() => fn, deps)

setState → 一定 schedule 本组件 re-render，与 render 是否读取该 state 无关
Object.is 新旧相同 → bail out
父 re-render → 子默认跟着 render；memo + props 不变 → 子可跳过
子组件 state 变 → 只影响该子树，不带动父组件
key 变化 → unmount + remount，state 重置
useEffect 依赖变 → effect 重跑，不是 render 的原因
```

### 缓存

```
强缓存   不发请求  200 (from memory/disk cache)  Cache-Control: max-age / Expires
协商缓存 发请求    304 Not Modified              ETag / Last-Modified
优先级   先强缓存，过期才走协商

no-cache → 可以存，但每次必须向服务器验证（≠ 协商缓存本身）
no-store → 完全不存
发版     → HTML no-cache + JS/CSS contenthash 强缓存一年
```
