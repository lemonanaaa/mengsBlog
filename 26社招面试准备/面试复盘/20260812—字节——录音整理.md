## 一、项目深挖

### 1.1 精准测试小工具（本场重点，连续 5 问）

---

#### Q1-1 你这个是属于单测的覆盖对吧？就类似于测试或者单侧的覆盖能力？

**我的回答**：
- 它是单元测试的一个**补充**，不是替代
- 单元测试是写代码在项目里跑；这个是**插桩**手段，发布测试环境时在每一行打标记
- 页面运行时自动统计哪一行运行到了、哪一行没运行到
- 刷新页面用到哪些代码，就在覆盖到的行打勾
- 覆盖率报告和 **diff patch** 一对比，就能看到刷新页面时覆盖了多少改动代码，得到一个百分比

**自评**：✅ 原理和定位讲得清楚，主动对比了单测

**标准答案**：
- **Istanbul / babel-plugin-istanbul 类插桩**：构建阶段改写 AST，每行/每个 branch 注入计数器
- **运行时采集**：页面执行时上报 hit 信息
- **增量覆盖率** = 本次 diff 涉及的语句中被执行的比例（line coverage / branch coverage）
- 与单测区别：单测在 Node/JSDOM 环境跑用例；插桩覆盖在**真实浏览器 + 真实用户操作路径**下统计，测的是「你手点的那条链路」

**考察目的**：
- 看你做的是不是「真做过」还是只挂了覆盖率数字
- 能不能区分 **unit / integration / E2E / 插桩覆盖** 的边界和适用场景

**拓展**：
- 插桩会**增大 bundle、略降性能**，只在 test 环境开启
- branch 未覆盖（红色）常见于 `if/else` 只走了半边、`?.` 短路、三元表达式
- 面试可主动提：**不能替代单测**，适合「研发自测是否走过改动代码」；边界 case 仍要靠用例设计
- 你们实际是在 Webpack 解析阶段命中包插入规则 — 能展开讲 loader/plugin 钩子

---

#### Q1-2 观测覆盖率的主要作用是什么？

**我的回答**：
- 开发和测试的比例有要求，希望**降低测试介入比重**
- 自测项目变多，项目堆在一起时不知道「这个测了没、那个测了没」
- 有这个工具，发布测试环境后看页面，就能知道这次改动测了多少地方，**提升研发自测效率**

**自评**：✅ 业务动机真实；⚠️ 没提「质量门禁 / 提测准入」等工程化表述

**标准答案**：
- **核心目标**：让研发对「本次改动是否被验证过」有客观依据，而不是凭感觉
- **典型用法**：
  1. 提测前：增量覆盖率 ≥ 阈值（如 80%）才允许提测
  2. 自测清单：报告标红未覆盖行，引导补测路径
  3. 团队度量：测开比下降、自测项目占比上升
- **不是目标**：追求 100% 行覆盖（性价比低）；替代 QA 全量回归

**考察目的**：
- 项目不能只会讲技术，要知道**为什么做、服务什么流程**
- 高级岗要看是否理解「度量 → 行为改变 → 组织效率」

**拓展**：
- 可补充：**覆盖率高 ≠ 没 bug**，只说明代码被执行过，不说明断言正确
- 和 CR、冒烟用例、核心链路 E2E 组合成质量体系
- 准备一句数据口径：测开比从 X 到 Y、自测项目占比从 A% 到 B%（即使没统计 bug 数）

#### Q1-3 有没有尝试 E2E 自动化，或者用 Agent 做页面 E2E？

**我的回答**：
- 有尝试，但推广不多
- **Agent** 帮写测试用例、有测试用例库
- **XTest** 框架在机票那边单独做过，接入麻烦，没大面积推广，AI 效果看起来不稳定
- 日常开发大部分还是 **插桩覆盖 + 手工测**；Agent 用得窄，没有大规模铺开

**自评**：✅ 诚实、有横向视野；⚠️ 可再结构化对比各方案优劣

**标准答案**（测试金字塔 + 你们现状）：

| 层级 | 方案 | 优点 | 缺点 |
|------|------|------|------|
| 单测 | Jest/Vitest | 快、稳定 | 前端 UI 逻辑难 mock |
| 插桩覆盖 | Istanbul + diff | 贴近真实操作、增量可视 | 不验证结果正确性 |
| E2E | Playwright/Cypress/XTest | 端到端 |  flaky、维护成本高、CI 慢 |
| AI Agent 写用例 | 自然语言生成 | 降编写成本 | 不稳定、需人工审核 |

**考察目的**：
- 测试体系完整性 — 不是只会做一个工具
- 对新技术（Agent）有没有**冷静判断**，而非盲目吹或全盘否定

**拓展**：
- E2E 推广难的核心：**选择器脆弱、环境依赖、 flaky 用例** — 可提 Page Object、测试数据隔离、retry 策略
- Agent 适合：**生成初版用例 / 补边界**，不适合无人值守直接上线
- 若被追问「你会怎么推 E2E」：选 1～2 条核心链路 + 稳定选择器 + 纳入 MR 门禁

### 1.3 订单详情 ~20 业务模块 — 架构设计（场景题，3 问）

---

#### Q3-1 订单详情有 20 个左右业务模块，你怎么设计前端架构？

**我的回答**：
- 首屏不需要全部信息，首屏先请求**资源信息、出行人**等排在最上面的模块
- 第一个请求里塞要哪些模块的名字，后端返回对应数据
- **懒加载**：设定时器或用户往下拉时，再触发下一个请求，把下一个模块名塞进去
- 这样对首屏渲染会好一点

**自评**：✅ 懒加载 + 按需请求思路对；⚠️ 缺模块注册、错误隔离、代码分割

**标准答案**：

```
┌─────────────────────────────────────┐
│  Shell（路由、布局、公共 Header）      │
├─────────────────────────────────────┤
│  Module Registry（模块名 → 组件映射）  │
│  ├─ 首屏模块：资源、出行人（SSR/首请求）│
│  └─ 非首屏：IntersectionObserver 触发  │
├─────────────────────────────────────┤
│  数据层：PuModel / 模块级 Model       │
│  通信：EventBus + 共享 Store           │
└─────────────────────────────────────┘
```

- **首屏**：BFF 聚合 or 模块化 API（`?modules=resource,traveler`）
- **非首屏**：滚动触底 / IO 预加载下一屏模块
- **代码**：`import()` 动态加载模块组件，独立 chunk
- **容错**：每模块 Error Boundary，单模块挂不影响整页
- **骨架屏**：模块级 Skeleton，避免布局跳动

**考察目的**：
- 大型 B 端详情页的真实经验 — 不是只会 CRUD
- 性能（首屏）、可维护（20 模块怎么拆）、可扩展（新模块接入）

**拓展**：
- 对比 **瀑布流加载 vs 一次聚合 vs 微前端** — 20 模块同团队维护用模块化 + 懒加载即可；跨团队才考虑 qiankun/MF
- 订单详情常见坑：模块间**数据依赖**（出行人 ID 其他模块要用）→ 见 Q3-2
- 可提 **React.lazy + Suspense** 或你的 PuModel 分层

---

#### Q3-2 这些模块之间是怎么通信的？

**我的回答**：
- 可以**更新组件 state**
- 举例：主接口出行人只给了 `clientId`，往下翻 hover 要展示姓名、身份证号，需单独调出行人接口，回来和 `clientId` 匹配再展示
- 一开始只显示 ID，另一个接口回来后更新成姓名等
- 项目里还有**发布订阅**，后面模块数据出来会 `eventBus.on` 通知前面模块变化

**自评**：✅ 有真实业务例子；⚠️ 可系统归纳通信模式

**标准答案** — 模块间通信选型：

| 场景 | 方案 |
|------|------|
| 父子/兄弟简单数据 | props + callback |
| 跨多层模块 | Context / 全局 Store（PuModel） |
| 一对多通知（解耦） | EventBus / 自定义事件 |
| 复杂联动 | 状态机（XState）/ 单向数据流 |
| 服务端状态 | React Query / SWR（缓存 + 失效） |

**你的 EventBus 方案适用**：「A 模块数据后到，通知 B 刷新」— 注意 EventBus 要**注销监听**防内存泄漏

**考察目的**：
- 20 模块避免 spaghetti — 有没有清晰的通信分层
- 真实业务里的 ID 关联、异步回填

**拓展**：
- EventBus 缺点：难追踪、难调试 → 大规模用 Store + devtools
- 「什么时候不用 EventBus」：强一致状态放 Store；EventBus 只适合 fire-and-forget 通知
- 订单场景：模块权限不同（供应商只能看部分模块）→ 模块注册表带 `visible` 配置

---

#### Q3-3 平时使用的 UI 状态管理用的是什么？

**我的回答**：
- 框架是 **Rematch**，封装了一层，和 **PuModel** 结合
- Rematch 比 Redux 多一些东西
- 对商家 PC 和 H5 都有，相同逻辑抽象到 **PuModel**，PC/H5 的 Controller 分别注入 PuModel，加上下文，Controller 就有 PuModel 里的状态、计算等
- 不太推荐 `useEffect`，只有特别简单的（页面内展开收起）才用原生 Hook
- 大部分功能 PC/H5 都有，希望逻辑放同一处，状态管理基本用 PuModel 那套

**自评**：✅ 同构架构讲得清楚；⚠️ 没解释 Rematch 具体简化什么

**标准答案**：
- **Rematch**：Redux 之上封装，内置 model、reducers、effects，减少 boilerplate
- **PuModel**（你们内部）：可描述为「跨端共享的业务 Model 层」，Controller（View 层）只负责 UI 和 dispatch
- **为什么少用 useEffect**：副作用放 Model effects 里统一管理，避免 PC/H5 各写一套 effect 逻辑不一致

**考察目的**：
- 状态管理不是背 API，看**团队工程化选型理由**
- 同构 B 端经验 — PC/H5 双端维护成本

**拓展**：
- 若问「为什么不用 Zustand/Jotai」：历史 Rematch 生态 + PuModel 沉淀 + 双端同构
- Rematch vs Redux Toolkit：都可，重点是你能讲清**分层**（View / Model / Service）
- `useEffect` 滥用问题：应用层应用 PuModel effects；组件内仅 UI 副作用（监听 resize 等）

## 二、JavaScript / 浏览器八股

### 2.1 Event Loop

---

#### Q4-1 介绍一下浏览器里事件循环的机制

**我的回答**：
- 一轮执行：先执行一轮**宏任务**
- 一个宏任务执行完后，把当前**微任务栈**里的微任务全部执行一遍
- 再执行第二个宏任务，再清空微任务……循环

**自评**：✅ 主流程正确

**标准答案**：

```
   ┌──────────────┐
   │  取宏任务     │ ← script / setTimeout / I/O / UI rendering
   └──────┬───────┘
          ▼
   ┌──────────────┐
   │ 执行宏任务    │
   └──────┬───────┘
          ▼
   ┌──────────────┐
   │ 清空微任务队列 │ ← Promise.then / queueMicrotask / MutationObserver
   │ (直到空)      │    微任务里再产生微任务会继续执行
   └──────┬───────┘
          ▼
   ┌──────────────┐
   │ 是否需要渲染  │ ← 通常每轮 event loop 最多渲染一次
   └──────┬───────┘
          └──→ 下一个宏任务
```

- 首次执行：整个 `<script>` 是一个宏任务
- **Node 与浏览器差异**：Node 有 phases（timers、poll 等），不要混答

**考察目的**：异步基础 — 后面 setTimeout、Promise 题都依赖这个

**拓展**：
- 经典输出题：`setTimeout(()=>console.log(1),0); Promise.resolve().then(()=>console.log(2)); console.log(3)` → 3,2,1
- `requestAnimationFrame` 回调在**渲染前**执行，不是微任务
- 长微任务链会阻塞输入响应 — Performance 面板看 Long Task

---

#### Q4-2 Promise、定时器这类属于什么任务？

**我的回答**：
- **Promise** 是微任务，每轮都会执行，实时性要求高
- **setTimeout / setInterval** 是宏任务

**自评**：✅

**标准答案**：

| 宏任务 | 微任务 |
|--------|--------|
| script | Promise.then/catch/finally |
| setTimeout/setInterval | queueMicrotask |
| I/O | MutationObserver |
| postMessage | async/await（await 后面相当于 Promise.then） |
| UI rendering（浏览器） | process.nextTick（Node，优先于 Promise） |

**考察目的**：精确分类 — 为 setTimeout 延迟题铺垫

**拓展**：
- `new Promise(fn => fn())` 里同步部分立即执行，`.then` 才是微任务
- `async` 函数在 await 前是同步，await 后代码进微任务

---

#### Q4-3 浏览器一次刷新流程中，微任务过多会导致什么问题？影响刷新效率吗？

**我的回答**：
- 微任务执行完后会检查有没有**渲染**工作
- 微任务过多可能**阻塞渲染**

**自评**：⚠️ 方向对，可更完整

**标准答案**：
- 每轮宏任务后必须**清空全部微任务**才能进入渲染阶段
- 若微任务持续产生新微任务（死循环式），会导致 **render starvation** — 页面白屏、卡顿、无法交互
- 影响的不只是「刷新效率」，还有 **INP/TTI**、用户输入无响应

**考察目的**：知道 Event Loop 与**渲染管道**的关系，不是背定义

**拓展**：
- 解决：拆分微任务（`setTimeout(0)` 让出宏任务）、`requestIdleCallback`、Web Worker
- React 18 自动批处理减少重复 render，但 state 更新仍在 JS 线程
- 用 `queueMicrotask` 滥用也会踩坑

### 2.2 setTimeout 精度

---

#### Q4-4 为什么 setTimeout(fn, 3000) 不一定 3 秒后执行？受什么影响？

**我的回答**（较乱，但核心点有）：
- setTimeout 是宏任务
- 3 秒到后是把它放进宏任务队列，不是立刻执行
- 当前这轮宏任务对应的微任务要先执行完
- 队列里可能先执行别的宏任务，再轮到我们这个 3 秒的
- 主线程复杂时，console 不一定在 3 秒后打印

**自评**：⚠️ 机制理解对，表达紧张、顺序略乱

**标准答案**：
1. **计时 ≠ 执行**：3 秒只是「到期可入队」，入队后还要等前面宏任务 + 微任务跑完
2. **微任务阻塞**：到期时刻若微任务堆积，继续推迟
3. **主线程繁忙**：长 JS 任务占用
4. **浏览器节流**：后台标签 minimum delay 1000ms+；嵌套 5 层以上 minimum 4ms
5. **系统负载**：定时器精度本身毫秒级，不保证实时系统

**考察目的**：异步 + 真实开发经验 — 不是只知道定义

**拓展**：
- 经典题：`setTimeout(fn, 0)` 实际延迟通常 > 0
- `setInterval` 同样漂移，且可能**堆积**（执行时间 > 间隔）

#### Q4-5 平时遇到过吗？有什么解决办法？

**我的回答**：
- 有点忘记了
- 提到 **setInterval** 设置一次循环 3 秒好像可以 — **这是错的**
- 说之前看到过解法，瞟了一眼忘了

**自评**：❌ 没给出有效方案，setInterval 答错

**标准答案**：

| 场景 | 方案 |
|------|------|
| 动画/倒计时 UI | `requestAnimationFrame` + `performance.now()` |
| 不能阻塞 UI 的计时 | Web Worker 内 `setInterval` |
| 避免堆积 | 递归 `setTimeout` 代替 `setInterval` |
| 业务防抖 | `clearTimeout` 取消过期 timer |
| 需要绝对时间对齐 | 服务端时间戳校准，不只靠客户端 timer |

```javascript
// 较精确的延迟
function delay(ms) {
  return new Promise(resolve => {
    const start = performance.now();
    function tick(now) {
      if (now - start >= ms) resolve();
      else requestAnimationFrame(tick);
    }
    requestAnimationFrame(tick);
  });
}
```

**考察目的**：八股能否落到工程实践

**拓展**：
- 订单倒计时/支付超时：应用**服务端截止时间** + 客户端展示，不用纯 setTimeout 做关键逻辑
- `document.hidden` 时暂停 timer 逻辑

### 2.3 URL → 页面可交互

---

#### Q4-6 从用户输入 URL 到页面可以操作，发生了哪些事？

**我的回答**：
- 浏览器解析 URL，DNS 查询，找到地址，发 HTTP 请求
- 拿回页面，浏览器解析 HTML
- 遇到 CSS、JS 加载
- CSS 遇到时会阻塞 — 修正为同步下载 CSS
- 遇到 JS，不用 defer/async 会停止当前线程去下载执行；`async` 开下载线程，页面加载完执行；`defer` 整个页面解析完再执行

**自评**：⚠️ 主链路有，缺 TCP/TLS、DOM 树/渲染树、分层绘制；CSS/JS 表述有小瑕疵

**标准答案**（完整链路）：

1. **导航**：URL 解析 → DNS → TCP 三次握手 → TLS（HTTPS）→ HTTP 请求
2. **响应**：HTML 字节流到达
3. **解析 HTML**：构建 DOM 树；遇 `<link>` CSS **阻塞渲染**（不阻塞 DOM 解析，但阻塞 Render Tree）
4. **解析 CSS**：构建 CSSOM → Render Tree → Layout → Paint → Composite
5. **遇到 `<script>`**：
   - 默认：阻塞 HTML 解析，下载并执行
   - `defer`：并行下载，DOMContentLoaded 前按序执行
   - `async`：并行下载，下完立即执行（乱序）
6. **加载完成**：`load` 事件；JS 绑定交互
7. **可交互**：主线程空闲、关键 handler 绑定 → TTI

**考察目的**：性能优化、首屏问题的知识基础

**拓展**：
- CSS 在 head、JS 放 body 底或 defer 的原因
- 关键渲染路径 CRITICAL RENDERING PATH
- preload / prefetch / preconnect 区别
- HTTP/2 多路复用对「CSS 阻塞」讨论的影响

#### Q4-7 「页面展示出来」和「页面可以操作」的区别？

**我的回答**：
- 以为是同一时间点，被问后意识到不是
- 展示出来可能还有 JS 没加载
- 可能有占位符，先展示页面，后面拿到数据再渲染

**自评**：⚠️ 直觉对，没主动说出 TTI

**标准答案**：

| 概念 | 含义 | 典型指标 |
|------|------|----------|
| 展示出来 | 用户看见内容 | FCP、LCP |
| 可以操作 | 能稳定点击、输入、滚动 | **TTI**、FID/INP |

- 中间可能：JS 未执行完、Hydration 未完成、长任务阻塞主线程、骨架屏已显示但按钮未绑定事件
- **TTI** 判定：安静窗口（如 5 秒内无 long task）、关键网络请求完成

**考察目的**：性能指标是否真懂 — 字节很看重

**拓展**：
- Core Web Vitals：LCP、INP、CLS
- SSR 场景：FCP 快但 TTI 慢（Hydration 成本）
- 优化：代码分割、减少 main thread work、defer 非关键 JS

### 2.4 缓存

---

#### Q4-8 强缓存和协商缓存有什么区别？

**我的回答**：
- 强缓存：`Cache-Control`，`no-cache` 是可以缓存但要协商；`no-store` 不让缓存
- 强缓存：发请求前先查浏览器存储，有就直接命中
- 协商缓存：返回 `max-age`，超出再发请求；不超出用本地 — **部分混淆**
- 协商缓存 304

**自评**：⚠️ 核心有，`no-cache`/`no-store`、200 vs 304 表述需理顺

**标准答案**：

| | 强缓存 | 协商缓存 |
|---|--------|----------|
| 是否发请求 | **不发** | **发**（带验证头） |
| 响应 | 200 (from memory/disk cache) | 304 Not Modified + 用本地 |
| 控制头 | `Cache-Control: max-age` / `Expires` | `ETag` / `Last-Modified` |
| 优先级 | 先强缓存，过期才协商 | — |

- **`no-cache`**：可存，但每次必须**向服务器验证**（常配合 ETag）— 不是「协商缓存本身」
- **`no-store`**：完全不存

**考察目的**：发版、静态资源、用户反馈「看不到新功能」的基础

**拓展**：
- 最佳实践：**HTML no-cache + JS/CSS hash 强缓存一年**
- `ETag` 在分布式 CDN 上可能有问题（inode 不同）→ 用 contenthash 文件名更稳
- `Vary` 头、Service Worker cache 策略

---

#### Q4-9 发版后用户一直加载旧资源，怎么排查和解决？

**我的回答**：
- 让用户**无痕浏览器**或**清除缓存**
- 供应商难提供 trace，可能本地复现
- 向用户要 ID 查日志，看请求到哪个镜像版本

**自评**：⚠️ 用户侧排查有，缺工程侧根治方案

**标准答案**：

**工程侧（根治）**：
1. JS/CSS 文件名带 **contenthash**，新部署 = 新 URL
2. **HTML 入口**不长期强缓存
3. CDN 刷新 / 版本号 query（不推荐单独 query，应用 hash）

**排查侧**：
1. 看 Response Headers：`Cache-Control`、`Age`、`X-Cache`
2. 对比实际加载的 `app.xxx.js` hash 与最新发布
3. Service Worker 是否 serve 旧 cache
4. 浏览器扩展、公司代理缓存

**用户侧**：硬刷新 Ctrl+Shift+R、清站点数据

**考察目的**：真实 B 端发版问题处理经验

**拓展**：
- 灰度发布 + 版本上报（你们的监控可采集 `buildId`）
- 「强缓存命中但 HTML 是旧的」→ 入口 HTML 缓存策略问题

## 三、React 八股

### 3.1 重新渲染

---

#### Q5-1 React 组件什么情况下会触发重新渲染？

**我的回答**：
- `useEffect` 依赖的值更新时 — **不准确**，混淆了 effect 重跑和 render
- 父组件传入 props 变化会导致子组件重新渲染
- 被追问「还有其他方式吗」→ 答「加 key 吗？」（方向沾边但没说清 key 变化 = unmount + remount）

**自评**：⚠️ 只答了一部分，且第一反应答到 useEffect 上，暴露心智模型不清

**标准答案** — 触发 re-render 的条件：
1. 自身 **useState / useReducer** dispatch
2. 父组件 re-render（默认子组件也 re-render）
3. **Context** 订阅的值变化
4. **forceUpdate**（类组件）/ 父组件 key 变化导致 remount
5. 父组件传入的 **props 引用变化**

**不触发**：子组件 state 变不会导致父组件 re-render；memo 子组件 props 浅相等则跳过

**考察目的**：性能优化、React 心智模型

**拓展**：
- React 18 自动批处理：多次 setState 一次 render
- Strict Mode 开发环境 double render

---

#### Q5-2 子组件内部 state 变化，会不会导致重新渲染？

**我的回答**：
- 一开始说不会，后来改口说可能会
- 想到虚拟 DOM、useState 初始化更新、依赖值变化会更新

**自评**：⚠️ 最终结论对，过程犹豫

**标准答案**：
- 子组件内部 `setState` → **该子组件** re-render（函数组件重新执行）
- **不会**导致父组件或兄弟组件 re-render（除非向上传递 callback 里改了父 state）
- 重新 render ≠ 重新 mount；DOM 可能通过 diff 复用

**考察目的**：render 范围边界 — 优化 memo 的前提

**拓展**：
- 状态**就近放置**：只影响子树的 state 放子组件，避免父 re-render 连带
- key 变化 = unmount + remount，state 重置

---

#### Q5-3 触发 setState 后，整个组件会重新渲染吗？render 里没用到这个 state 呢？

**我的回答**：
- 也分情况
- 页面用到这个值就会重新渲染
- 页面没用到这个值应该就不会重新渲染 — **错误**

**自评**：❌ 关键错点

**标准答案**：
- `setState` 会**调度该组件 re-render**（函数重新执行），与 render 函数里是否「读取」该 state **无直接关系**
- 若新 state 与旧 state `Object.is` 相等 → **bail out**，不 re-render
- re-render 后若 JSX 输出相同 → DOM 可能不变，但组件函数仍执行了（除非 bail out）
- React 不会细粒度「只重渲染用到该 state 的那一行 JSX」（不像 Vue 依赖追踪）

**考察目的**：React 更新粒度 — 高频考点

**拓展**：
- 性能优化靠 `memo`、拆分组件、状态下沉，不是指望「没读到就不 render」
- Concurrent Mode 下 render 可中断

---

### 3.2 useMemo / useCallback / React.memo

---

#### Q5-4 三者分别解决什么问题？

**我的回答**：
- 都用来缓存，具体区别忘了
- 混淆：useMemo 返回函数/组件；useCallback 返回 Promise（错）；销毁时机不一样
- 最后纠正：useCallback 返回函数

**自评**：❌ 核心区别没答稳

**标准答案**：

| API | 缓存什么 | 返回值 | 典型场景 |
|-----|----------|--------|----------|
| `useMemo(fn, deps)` | 函数**执行结果** | 任意类型（对象、数组、数字） | 昂贵计算、稳定 props 引用 |
| `useCallback(fn, deps)` | 函数**引用** | 函数本身 | 传给 `memo` 子组件的 callback |
| `React.memo(Cmp)` | 组件 render 结果 | 组件 | props 不变则跳过 render |

- 关系：`useCallback(fn, deps)` === `useMemo(() => fn, deps)`
- **滥用有害**：缓存本身有 deps 比较成本；普通组件不必全包 memo

**考察目的**：性能优化是否理解原理，不是只会背「缓存」

**拓展**：
- 经典题：输入框 + 列表，`useCallback` 配合 `memo` 列表项
- 依赖数组为空 `[]` vs 不传 deps 的区别
- React Compiler（19）自动 memo 后这些 API 可能减少

### 3.3 请求竞态

---

#### Q5-5 输入框/筛选项连续发请求，B 先返回 A 后返回，A 覆盖 B，怎么解决？

**我的回答**：
1. **防抖**：等停止操作 500ms 再发 — 合理但避开了「必须并发」
2. 回到正题：**请求标识** — 保存当前筛选 key/value，请求回来时和当前选择比对，对才展示
3. 还提到尽量不并发、订单场景发请求后状态改变不允许再发第二个

**自评**：✅ 标识比对方案对；⚠️ 缺 AbortController、缺主动提防抖+取消组合

**标准答案**（按优先级）：

1. **AbortController** — 新请求取消旧请求（最干净）
2. **递增 requestId / stamp** — 过期响应丢弃
3. **防抖 / 节流** — 减少无效请求
4. **React Query / SWR** — `queryKey` 变化自动 ignore 旧结果
5. **后端** — 幂等、按 session 只取最新

```javascript
// 推荐写法
useEffect(() => {
  const ctrl = new AbortController();
  fetch(url, { signal: ctrl.signal }).then(setData);
  return () => ctrl.abort();
}, [keyword]);
```

**考察目的**：B 端列表/筛选高频场景 — 真实工程能力

**拓展**：
- 订单详情切换 ID 时同样竞态
- loading 态要配「只对最新请求生效」
- 防抖 500ms 和 Abort 可组合

## 五、算法

### 5.1 最长递增子序列（LIS）

**原题**：输入一个整数数组，输出**一组**最长递增子序列（**不要求连续**）。
面试官口头举的例子是 `3 5 7 8` 这一组；我调试时打出来的数组接近 `[1,2,8,3,5,7,...]`。

> ⚠️ **口径待核**：原记录写成「`[1,2,8,3,5,7,1]` → `[3,5,7]` 或 `[2,3,5,7]`」，这是**错的** —

**标准答案**：

**方法一：DP O(n²)** — 面试先写这个，好还原路径

```javascript
function lis(nums) {
  const n = nums.length;
  const dp = Array(n).fill(1);
  const prev = Array(n).fill(-1);
  let maxLen = 1, maxIdx = 0;

  for (let i = 1; i < n; i++) {
    for (let j = 0; j < i; j++) {
      if (nums[j] < nums[i] && dp[j] + 1 > dp[i]) {
        dp[i] = dp[j] + 1;
        prev[i] = j;
      }
    }
    if (dp[i] > maxLen) { maxLen = dp[i]; maxIdx = i; }
  }

  const res = [];
  for (let i = maxIdx; i >= 0; i = prev[i]) res.unshift(nums[i]);
  return res;
}
```

**方法二：贪心 + 二分 O(n log n)** — 求长度；还原路径需额外记录

```javascript
function lisLength(nums) {
  const tails = [];
  for (const n of nums) {
    let l = 0, r = tails.length;
    while (l < r) {
      const m = (l + r) >> 1;
      if (tails[m] < n) l = m + 1;
      else r = m;
    }
    tails[l] = n;
  }
  return tails.length;
}
```

**考察目的**：
- 基础算法能力 — 字节必考
- 能否快速识别：**子序列 → DP / 贪心**，**连续子数组 → 滑动窗口**

**拓展**：
- 最长递增**子串**（连续）才用滑动窗口
- 变体：最长递减、俄罗斯套娃信封、删数成 LIS
- 面试写 DP 版 + 口述贪心优化即可
